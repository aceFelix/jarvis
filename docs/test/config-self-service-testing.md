# 自配置层实机走查清单（阶段 12 P1）

> 交付内容：模型侧的 `ConfigList` / `ConfigSet` 两个工具 + 28 项配置真源表（15 auto /
> 12 confirm / 1 禁改，模型可见 27）+ 桌面与感知面板从同一张表派生
> + 五种 `apply_mode` + `/undo` 配置回退。
>
> 一句话判据：**用户只说话，jarvis 能把体验类配置改对并当场生效，且说得出原值多少、
> 怎么回退。**
>
> @author aceFelix　|　更新：2026-10-26

## 0. 前置

### 0.1 三个窗口的分工

| 窗口 | 干什么 | 命令 |
|---|---|---|
| A | 跑桌面壳（含后端） | `cd jarvis-desktop && npm run dev` |
| B | 盯着配置文件的变化 | `tail -F ~/.jarvis/settings.toml`（PowerShell 用 `Get-Content -Wait`）|
| C | 查副作用账本 | `tail -F ~/.jarvis/actions.jsonl` |

### 0.2 先备份配置

```bash
cp ~/.jarvis/settings.toml ~/.jarvis/settings.toml.bak
```

后面每一项都会真改文件。走查完想还原就 `cp ~/.jarvis/settings.toml.bak ~/.jarvis/settings.toml`。

### 0.3 确认后端是新代码

`ConfigList` / `ConfigSet` 是本次新增的工具，**改完代码必须重启后端**（桌面壳退出重开）。
判据：在对话里说「你能改哪些配置」，能列出清单即新代码已生效；若模型说"我没有这个工具"，
说明还在旧进程上。

### 0.4 本机当前状态（2026-10-26 预演实测，供你对照）

| 项 | 当前值 | 影响哪一节 |
|---|---|---|
| `[percept] enabled`（感知总开关） | **开** | §2.2 / §2.4 可以直接验，无需先开总开关 |
| 开着的感知源 | window / file / vcs / mail **共 4 个** | 改一个源后回执的"启用 N 个源"会变成 3 |
| `[tts] volume` | **100** | §2.1 回执应是 100 → 30（不是 50）|
| `[policy.notify_budget] daily_max` | **10** | §3.3 回执应是 10 → 20 |
| `[actions] journal_enabled` | **开** | `/undo` 可用 |

> ⚠️ §2.4 关总开关会把上面 4 个源**一起停掉**（这是设计如此）。验完记得再说一句
> 「把感知打开」恢复——回执会是"总线已装配（启用 N 个源）"。

> 📋 **下面每张表的「判据」列都是预演实跑出来的回执原话**，可以直接逐字比对。
> 预演在 `settings.toml` 的临时副本上完成，没有动你的真实配置。

### 2.4 感知总开关（`confirm` + `percept` 双属性）

这一项同时是"要确认"和"要重装配"，而且它的回执文案有一处容易写错的地方：

| # | 操作 | 判据 |
|---|---|---|
| 2.4.1 | 说「把感知整个关掉」 | 先弹确认（正文含「感知层总开关」）；同意后回执：`- 感知层总开关：开 → 关` / `感知层总开关已关闭，总线已停（逐源开关也随之失效）` |
| 2.4.2 | 核对上面那条文案 | **不能**是「已重装配感知总线（启用 0 个源）」——那会让人以为总线还在、只是没源在采 |
| 2.4.3 | 再看感知源面板 | 全部灰掉（总开关关 = 逐源开关全部失效）|
| 2.4.4 | 此时再说「把仓库状况感知关掉」 | 回执：`已保存；感知层总开关关着，当前没有总线可重装配（打开总开关时会按这份配置装配）`——这才是诚实的说法，不该说「宿主未接线」（接线是好的，只是没总线）|
| 2.4.5 | 说「把感知打开」并确认 | 回执：`- 感知层总开关：关 → 开` / `感知层总开关已打开，总线已装配（启用 N 个源）`；**总线是当场现装的**，不用重启 |

### 2.5 感知名单类（P2 新增，`list` + `confirm` + `percept`）

P2 把面板早就能改、但真源表里没有的 6 项补上了；它们现在对模型开放（留痕开关除外）。
名单类改的是"看什么"，所以都要先确认。

| # | 操作 | 判据 |
|---|---|---|
| 2.5.1 | 说「守望目录只盯 下载目录」并确认 | 回执形如 `- 守望目录：（空） → E:/Downloads`——**不能**出现 `['E:/Downloads']` 这种带方括号引号的 Python 字串 |
| 2.5.2 | 说「把 1Password 加进排除应用」并确认 | `[percept] window_exclude_apps` 里新增该项；去重与 strip 生效 |
| 2.5.3 | 说「把感知事件留痕关掉」 | **拒绝**：`log_events 不能由模型改：本地留痕是感知行为的唯一审计线…`；面板上仍可自己关 |
| 2.5.4 | 在面板「观测范围」里加一条目录 | 与模型的改动互相可见（任一边改完另一边重拉），文件里注释不丢 |

## 3. 确认层：必须先问一句

| # | 操作 | 判据 |
|---|---|---|
| 3.1 | 说「每天最多提醒我 20 次」 | **先弹确认框**（正文含「每日播报上限」+「这类设置会影响何时能打断你」）|
| 3.2 | 拒绝确认 | 回执「用户拒绝」；`settings.toml` 里 `daily_max` **没变** |
| 3.3 | 再说一次并确认 | 回执：`- 每日播报上限：10 → 20` / `打扰预算已按新参数当场重建（当日计数不清零）` |
| 3.4 | 验证真的生效 | `~/.jarvis/notify_state.json` 里应能看到 `daily_max: 20` |
| 3.5 | 说「静默时段设成 23:00 到 7:00」 | 同样要确认；回执：`- 静默时段：18:00-19:30 → 23:00-07:00` |

> 💡 确认那一层用的是**权限管线已有的 ASK**，不是新造的确认框：所以拒绝之后的效果
> 与工具被拒一模一样（回执「用户拒绝」、文件零改动），不会出现"问过了但还是改了"。

## 4. 禁改项：拒绝要给出正确改法

| # | 你说 | 看到这样算过 |
|---|---|---|
| 4.1 | 「把沙箱关了」 | **直接拒绝**（不问确认），回执：`【错误】sandbox_enabled 不能由模型改：沙箱是权限护栏本身，模型改它等于给自己提权` |
| 4.2 | 「把 API Key 改成 sk-xxx」 | 拒绝，理由含「凭据只能由人填」 |
| 4.3 | 「邮箱密码也帮我改一下」 | 拒绝，同上 |
| 4.4 | 以上三项核对文件 | `settings.toml` **一个字节都没动**（`diff -u settings.toml.bak settings.toml` 无输出）|

> 💡 4.1 的确认框**不会弹**——这是有意的：禁改项走 DENY，不是 ASK。让它弹框反而
> 暗示"再确认一次就能改"，而这件事无论问多少次都不能改。

## 5. 脏值：不许落进文件

| # | 你说 | 判据 |
|---|---|---|
| 5.1 | 「音量设成 999」 | 回执：`【错误】tts_volume 不得大于 100`；文件没变 |
| 5.2 | 「音量设成 -1」 | 回执：`tts_volume 不得小于 0` |
| 5.3 | 「简报定在 8:30」 | 回执要求 `HH:MM`（`8:30` 不合法，要 `08:30`）|
| 5.4 | 一次说两件事且其中一个非法（「音量调到 20、语速设成很快」） | 回执只报语速那项错；**音量也没写进文件**（先校全部再落盘，整批不动）|

## 7A. 终端入口 `/config list` / `/config set`（P2）

与让模型改走**同一条写入路径**，但入口语义不同，三个差异点各验一条：

| # | 操作 | 判据 |
|---|---|---|
| 7A.1 | `/config list` | 列出 **27 项**（含当前值与否需要确认），禁改项（沙箱/凭据/留痕）**连名字都不出现** |
| 7A.2 | `/config set tts_volume 30` | 当场改：回执 `播报音量：x → 30`，`settings.toml` 里 `volume = 30`，`/undo` 能退回 |
| 7A.3 | `/config set daily_max 20`（需确认项）| **只给预览**（原值 → 新值 + 为什么要问），配置**一步没动**；再敲 `--yes` 才落盘 |
| 7A.4 | `/config set daily_max 200 --yes` | 超范围被拦，文件零改动（`--yes` 只能跳过确认，不能跳过校验）|
| 7A.5 | `/config set sandbox_enabled false --yes` | 拒且给出理由与正确改法（护栏是配置本身的属性，`--yes` 绕不过）|
| 7A.6 | 已存有名单时敲 `/config set vcs_repos`（不给值） | 提示写 `""` 才是清空；名单**不变**；写 `/config set vcs_repos "" --yes` 才真清空 |
| 7A.7 | `/config set window_exclude_apps A, B ,A` | 预览回显**规范化后**的 `A, B`（不是脏原始串），照抄回去能直接执行 |
| 7A.8 | `/config` / `/config show` | 全量自查面板照旧（老用法不破）|
| 7A.9 | `/config bogus` | 给用法，而不是默默打一屏配置 |
| 7A.10 | 改完看 `~/.jarvis/actions.jsonl` | 记 `tool=ConfigSet` 且 `args.entry="terminal"`（模型侧为 `"model"`）|

## 7B. 偏好账本（P3）

与改配置的区别：改配置是"现在就是 30"，偏好是"写代码时才是关"。

| # | 操作 | 判据 |
|---|---|---|
| 7B.1 | 「以后我写代码时别念出来」 | 回执给出"在 Code.exe 时 → 主动播报是否出声 = 关"与一个 id |
| 7B.2 | `/prefs` | 列出该条（条件 + 原话 + 命中次数）；再改一次音量，它**不应**出现在列表里 |
| 7B.3 | 切到编辑器，让它主动播一次 | 仅上屏/系统通知，**不朗读**（日志 `偏好降级`）；切回其他程序后恢复朗读 |
| 7B.4 | 「以后每天最多提醒 50 次」 | **被拒**（需确认类不能进偏好），提示改成一次性配置并会问一句 |
| 7B.5 | 让它记一条不带给条件的偏好 | **被拒**，提示改走 `ConfigSet`（无条件就是永久改配置，且不入账本）|
| 7B.6 | 「晚上十点以后小点声」 | 可记多条；`22-7` 这种跨午夜的要能正确处理 |
| 7B.7 | `/prefs forget <id>` / `/prefs clear` | 消失；且之后不再影响播报 |
| 7B.8 | `~/.jarvis/prefs.jsonl` | 每次记/忘/命中都追加一行，按 id 合并读；手改成坏行也不会让偏好系统起不来 |

### 7B-A. 提炼与多决策点（P3 后半）

| # | 操作 | 判据 |
|---|---|---|
| 7B.9 | 同一小时里三次把音量调低，然后 `/prefs suggest` | 给出 1 条候选，带「共 3 次」与当时原话，并明写**还没生效** |
| 7B.10 | 上一步后立即看 `/prefs` | 候选在「待确认」一节，已生效一节为空；此刻音量**不受影响** |
| 7B.11 | （接上）敲 `/prefs accept <id>` | 候选转「已生效」；再命中那个小时时段时，播报音量真的变小（日志 `偏好生效`）|
| 7B.12 | 9 点改一次、15 点改一次，再 `/prefs suggest` | **不提炼**（无共同上下文就不编条件），并说明规则 |
| 7B.13 | 「以后每天最多提醒 50 次」那类记录 | 即使反复改也**不会**被提炼（只能 auto 域）|
| 7B.14 | 拒掉一条候选后再 `/prefs suggest` | 同一条件**不再重提** |
| 7B.15 | `~/.jarvis/actions.jsonl` 里配置变更记录 | 含 `args.context`（当时的 app 与 hour）；没有它提炼无从下手 |
| 7B.16 | 说「以后我写代码时别念出来」，它记成 `when_app=Code.exe` | 回执里带「当前前台是 X」——**这才是能自己发现条件写错的地方** |
| 7B.17 | 同一条改成 `when_app` 写多个（`Code.exe,Qoder.exe`） | 描述显示「在 Code.exe / Qoder.exe 时」；前台是 Qoder.exe 时也命中 |
| 7B.18 | `/prefs` | 每条带「✓ 此刻命中 / － 此刻不命中」，末尾给当前上下文 |

## 8. 首启三问与「用几天后提议」（P4）

首启体验有两条相反的失败：问太多（用户没配完就烦了）、问错地方（把自动化卡死）。

| # | 操作 | 判据 |
|---|---|---|
| 8.1 | 在一个干净 HOME 下直接跑 `jarvis`（交互式终端） | 进入 **3 个问题**的开场：厂商 → API Key → 模型；问完能直接对话 |
| 8.2 | 第 ① 问选厂商、第 ② 问给有效 key | 第 ③ 问的模型列表来自**厂商实时返回**（提示「厂商返回 N 个可用模型」），不是内置表 |
| 8.3 | 模型列表里选「手动输入模型名…」 | 能自己填型号，不受列表限制 |
| 8.4 | 第 ② 问直接回车（不给 key） | **不发起在线拉取**；明确显示「未提供 API Key，未发起在线查询」+ 内置兑底；配置仍写盘 |
| 8.5 | 断网/无效 key 时给 key | 回落内置兑底，并显示**具体失败原因**（异常类型与信息）；流程不卡死（10s 超时）|
| 8.6 | 全程 | **不问工作目录**（默认当前目录）；结尾提示 `jarvis --workdir` 可改 |
| 8.7 | 把 `jarvis` 的输出管道给另一个命令（`jarvis \| cat`）| **不问任何问题**（非交互直接跳过）|
| 8.8 | 已配置好（有 model / key / 环境变量 key）再启动 | 不问；直接进 REPL |
| 8.9 | 首启时按 Esc 取消 | 写 `~/.jarvis/usage.json` 的 `declined`；**以后不再自动问**（`/init` 仍可手动）|
| 8.10 | 在 REPL 里敲 `/init` | 同样只问三件；`/init full` 才走完整五问（含自定义 base_url / 多模态）|
| 8.11 | 启动 ≥5 次、首启满 3 天，且账本里有"同一场合反复改同一项" | 启动后提**一次**候选（带依据）；再启动不再提 |
| 8.12 | 上一步那批候选 | 仍在「待确认」（`/prefs`），**未生效**；要 `accept` 才生效 |
