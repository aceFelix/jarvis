# 模棱两可的话，先问清楚再动手

> **类型**：交互行为改进（提示词层，非代码 bug）
> **触发**：用户澄清「看一下吧」是自己口误，并不是真让贾维斯看东西
> **修复日期**：2026-10
> **相关文件**：`agent/prompts/text_blocks.py`（核心原则第 4 条）
> **相关用例**：`tests/core/test_system_prompt.py`（+2 例）

---

## 0. 一句话结论

用户那句「看一下吧」本来就是句口误。贾维斯**猜**成了「大概想看屏幕」就去截图，
于是踩出一串 DSML 裸码。真正该做的是先回一句「先生，您想让我看什么？」——
**猜错的代价不是多查一次，而是他会以为你听懂了。**

---

## 1. 事情经过

语音模式下：

```
🧑 你说: 贾维斯在吗？
先生，我在。有什么吩咐？
🧑 你说: 看一下吧。          ← 用户自己的口误，他并没有想让贾维斯看什么
（思考：这个"看一下"很可能是指看屏幕——先生可能想让我看看屏幕上有什么。我先截个屏看看。）
<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="ScreenShot">
</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
🧑 你说: 你说什么呢，兄弟。
```

上一轮（见 `deepseek-dsml-toolcall-leak-fix.md` 五次补漏）修的是**技术侧**：
为什么它吐裸码、为什么工具不执行。这一轮用户把话说透了——

> 「其实这句话是我口误了，我没让贾维斯看啥……面对用户这种模棱两可的表述，
> jarvis 最好是先问清楚，而不是直接想当然的去做事。」

技术侧修完，它**能截屏了**。但按用户的标准，它**根本不该截屏**。

---

## 2. 为什么"猜"在这里格外危险

三个因素叠在一起，让猜测的成本被放大：

| 因素 | 说明 |
|---|---|
| 语音没有上下文 | 「看一下吧」前面的全部历史只有一句「贾维斯在吗」 |
| 口误是常态 | 语音输入没有回看的机会，说完自己也未必记得说了什么 |
| 猜错时**看不出来** | 截屏也执行了、也返回了，用户只会觉得"它怎么突然开始截图" —— 比报错更难察觉 |

模型当时的思考原话是「**很可能**是指看屏幕」。问题就出在这个"很可能"上：
它把一个模糊推断当成了足够行动的依据。

## 3. 现有机制为什么没拦住

两样东西其实都已存在，但没有起作用：

| 已有 | 位置 | 为什么没生效 |
|---|---|---|
| `AskUserTool` | `agent/tools/ask_user.py` | 那一轮 `build_tool_defs` 判了纯聊天 → `tools=[]`，**连 AskUser 都没下发给它** |
| 核心原则第 4 条「主动澄清」 | `agent/prompts/text_blocks.py` | 原文只说了「缺少关键信息（路径、参数、确认意图）时用 AskUser」——例子全是**任务类**参数，没说「口语含糊、宾语缺失」这种情形 |
| 纯聊天轮 | `tool_dispatch.build_tool_defs` | 上一轮已修：留 `ToolSearch` 让模型能自救，但**仍拿不到 `AskUser`** |

也就是说：**模型想问也问不了，而且提示词也没教它"这种话该问"。**

## 4. 修复：把判据写具体

改的是 `agent/prompts/text_blocks.py` 的核心原则第 4 条，从一句话扩成可执行的判据：

```
4. **模糊就先问，别猜着做**: 用户这句话里**动词有、宾语空**，而这个宾语在你手上的
   上下文里指不出**唯一**对象时，先用一句话问清楚 —— 不要挑一个"最可能的"照着做。
   - 该问：「看一下吧」（看什么？屏幕 / 某个文件 / 上一句话的结论？）
   - 该问：「改一下」「处理掉」「那个弄好了吗」（哪个东西、改成什么）
   - 不必问：「看一下 main.py」「把 a.txt 改成 alpha2」（宾语明确，直接动手）
   语音场景**尤其**要问：没有上下文、听错、口误、半句话都是常态，而这类话听起来
   又很像命令（先生说完自己也觉得"我到底说了啥"）。
   怎么问：（1）语音模式**直接说这句话**（"先生，您想让我看什么？"），
   不要调 `AskUser`——语音下它是阻塞式的，会卡住；
   （2）文本模式两者都行，信息很多时用 `AskUser`。
   宁可多问一句，也别照着猜到的对象跑一遍——猜错时他以为你听懂了，代价比多问
   一句大得多。
```

### 几个刻意的设计

- **判据要"形状化"**：「动词有、宾语空」是可以当场判断的语法形状，比「缺少关键信息」
  这种抽象说法更容易被照做。和上一轮 `_looks_fileish` 用「文件名形状」代替词表枚举
  是同一个思路。
- **必须给反例**：只写"该问"会让模型变成什么都问（用户更烦）。所以专门写了
  「不必问」的三个例子。
- **语音模式不让它调 `AskUser`**：`RichCLI.ask_user` 是**阻塞 stdin** 的
  （`Prompt.ask`），而语音循环跑在 `asyncio.run` 里 —— 让用户在对着麦克风说话时
  去终端打字回答案，既错位又有卡死事件循环的风险。
  同类教训已经写在同一文件的 DevServer 段：「Bash 的 kill/taskkill 在语音模式下
  会触发阻塞式权限确认，导致贾维斯卡住」。
  语音场景下**直接用嘴问**才是对的：TTS 念出来，用户用语音回答，本来就支持多轮。

## 6. 边界与已知局限

- **这一层是软约束**：提示词能提高"该问就问"的概率，但不保证每条模糊指令都会问。
  要硬保障只能靠正则判"动词+空宾语"，而那是自然语言理解，规则化必然误伤
  （和 `chat_detection` 堆词五次的历史一样）。
- **纯聊天轮仍拿不到 `AskUser`**：`_safety_defs` 目前只留 `ToolSearch`。文本模式下
  模型想用 `AskUser` 会拿不到，只能改用自然语言问 —— 可以接受（问得出来就行）。
  若以后要放开，**必须先解决语音模式下同步阻塞的问题**（改用 `ask_user_async`
  或语音专用的"口头提问"通道）。
- **需要真机验证**：prompt 类改动无法用单测证明模型行为，需在语音模式下重说
  「看一下吧」，看它是否先反问而不是去截图。建议**另起新会话**（旧会话里存着
  DSML 原文，会当"文本态调用示范"回灌）。

## 7. 教训

- **「修好它能做」不等于「修好它该不该做」。** 上一轮把 DSML 裸码修完，工具能正常
  执行了——但如果方向本身就错，越是修得顺滑，越是在错误的路上一路跑到底。
  用户一句"其实我口误了"把整个问题的层次抬高了。
- **同一件事在提示词里"提过"不等于"说得动"。** 原文第 4 条确实写了"不要瞎猜"，
  但例子全是路径参数，没覆盖「口语含糊」这一类；模型不会把抽象的劝告自动推广到
  新情形，得把具体的样子（含反例）摆出来。
- **能给"嘴"就别给"工具"**：语音场景里，让模型说一句话的成本远低于让它调一个
  阻塞式工具。选工具时要先问"这个工具在这个宿主里真的能用吗"。
