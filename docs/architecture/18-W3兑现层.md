## 一、解决什么问题

W1 判断层把"该不该打扰你"裁清楚了，W2 感知层把上游事件源接上了，但**兑现**这一栏
还是空的（见 [PLAN §0 的缺口对照](../roadmap/PLAN-butler-autonomy-upgrade.md)）：

| 症状 | 本层对策 |
|---|---|
| 确认一次"发这封邮件"就再也收不回，于是只能事事追问 → 主动性上不去 | 不可逆动作先进**延时窗口**（默认 30s），到点才真执行，期间 `/undo cancel` 可撤回 |
| 模型替你写了六个文件，事后想说"退回去"只能一句句手动改 | 每次破坏性本地写**引用本轮 shadow git 检查点**，`/undo` 一条命令整轮回退 |
| "替我盯着这件事，条件到了再往下做"没有承载体：`ScheduleTask` 只是闹钟 | **任务脊柱**：目标 → 有序步骤 → 条件等待 → 断点续跑，驱动器在条件满足后推一步 |
| 后台自主推进 = 无脑轮询烧钱 | 唤醒时刻由条件本身算出来（`time` 到点、`file_exists` 廉价 stat 节拍、`percept_event` 总线订阅回调），等待期间**一次 LLM 都不调** |

## 二、两条主线的分工

```
                    工具调用（已通过五层权限 + W1 闸门 + tool_before 钩子）
                                      │
                     ┌────────────────┴────────────────┐
              is_irreversible?                    is_destructive?
                     │ yes                                │ yes
        【W3.2 延时窗口】                          【立即执行】
        记 held + 冻结 args，本轮不执行               │
                     │ 到点                       执行成功
        【W3.2 到点重放】                              │
        按冻结 args 调 tool.call                记 applied
                     │                          + undo_spec=本轮检查点 cid
                 applied / failed                      │
                     └──────────┬───────────────────────┘
                                ▼
                     ~/.jarvis/actions.jsonl ──▶ /undo（撤单条 / 整轮 / 按任务批量 / 撤回窗口）

   ~/.jarvis/goals/<id>.json（目标台账）◀──▶ TaskDriver（后台一条线程）
        条件满足 → run_subagent 推一步 → 结果经 W1 打扰闸门播报
```

W3.2（账本）与 W3.1（脊柱）互相引用但互不侵蚀存储：脊柱步骤执行时产生的副作用照样
进同一本账（带 `task_id`），于是 `/undo --task <id>` 能按目标批量补偿。

## 四、副作用账本（W3.2）

### 4.1 为什么是一行一条的事件流，不是一个 JSON 文件

状态要能流转（`held → applied → undone` / `cancelled` / `failed`）。整量覆盖写在崩溃时
会把**整本账**丢掉；追加写最多坏最后一行，读时按 `id` 合并最新快照即可。
超 1MB 或条数超 500 触发轮转，轮转本身也是"临时文件 + `os.replace`"。

坏行处理是显式设计：解析失败的行跳过；**没有 `id` 的行必须丢掉**——`from_dict`
会给缺 id 的行现造一个随机 id，于是每次重读都从同一行编出一条"看起来合法"的幽灵记录
（`/undo list` 会多出一堆撤不动的空白项）。

### 4.2 `undo_spec` 只有两种形态

| 形态 | 内容 | 语义 |
|---|---|---|
| `checkpoint` | `{"kind","cid","workdir"}` | 本地破坏性写：撤销 = 恢复到本轮开始前的 shadow git 检查点（**整轮**粒度，本轮其他文件改动一并回退） |
| `none` | `{"kind","reason"}` | 外发类：补偿计划写不出真实回滚，就照实写"该动作已离开本机，无法撤回" |

两条硬口径：

1. **本地写必须有本轮 cid 才入账**。没有检查点就记，等于让 `/undo` 列出一堆撤不动的
   条目——宁可少记，不可假可撤销。
2. **账本不新建检查点，只引用宿主本轮已经打的那一个**。另建快照会把配额（每会话
   20 条）吃光，反噬 `/rewind` 依赖的那条 ref 空间。

cid 的来源是 `ctx.extra["checkpoint_cid"]`：检查点在轮前打，但 cid 要到轮末才挂到
用户消息上（`main.py` 与 `engine.py` 都是这个顺序），工具调用时刻消息里查不到。
两个宿主各补一行轮前写入。**"键存在但为空"与"键不存在"严格区分**：前者说明本轮确实
没有检查点（没装 git 或已关闭），必须照实返回"无"；去翻消息会拿到上一轮的 cid，
把"回到本轮开始前"做成"多退一轮"。

### 4.3 延时窗口：只延后，不豁免

`_run_one` 里的插入位置刻意在**五层权限判定、W1 策略闸门、`tool_before` 钩子之后**：
所有"允不允许做这件事"的判定都已成立，只是把"做"推迟到用户还能喊停的那一刻之前。

```
钩子通过 → is_irreversible? → 记 held + 冻结 args → 登记 call_later → 返回"已排入 30 秒窗口"
                                                              （本轮不执行 tool.call）
                                    30 秒后 ──▶ 重读账本状态 → 按冻结 args 真执行 → applied/failed
```

**返回给模型的文案本身就是行为约束**：窗口拦住的是一条 tool_use，而"把这件事做成"是模型的
目标。实机测过（2026-10-21）：只写"已排队、到点自动执行"时，模型会自己改用 `Bash curl`
完成同一件事——用户以为已被拦住的外发动作照常发生，窗口形同虚设。所以文案里必须明写
**【不要绕道】并举出等价路径**（curl / 脚本 / 浏览器模拟），同时要求"确实不能等就说明受阻原因、
由用户决定"。光有这一层只是提示侧约束，下面还有一层硬拦；复盘：
[w3-delay-window-bypass-fix](../fixlogs/w3-delay-window-bypass-fix.md)。

**软约束之外还有一层硬拦（口径 A 收窄版，2026-10-21 定）**：窗口里有未结案动作时，
`BashTool.check_permissions` 对**网络外发类**中风险命令关掉"沙箱自动放行"这条捷径、
改成问人（`agent/core/sandbox/risk_scorer.py::looks_network_outbound` 判通路不判危险度，
`agent/tools/bash.py::_hold_pending_reason` 取在窗项的展示文本作解释）。三点取舍：

- **只收外发通路**：`git commit`、`mkdir` 这类本机中风险命令照旧自动放行，不打扰；
- **收紧范围等于窗口生命周期**：`DelayWindow` 是进程内登记表，结案（applied /
  cancelled / failed）或重启后立即恢复自动放行，不会留下一个关不掉的收紧态；
- **可用 `[actions] hold_blocks_equivalent = false` 退回旧行为**：无 UI 环境（serve
  后台）里 ASK 会落成 DENY，若这种误伤不可接受就关掉它，只留文案约束。

四个必须写清楚的取舍：

- **必须返回一个正常的 `tool_result`**：本轮历史里已经留下了 `tool_use`，缺对应结果
  会让该会话之后所有请求被 API 拒收（见
  [dangling-tool-use-fix](../fixlogs/dangling-tool-use-fix.md)）。同时也要给 UI 回一条
  `tool_result`，否则桌面/工作台那张工具卡片永远转圈。
- **到点执行不走权限管线**：无 UI 时 ASK 会被 fail-closed 拒成 DENY
  （"需要用户确认但当前环境无 UI"），把用户刚批准过的动作自己拦掉，语义是错的。
  重放用的是账本里**冻结的那一份 args**，因此模型后续改口也改写不了已排队的动作。
- **重启后遗留的待发动作一律作废**（`resume_pending` → `cancelled`）：30 秒窗口的意义
  在于"人还坐在前面能喊停"，重启后没人在场，把一个外发不可逆动作自动补发出去
  是最不该发生的事。宿主启动时把作废项逐条播报。
- **用户中断（`abort_event`）即取消**：中断说明人还在且反悔了。

### 4.4 与操作审计的关系

`ToolAuditor` 记的是**事后流水**（`tool_call` 记录，用于排查与统计），账本记的是
**可执行的补偿计划**。两者共用同一次调用，各自落自己的文件（`~/.jarvis/actions.jsonl`
与审计留痕），互不代替。账本含收件人等敏感字段，只落用户目录，不随对话上传。

## 五、任务脊柱（W3.1）

### 5.1 三个"任务"概念的分工

| 概念 | 存活期 | 存储 | 关系 |
|---|---|---|---|
| `ScheduleTask`（daemon/scheduler） | 到点说一句话 | `~/.jarvis/schedule.json` | 闹钟，不是任务 |
| `TaskList`（collaboration） | **一次查询内**的并行子任务 | `~/.jarvis/tasks/<team>/` | 与脊柱用 `parent_task_id` 关联 |
| `TaskGoal`（脊柱） | **跨会话、跨天**的目标台账 | `~/.jarvis/goals/<id>.json` | 一个目标拆有序步骤，步骤可"等条件" |

两套存储互不写入。台账路径与计划文档的 `~/.jarvis/tasks/goals/` 不同是刻意的：
`~/.jarvis/tasks/<team>/` 已被协作 TaskList 用作团队目录，插一个 `goals` 子目录会在
团队恰好叫 "goals" 时串目录、双方互相读坏。

### 5.2 条件等待的三条硬约束

1. **判定不花钱**：`TaskWait.check()` 只做时间比较与本地 `stat`，绝不调 LLM、不起进程。
   `percept_event` 的命中由驱动器订阅回调写回 `spec["hit_at"]`——本模块从不"主动查总线"，
   查了就退化成轮询。
2. **一律带 `deadline_at`**：感知层逐源默认全关，事件可能永不到来。超时转
   `blocked_timeout` 并经 W1 闸门来问用户，绝不静默挂起（否则"替我盯着"变成"替我失踪"）。
3. **坏文件不崩**：任何一行读不出来就跳过该目标，不抛异常。

### 5.3 驱动器：一条线程 + 到期唤醒

```
Event.wait(距下一次该醒的秒数) → 复查活跃目标 → 就绪步骤交给 Subagent → 再算唤醒时刻
```

- **不轮询**：唤醒时刻由条件算出来（`time` 到点或 deadline、`file_exists` 按 60 秒
  廉价 stat 节拍、`percept_event` 由总线回调即时 `wake()`）。等待期间 LLM 调用次数为 0
  ——这条被单测直接钉住（`test_time_wait_not_due_zero_llm_calls`）。
- **一次只跑一步**：后台自主执行不该并发烧钱，也不该同时改工作区两处（`_busy` 闸门）。
- **推进复用 `run_subagent`**：独立 QueryLoop、不写主会话转录，因此**不抢桌面/手机的
  query 锁**，用户正在对话也不打断。权限模式刻意用 `default` 而不是子代理默认的 `yolo`：
  无人值守时不该默认放行任何需确认的操作；无 UI 时 ASK 落成 DENY，驱动器把它翻译成
  "需要授权"来问用户（`request_approval(goal_id, step_id, approve=…)` 是答复入口）。
- **失败退避落在磁盘上**：`TaskStep.next_run_at` 记最早可再执行的时刻。只记在内存里时，
  进程重启会丢掉它，未达上限的失败步骤被立刻重跑——退避形同虚设。
- **重试到上限就定局 `failed`**，不是 `blocked`：`blocked` 被算作"仍需推进"，用它做终态
  会让驱动器下一轮又跑一次，变成无退避的死循环重试。
- **崩溃安全**：进程死在半路时步骤停在 `running`，`resume()` 在锁内按 id 重找并复位成
  `pending` + 计一次失败（复位算尝试次数，避免重启后无限重试）。
- **播报只走 W1 闸门**：宿主注入的 notifier 内部调 `proactive.apply_notify_gate`
  （与简报、感知事件同一份实现），驱动器自己不 print、不 TTS。源名固定 `task`，
  必须显式登记进 `policy/budget.py` 的权重表——漏登记就落 `default` 被门槛误裁，
  整个脊柱"永远不吱声"（同
  [notify-budget-percept-relay-fix](../fixlogs/notify-budget-percept-relay-fix.md) 的坑）。
- **同一件事只问一次**：`TaskStep.asked` 标记 + `blocked_ask_days`（默认 3 天）到期才再问。
- **禁用态不起线程**：`tasks_enabled=false`、或 settings 里凑不出可用 provider（且没注入
  `spawn`）时 `start()` 返回 False；台账读侧不依赖驱动器，关着也能 `/tasks` 看。

### 5.4 目标从哪来：三个入口、一层语义（阶段 10 收尾切片）

脊柱后端早就交付了，但**没有任何入口能把目标写进去**——用户说“替我盯着这件事”，
模型只能回一句“好的”，然后什么都不发生。本切片补的就是这一段：

| 入口 | 给谁 | 落点 | 典型写法 |
|---|---|---|---|
| `/tasks add …` | 终端用户（不经模型也能测） | `commands/handlers/collab_commands.py` | `/tasks add 等构建产物出现后跑冒烟 --wait file:C:/dist/app.exe` |
| `TrackGoal` 工具 | 模型（一句自然语言就落台账） | `tools/track_goal.py` | `action=create, goal=…, wait={"kind":"time","at":"+2h"}` |
| `tasks.exec` RPC | 桌面「任务中心」 | `serve/rpc_tasks.py` | `{type:"tasks.exec", action:"create", goal:"…"}` |

三个入口都只调 :mod:`agent.core.tasks.spine_ops`，自己不做判定。理由不是“少写代码”：
“取消该不该清 wait”“advance 算不算条件成立”“终态目标能不能改活”这类取舍只要
在两处各写一遍，就会出现“终端能建、面板建出来两个样”的双口径。

必须记住的几条语义：

- **等待条件只挂第一步**。“先等、再动手”是唯一有物理意义的顺序；挂到后面的步骤上，
  用户看起来就是“没生效”。
- **步骤缺省补单步**。`goal` 里没有分号时把目标本身当唯一步骤——零步骤的目标会被
  驱动器 `current_step() is None` 直接跳过，台账看着像功能坏了。
- **`time` 类不补 deadline**（它自带确定时刻，再叠一层会出现“到点之前先超时”）；
  `file_exists` / `percept_event` **必须有兜底时限**（默认 `[tasks].wait_deadline_hours`），
  否则目标会永远挂着一个不会来的文件。
- **写完必 `wake_driver()`**。否则新目标要等到下一次自然唤醒（可能是一小时后）才被看到。
  唤醒失败**不算错**（台账单例可被脚本单独用），但 `advance`/`resume` 时若真没人推，
  返回文案必须补一句“当前没有驱动线程”——否则用户敲完就盯屏幕等一个不来的结果。
- **`advance` 是测试绕行口子，不是“条件成立”**：它清掉等待并把步骤改回 `pending`，
  同时在 `result` 里留下“用户以 advance 跳过等待条件”的痕迹，便于事后分得清是真做到还是被绕过。
- **定局目标只允许 `delete`**：`done`/`failed`/`cancelled` 之后再 `resume` 会让驱动器重跑
  已经做完的事，最坏结果是重复外发。
- **`find_goal` 支持前缀但歧义时不猜**：台账 id 是 12 位随机串，手敲不现实；多个目标共享
  前缀时直接报“没找到”——挑错一个去 `cancel`/`delete` 的代价比“没找到”高得多。
- **RPC 的两拍确认**：`actions.exec undo` / `undo_task` 未带 `confirm=true` 时只回影响面
  预览（`need_confirm` + `preview`），`tasks.exec delete` 则回 `need_confirm` + `goal` 明细
  （面板据此列得出“要删的是哪个”），都**绝不落手**——这跟终端 `/undo` 读 y/N 是同一条
  约束的两种实现，不是“桌面比终端宽松”。`cancel_hold` 之所以不做确认，是因为它撤的是
  **还没执行**的预约，做的是“不做”。

## 六、配置

```toml
[actions]                    # 副作用账本（默认开）
journal_enabled = true       # 总开关：false = 不记账也不延时，/undo 无从下手
undo_window_s = 30           # 不可逆动作延时窗口（秒）；0 = 不拦、直接执行
track_local_writes = true    # 本地破坏性写是否记一条可回滚条目
irreversible_tools = []      # 额外按不可逆处理的工具名（应急口子，改配置不改代码）
hold_blocks_equivalent = true  # 窗口未结案时，网络外发类中风险命令不再自动放行（改问人）

[tasks]                      # 任务脊柱（默认关）
enabled = false              # 驱动器总开关：false = 只读台账，不自动推进
blocked_ask_days = 3         # 阻塞超此天数主动问一次（走 W1 预算闸门）
step_max_attempts = 3        # 单步失败重试上限
retry_backoff_s = 60         # 重试退避间隔（秒）；本期固定间隔
wait_deadline_hours = 72     # 条件等待最长时限（超时转 blocked_timeout 来问）
```

两个默认值取向不同是有意的：**账本默认开**（它是"敢放手"的前提，关掉等于把已发生的
副作用记不住）；**任务脊柱默认关**（它会自主调 LLM 花钱并自己动手执行，必须用户显式
授权，同 W2 逐源默认关的口径）。

字段落点成套：`config/settings.py` 字段 + `config/settings_domains.py` 域表
（`actions` / `tasks` 两个扁平域 + `actions_irreversible_tools` 列表字段）+
两份 `settings.example.toml` + [configuration.md](../../config-docs/configuration.md)。

`hold_blocks_equivalent` 的取向与其它三键不同：它改的是**权限判定的松紧**而不是记账，
默认开（宁可多问一次，也不让"用户以为拦住了"变成假象）。

## 七、用户面

| 命令 | 行为 |
|---|---|
| `/undo` | 撤上一步已执行的副作用（先展示整轮回滚影响面，问过用户才落手） |
| `/undo <id 前缀>` | 撤销指定记录 |
| `/undo list` | 最近记录与各自可否撤销（**撤不动的照样列出来并带原因**） |
| `/undo cancel [id]` | 撤回还在延时窗口里、尚未执行的动作 |
| `/undo --task <id>` | 按目标批量补偿，逐项报"撤了 / 撤不动 + 原因" |
| `/tasks` | 两节：协作内共享任务（`TaskList`）+ 跨会话任务脊柱（目标、进度、卡在哪、等什么、最迟什么时候） |
| `/tasks add <目标>[;步骤2 …] [--wait <条件>] [--deadline <小时>]` | 新建目标。等待条件：`time:+90s`·`time:2026-10-22T09:00`·`file:<路径>`·`gone:<路径>`·`event:<source>/<kind>`；建完直接回显第二节 |
| `/tasks show <id>` | 逐步展开（含在等什么、上次失败原因、本目标产生的副作用 id） |
| `/tasks pause\|resume\|cancel <id>` | 暂停 / 恢复 / 取消（取消保留记录便于复盘） |
| `/tasks advance <id>` | 跳过等待条件立刻推进（**测试用**，不等 90 秒也能验完链路） |
| `/tasks delete <id>` | 从台账硬删（本期无软删归档） |
| `TrackGoal`（工具） | 模型侧入口，“替我盯着…”一句话就落台账；八个动作同上，`delete` 要用户确认 |
| `tasks.exec` / `actions.exec`（RPC） | 桌面侧入口（一条指令承载多个动词）；`undo`/`undo_task` 未带 `confirm=true` 只回影响面预览，`delete` 只回目标明细 |

本轮**不新建同义命令**：slash 命令表只有一份（`ui/slash_completer.py`），再加一个
"看目标"的入口会让模型与用户都先猜哪个是活的，故把 `/tasks` 扩成两节 + 子命令。
`/tasks` 仍**不进**桌面斜杠白名单（`slash_bridge.ALLOWED_COMMANDS`）：写入子命令与
`/undo` 一样需要宿主控件或二次确认，桌面走 `tasks.exec` / `actions.exec` 原生指令。

## 八、安全红线（不变）

- **DENY 永不放宽**；延时窗口只延后执行，不豁免任何一次权限判定与 W1 闸门。
- **窗口未结案期间不放过等价通路**：外发类中风险命令的自动放行被临时关掉（§4.3），
  收紧本身只会把 ALLOW 变成 ASK，从不把 DENY 变成 ALLOW。
- 后台步骤用 `PermissionMode.DEFAULT` 而非 `yolo`；无 UI 时的 ASK 落成 DENY 由驱动器
  如实转成"需要授权"来问，不绕过。
- 账本与台账只落 `~/.jarvis/`（用户目录），含收件人等敏感字段不外传。
- 脊柱不新建 shadow git 检查点，避免挤占 `/rewind` 的配额。

## 十、已知边界（本期未做）

- **绕道硬拦只收“自动放行”这条捷径**：预约未结案期间，网络外发类中风险命令改为问人
  （§4.3）。它不是一条黑名单：模型仍可请求别的通路，而 HIGH/CRITICAL 本来就要确认；
  真正确定的拦住只能靠“到点才执行”这个时间差。要关掉收紧用
  `hold_blocks_equivalent = false`（无 UI 环境 ASK→DENY 会误伤时的后手）。
- **`/undo --task` 靠任务归属接线，旧版断过**：编排器只从 `ctx.extra["task_id"]` 取归属，
  现在 `spawn.default_spawn` 与 `run_subagent(extra=...)` 已把 `task_id`/`session_name`/`effect_ids`
  接齐，驱动器跑完回填 `TaskStep.journal_ids`（两头都有单测钉住）。
  仍需注意：宿主自写的旧式两参 `spawn` 依旧拿不到归属（按签名判定后不强塞）。
- **绕道硬拦只覆盖"等价外发命令"这一类**：它只关掉预约期间的自动放行（改 ASK），
  不靠特征匹配同一收件人/域名（§十 早期记录的方案 B 未做）；模型写个脚本文件再跑
  仍属于同一条命令族，会因不含外发线索而漏判。实机要验两层，见走查清单 §2.8。
- **到点执行的结果不回灌对话**：`_fire_irreversible` 用 `messages=[]`、`ui=None` 的最小上下文跑，
  成功只播一行 `预约动作已执行：…`。对邮件是"照发且只报一句"，对只读类工具则是重复执行
  且产物无人接——所以不要把只读工具塞进 `irreversible_tools` 做演示。
- **目标拆解仍靠人给步骤**：三个入口都能建目标，但**没有“把一句远景自动拆成五步”**
  的能力：不写分号就是单步，步骤文本同时就是交给子代理的任务描述。要做自动规划得先有
  费用归集与步骤质控，那不在本层（见 §十“token/费用未归集”）。
- **桌面「任务中心」面板仍未做**：`tasks.exec` / `actions.exec` 已就位并有单测，但面板在
  jarvis-desktop 仓（本仓外），需那边接上才能看到可视化；在那之前桌面用户仍只能用终端。
- **token/费用未归集**：`SubagentResult` 不回报 usage，`TaskGoal.budget` 只是留位。
- **多机共享台账**：存储是本机文件，跨进程锁只保护同一台机器上的多个 jarvis 进程。
- **退避策略是固定间隔**，不做指数翻倍。
- 清理/整理类维护工具（BLUEPRINT §6.2/6.3）需要 W3 账本才安全，账本本轮就位后另开。
- 待批清单的自动重放（[16-W1判断层](16-W1判断层.md) §八留的口子）本轮只提供了
  `request_approval` 编程入口，尚未接命令面板。
- **`/undo` 不放行给桌面斜杠命令**：它要先展示影响面再读 y/N，属于交互式处理器，
  不进 `slash_bridge.ALLOWED_COMMANDS`（口径同 `/rewind`：桌面有原生控件的交互命令不
  透传）。桌面侧的撤销入口属下一切片（`actions.*` RPC）。

## 十一、与计划文档的偏离（实施时核实后的判断）

| 计划原文 | 实际做法 | 理由 |
|---|---|---|
| 复用 `Tool.is_destructive` 判定延时窗口 | 新增 `is_irreversible` / `describe_irreversible` | `is_destructive` 含"删除/覆盖"，`FileWrite` 也是 True 但可由检查点回滚；挂在它上面每次存文件都要干等 30 秒 |
| 新增 `/tasks` 命令展示脊柱 | `/tasks` 扩成两节 | slash 表只有一份，同义命令让人先猜哪个是活的 |
| 到点重放走完整管线（重建 ctx 过权限） | 直接按冻结 args 调 `tool.call` | 无 UI 时 ASK 会被 fail-closed 拒成 DENY，等于把用户刚批准的动作自己拦掉 |
| 台账落 `~/.jarvis/tasks/goals/` | 落 `~/.jarvis/goals/` | 避开与 `~/.jarvis/tasks/<team>/` 串目录 |
| `file_exists` 复用 `source_file.py` 的白名单扫描函数 | 直接 `Path.exists` | 等待只需要"这一个文件在不在"，拉整个扫描函数会把感知层的目录白名单当成脊柱的依赖 |
| `SendMessageTool` 也声明不可逆 | **不声明**（代码注释里写明理由） | 它是本机文件信箱（`~/.jarvis/teams/`），拖进 30 秒窗口只会让团队协议往返成倍变慢，且没有"出了本机收不回"的属性 |
| 重启后由 `resume_pending()` 补投到期窗口 | 一律作废并播报 | 见 §4.3：重启后没人能喊停 |
