## 一、解决什么问题

W1 判断层（见 [16-W1判断层](16-W1判断层.md)）建好了"该不该打扰你"的闸门，
但闸门上游几乎没货可裁：主动播报的内容全部来自**时钟**（`Scheduler` 到点 +
`ProactiveEngine` 固定节律轮询）。jarvis 不知道你在哪个窗口干什么、构建有没有
失败、白名单目录有没有堆积、重要来信到了没有——于是"主动性"卡在 ⭐⭐⭐：
提醒闭环已成，但产生不了价值。

W2 感知层补的就是这条上游链路：

```
N 个感知源 ──PerceptEvent──▶ 事件总线（去重 / 节流 / 故障隔离 / 留痕）
                                  │
                                  ▼
                     serve ProactiveHub 适配器拼文本
                                  │
                                  ▼
                     W1 NotifyBudget 闸门 ──▶ 恰好的提醒
```

## 二、与 W1 的分工（两道闸门的边界）

这是本层最容易写歪的地方，故明写口径：

| 层 | 裁什么 | 依据 | 不做什么 |
|---|---|---|---|
| 总线（W2） | **事件层噪声**：同一件事重复上报、同源投得太密、明显无价值的噪声、坏源反复烧 CPU | 去重键窗口、每源最小投递间隔、重要度地板分、连续失败自动停用 | 不计数"今天打扰了几次"，不知道静默时段，不判断"现在能不能播" |
| 预算（W1） | **打扰层裁决**：该不该现在播 | 日额度 / 静默时段 / 聚合窗口 / 重要度评分（权重×紧迫×相关性×历史接受率）/ away | 不认识事件源的内部结构 |

两者串联互不知情：总线把 `salience_hint` 当**先验**（源只声明"这类事通常多重要"），
真正的评分始终在 `NotifyBudget.salience()`。

### 3.1 PerceptEvent

```python
PerceptEvent(source, kind, payload, ts, salience_hint, dedup_key, merged)
```

- `payload` **只放事实不放文案**，约定含 `summary`（一句中文事实）；总线与
  W1 用模板拼文本，**单条事件不调 LLM**（成本控制硬约束）。
- `dedup_key` 留空时自动取 `source:kind:payload指纹`（键排序后 sha256 前 12 位），
  所以"同一个构建失败被上报两次"天然命中去重，源不必自己记账。
- `payload` 字符串值投递前一律截断到 240 字符：窗口标题、构建日志尾行都可能
  很长，总线要常驻内存并落盘，必须有硬上限。

### 3.2 三道闸的判定顺序

`publish()` 顺序固定，任一环节命中即**不投递**且写清原因（可直接进日志与面板）：

1. **地板分** `min_salience`（默认 0=不裁）；
2. **去重窗口** `dedup_window_s`（默认 300s）：命中则合并计数 +1，不刷新首发时间戳；
3. **同源节流** `throttle_s[source]`（如 vcs 60s）：按源计数，与"是否同一件事"无关。

通过后才记账：写入环形历史 `history`、更新每源计数、追加 JSONL 留痕、分发订阅方。

### 3.3 故障隔离（两层）

- **订阅方隔离**：分发逐个 `try`，坏订阅方只累加 `subscriber_errors` 计数；
- **采集源隔离**：`collect()` 抛错不传染其他源，`consecutive_errors` 达到
  `auto_disable_after_errors`（默认 3）即**自动停用该源**并记 `last_error`，
  防止 pywin32 句柄失效 / IMAP 认证失败这类错误每秒重试烧满 CPU。成功一次即
  清零连败计数（偶发抖动不累积）。面板可见 `last_error`，用户可手动重开。
- 落盘失败（磁盘只读等）只累加 `log_errors`，绝不向上抛——**留痕坏了不能拖垮感知**。

### 3.4 单轮询线程 + 可注入时基

刻意不给每源起一个线程：

- 一个线程服务全部轮询型源，节拍取"启用源里最快到点的剩余时间"；
- **无任何启用源时根本不起线程**（验收口径"无源开启时 CPU 增量为 0"的实现依据）；
- `tick(now)` 与 `publish(now)` 共用 monotonic 时基且可注入，因此去重/节流/到点
  判定全部可在测试里确定性验证，不需要 `sleep` 真实时间。`tick()` 会把算到点用的
  同一个 monotonic 值透传给采集出的事件（`publish(ev, now=mono)`），否则“注入时间
  驱动测试”时投递窗口仍在走真实时钟，测不出确定性。

推送型源（IMAP IDLE 服务器主动推）不必实现 `collect`，直接 `publish()` 即可——
总线对 pull / push 两个入水口一视同仁。

## 四、隐私与逐源默认关（已拍板的口径）

计划文档第 8 节决策 2 已定：**逐源默认关 + 首次启动询问**。代码侧的落点：

- `register_source(..., enabled=False)` 是默认值，未获同意前 `collect()` **一次都不会被调用**
  （有专门单测保证"禁用源零采集"）；
- 总开关 `percept_enabled=False` 时 `source_enabled_map()` 返回全 False，
  面板不会出现"总开关关了但某个源显示正在观察"的分裂状态；
- `export()` 一次性吐出「当前配置 + 逐源开关与状态 + 最近事件完整 payload」，
  用户可以自查到底采了什么（采集范围可见即可导出）；
- `percept_log_events=False` 时 `default_log_path()` 返回 None，**完全不碰磁盘**；
  留痕文件 `~/.jarvis/percept/events.jsonl` 按 `history_max * 10` 行裁剪，
  常驻运行不会无限增长。

`window`（前台窗口）是唯一有明显隐私属性的源：已落地为**独立开关 + 标题正则脱敏
+ 长度截断 + 应用排除名单**，且排除命中次数作为面板上的“隐私生效中”证据。

## 六、已落地的事件源

### 6.1 前台窗口 `source_window.py`

- **采集**：Windows 下 `ctypes` 直调 `GetForegroundWindow` + `GetWindowThreadProcessId`
  → `psutil` 反查进程名 → `GetWindowTextW` 取标题；非 Windows 退回 `pygetwindow`
  （只能拿标题）。**零新增依赖**，但有一个必须处理好的坑：ctypes 默认 restype 是
  `c_int`，64 位下 HWND 会被**静默截断**，因此 `_win_api()` 一次性声明 restype/argtypes。
- **事件**：`focus_changed`（仅当**进程名**变化时发；同一应用内换标签页不发，
  因为不值得打扰），去重键 `focus:<应用名>`；`focus_linger`（同一应用连续停留
  超 `window_linger_minutes` 才发，且只催一次）。
- **脱敏**（隐私口径的具体落地）：标题先正则剥掉 `?token=`/`密码：xxx` 类片段，
  再截断到 40 字；`window_title_full_enabled` 显式开启才不截断（仍剥凭据）；
  `window_title_max_chars = 0` 等于“只报应用名”；内置敏感应用名单（密码/凭据管理类）
  命中则**零事件**，仅计数留痕（面板可见 `excluded_hits`，能证明“隐私生效中”）。
- **首采只建基线**：否则开源瞬间会播一条“切到 Chrome”而用户根本没切换，还白吃一条日额度。

### 6.2 文件守望 `source_file.py`

- **为何自建快照**：`core/memory/file_state.py` 是单文件 mtime 冲突缓存（挂
  `ToolContext.extra`、随会话消失），**没有目录扫描能力**，不可复用（PLAN 第 3.1 节已修正）。
- **只订阅白名单目录**；递归时跳过 `.git`/`node_modules`/`__pycache__`/`.venv`/`dist`/`build`
  与隐藏项，单目录快照有条数上限（命中只置 `truncated`，不报错也不炸内存）。
- **只对“新增”发声**：删除与修改是用户自己的动作，提醒它们是噪声。量小发
  `file_added`（点文件名），量大（达 `file_grow_threshold`）聚合为一条 `dir_grew`。
- **基线持久化**到 `~/.jarvis/percept/file_state.json`（临时文件 + `os.replace` 原子写）：
  首扫只建基线不报现存文件；而 jarvis 关闭期间攒下的新文件，重启后会被当作
  一次真实堆积报出来——这才是“目录堆积提醒”的价值所在。状态文件损坏则当作
  无基线处理，不抛异常。
- payload 只含**相对路径的文件名与计数**，不含内容、不含绝对路径；`summary` 用目录名。

### 6.3 “开了但没配齐”不算故障

`file_enabled = true` 但 `file_watch_dirs = []`（或邮箱未配置）时，源的 `collect()`
**返回空列表而不抛异常**——这类是用户配置未完成，不是运行时故障；若抛错，总线的
连败自动停用会把源标成“坏了”，面板就会显示一个误导人的错误。

### 6.4 仓库 `source_vcs.py`

- **一期只做本地 git（老实写“未做”）**：计划文档 §3.1 原列“构建/CI 结果尾行”，
  它要么依赖外部 `gh` CLI 与 GitHub 凭据（违背决策 1“只本机采集、不引入外部账号
  授权”），要么由 jarvis 自己跑构建（那是主动执行，属 W3 兑现层）。因此本期只采
  本机 git 能得到的事实，不假装已接 CI。
- **只读零副作用**：只有 `git status --porcelain=v1 -b` 与 `git stash list` 两条命令
  （不 fetch、不 pull、不动工作区），超时 10s，且带 `GIT_OPTIONAL_LOCKS=0` 避免
  只读命令去抢 `index.lock`。仓库是**登记制**（`vcs_repos`），未登记的一个都不问。
- **四种信号，只在“刚跨过提醒线”的那一档发一次**：`repo_dirty_grew`
  （未提交项达 `dirty_threshold`）、`repo_unpushed`（ahead 从 0 变正）、
  `repo_behind`（behind 从 0 变正）、`repo_stash_piled`（stash 达阈值）。脏文件从
  8 项变 12 项不会再催一遍——“一直碎嘴”是这个源最大的风险。
- **降级不传染**：目录不存在 / 不是 git 仓库（退出码非 0）/ 单条命令超时都只记到
  `unavailable[仓库]` 并跳过该仓库，一个坏路径不拖垮其他仓库；`git` 未安装是环境级
  不可用，置 `_fatal` 后短路返回空列表（而非抛异常），免把环境问题报成“源坏了”、
  也免每 120s 空转。事件只带目录名，不带仓库内容。

### 6.5 邮件 `source_mail.py`（决策 3）

三条硬约束写进实现，也各有单测锁死：

1. **只读信封头，永不拉正文**：`SELECT readonly=True`（不把邮件标成已读）+
   `FETCH BODY.PEEK[HEADER.FIELDS (FROM SUBJECT DATE MESSAGE-ID)]`——PEEK 不置
   `\Seen`，字段列表只取四个头，正文一个字节都不下（测试直接断言真实 FETCH 规格，
   防止以后被误改成 `RFC822`）。
2. **IDLE 长连接，断线自动降级轮询**：服务器广告 IDLE 就挂在 IDLE 上等推送，
   单次最多等 `IDLE_TICK_S=25*60` 后主动 DONE-再-IDLE（服务商常 30 分钟掉长连接，
   周期性重挂比死等更稳）；**任何异常一律 `mode="poll"`**，按 `poll_interval_s`（默认
   300s）重连拉一次，不崩不刷错误；`mode` 进 `state()` 供面板显示“长连接还在不在”。
3. **已报过的信要落盘**：readonly 下未读邮件会一直是未读，不去重则每轮重播同一封。
   已报键集合存 `~/.jarvis/percept/mail_seen.json`（环形上限 500，原子写），
   去重键用 `Message-ID`（缺失时退化为 发件人+主题+日期）。

另外四点：

- **首轮只记账不播报**（`_harvest(announce=not first)`）：否则一开源就把收件箱
  陈年未读全播一遍，用户第一感受就是“这玩意一装就吵”。
- **发件人白名单是源侧的第一道过滤**（`percept_mail_watch_senders`，经 factory 注入）：非空时只报
  命中的人（先验分抬到 0.75），被挡掉的封数记 `filtered`；比让 W1 猜“谁重要”更可靠。
- **它是 push 型源，但依旧走总线契约**：内部一个线程做 IDLE/轮询，`collect()`
  只排空队列投递（节拍 30s）；线程**懒启动**（第一次被总线采集才起，而总线只采
  已启用源），所以源关着时既不占总线轮询也没有任何连接；未配置邮箱时
  `configured()` 为 False，`collect()` 直接返回空、线程不起（§6.3 同一口径）。
- 凭据只在内存里持有，绝不写进事件 payload 与留痕文件（有单测断言事件 JSON 不含授权码）。

> 上、进程内、随会话结束消失），没有目录扫描能力。`source_file.py` 需自带目录
> 快照实现（白名单目录 walk + mtime/size 差分），已同步修正计划文档。

- `tests/core/test_percept_sources_vcs_mail.py`（30 例）覆盖：`git status` 五种输出解析
