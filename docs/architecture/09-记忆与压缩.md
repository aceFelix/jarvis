## 二、分层上下文压缩（LayeredContext）

[layered_context.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py) 是 QueryLoop 当前的上下文管理器，
替代了原"动态水位原地篡改历史"方案：

```
┌──────────────┐   ┌─────────────────────────────┐
│   冻结区      │   │        活跃窗口（滑动）        │
│ 压缩后的摘要   │   │  最近 N 条原始消息（持续追加）  │
│ 一旦锁定永不改 │   │  超阈值 → 合并进冻结区 → 重置  │
└──────────────┘   └─────────────────────────────┘
        └─────────── 组合成完整消息发给 LLM ────────┘
```

### 冻结触发

[freeze_if_needed()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L103-L161)：

```python
async def freeze_if_needed(provider, model, *, window_limit=8000, keep_recent=4):
    if self.active_tokens() < window_limit:
        return False   # 未超阈值，不冻结
    result = await compact_messages(provider, model, all_msgs, keep_recent=keep_recent)
    # 冻结区 = 摘要部分（永不修改），活跃窗口 = 保留的最近消息
    self._frozen = result.new_messages[:split_at]
    self._active = result.new_messages[split_at:]
```

### 反应式压缩

[compact_reactive()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L163-L199)：
API 报 `context too long` 时**无条件**压缩（不检查阈值），冻结前缀不变。

**为什么替换水位方案**：原方案"原地篡改历史消息"使每次请求的前缀都变化，
破坏 LLM 服务端 Prompt 前缀缓存。分层上下文让摘要固定，长对话保持缓存命中（省 token、降延迟）。

### 窗口内轻量优化（仅活跃窗口）

- `collapse_old_tool_results()` — 旧工具结果折叠（保留最近 4 个）
- `evict_old_images()` — 旧图片淘汰（保留最新一张）

冻结区不可变，这些操作只作用于活跃窗口。

## 三、compact_messages() 压缩流程

[compactor.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L211-L339)：

```
messages = [old...] + [recent 6 条]

1. 分割：to_summarize = messages[:-6], to_keep = messages[-6:]
2. 剥离图片：to_summarize 里的图片替换为 [图片] 文本
3. 格式化历史：转成 "用户: ... / 助手: ..." 纯文本
4. 调 LLM 生成摘要（9 段结构化）
5. 返回 [摘要消息] + to_keep
```

### 9 段摘要提示词

借鉴 Claude Code 的代码感知摘要：

```
### 1. 用户请求与意图
### 2. 关键技术决策
### 3. 文件与代码变更（文件路径 + 代码片段 + 变更原因）
### 4. 错误与修复
### 5. 用户反馈
### 6. 用户消息列表
### 7. 待办事项
### 8. 当前工作状态
### 9. 下一步行动
```

**为什么 9 段**：保留足够的代码细节，让 Agent 压缩后能无缝继续工作。丢失关键细节会导致它犯错。

## 四、Token 估算

[estimate_tokens()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L99-L124)：

| 内容类型 | 估算方式 |
|---|---|
| TextContent | `len(text) / 4` |
| ToolUseContent | `(len(name) + len(input_json)) / 4` |
| ToolResultContent | `len(content) / 4 + images * 1000` |
| ImageContent | 固定 1000 token |

**为什么粗略估算**：精确 tokenizer 依赖模型，粗略够用，不追求精确。

## 五、图片驱逐

[_evict_old_images()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/query_loop.py#L489-L520)：

- 只保留**最新一张**图片的 base64 数据
- 其余替换为 `[截图已处理: {summary}]` 文本占位（~20 tokens）

**为什么**：截图每张约 1500 tokens（base64 JPEG），LLM 看完后数据无再使用价值。

## 七、压缩后文件回灌

[restore_recent_files()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L367-L407)：

压缩后重新注入最近操作过的文件，让 LLM 不丢失关键文件上下文。

```python
def restore_recent_files(ctx) -> int:
    files = ctx.extra.get("_recent_files", [])
    recent = list(reversed(files[-5:]))  # 最近 5 个
    for file_path, _ts, access_type in recent:
        content = read_file(file_path)[:5000]  # 每个最多 5000 字符
        ctx.messages.append(Message(
            role="user",
            content=[TextContent(text=f"[压缩后文件回灌] `{file_path}`\n```\n{content}\n```")]
        ))
```

### 文件访问追踪

[track_file_access()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L350-L364)：

- 工具执行时记录文件路径到 `ctx.extra["_recent_files"]`
- 按访问时间排序，去重保留最近 20 个
- 压缩后回灌最近 5 个

**为什么回灌**：压缩摘要可能丢失文件细节，回灌让模型重新看到最近操作的文件内容。

## 十二、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 压缩策略 | LayeredContext 冻结前缀 | 前缀稳定 → LLM 缓存命中，省 token |
| 摘要格式 | 9 段结构化 | 保留代码细节 |
| Token 估算 | 粗略 | 够用，不追求精确 |
| 图片处理 | 淘汰最新一张外 | 省 token，旧图无价值 |
| 文件回灌 | 最近 5 个 | 不丢失关键文件上下文 |
| 会话记忆 | 自动追加 | 跨会话记忆延续 |
| 反应式压缩 | 兜底 | 防止估算不准 |
