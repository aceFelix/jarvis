## 二、分层上下文压缩（LayeredContext）

[layered_context.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py) 是 QueryLoop 当前的上下文管理器，
替代了原"动态水位原地篡改历史"方案：

```
┌──────────────┐   ┌─────────────────────────────┐
│   冻结区      │   │        活跃窗口（滑动）        │
│ 压缩后的摘要   │   │  最近 N 条原始消息（持续追加）  │
│ 一旦锁定永不改 │   │  超阈值 → 合并进冻结区 → 重置  │
└──────────────┘   └─────────────────────────────┘
        └─────────── 组合成完整消息发给 LLM ────────┘
```

### 冻结触发

[freeze_if_needed()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L103-L161)：

```python
async def freeze_if_needed(provider, model, *, window_limit=8000, keep_recent=4):
    if self.active_tokens() < window_limit:
        return False   # 未超阈值，不冻结
    result = await compact_messages(provider, model, all_msgs, keep_recent=keep_recent)
    # 冻结区 = 摘要部分（永不修改），活跃窗口 = 保留的最近消息
    self._frozen = result.new_messages[:split_at]
    self._active = result.new_messages[split_at:]
```

### 反应式压缩

[compact_reactive()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L163-L199)：
API 报 `context too long` 时**无条件**压缩（不检查阈值），冻结前缀不变。

**为什么替换水位方案**：原方案"原地篡改历史消息"使每次请求的前缀都变化，
破坏 LLM 服务端 Prompt 前缀缓存。分层上下文让摘要固定，长对话保持缓存命中（省 token、降延迟）。

### 窗口内轻量优化（仅活跃窗口）

- `collapse_old_tool_results()` — 旧工具结果折叠（保留最近 4 个）
- `evict_old_images()` — 旧图片淘汰（保留最新一张）

冻结区不可变，这些操作只作用于活跃窗口。

## 三、compact_messages() 压缩流程

[compactor.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L211-L339)：

```
messages = [old...] + [recent 6 条]

1. 分割：to_summarize = messages[:-6], to_keep = messages[-6:]
2. 剥离图片：to_summarize 里的图片替换为 [图片] 文本
3. 格式化历史：转成 "用户: ... / 助手: ..." 纯文本
4. 调 LLM 生成摘要（9 段结构化）
5. 返回 [摘要消息] + to_keep
```

### 9 段摘要提示词

借鉴 Claude Code 的代码感知摘要：

```
### 1. 用户请求与意图
### 2. 关键技术决策
### 3. 文件与代码变更（文件路径 + 代码片段 + 变更原因）
### 4. 错误与修复
### 5. 用户反馈
### 6. 用户消息列表
### 7. 待办事项
### 8. 当前工作状态
### 9. 下一步行动
```

**为什么 9 段**：保留足够的代码细节，让 Agent 压缩后能无缝继续工作。丢失关键细节会导致它犯错。

COMPACT_MAX_OUTPUT_TOKENS = 2048  # 摘要输出上限

## 四、Token 估算

[estimate_tokens()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L99-L124)：

| 内容类型 | 估算方式 |
|---|---|
| TextContent | `len(text) / 4` |
| ToolUseContent | `(len(name) + len(input_json)) / 4` |
| ToolResultContent | `len(content) / 4 + images * 1000` |
| ImageContent | 固定 1000 token |

**为什么粗略估算**：精确 tokenizer 依赖模型，粗略够用，不追求精确。

## 七、压缩后文件回灌

[restore_recent_files()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L367-L407)：

压缩后重新注入最近操作过的文件，让 LLM 不丢失关键文件上下文。

```python
def restore_recent_files(ctx) -> int:
    files = ctx.extra.get("_recent_files", [])
    recent = list(reversed(files[-5:]))  # 最近 5 个
    for file_path, _ts, access_type in recent:
        content = read_file(file_path)[:5000]  # 每个最多 5000 字符
        ctx.messages.append(Message(
            role="user",
            content=[TextContent(text=f"[压缩后文件回灌] `{file_path}`\n```\n{content}\n```")]
        ))
```

### 文件访问追踪

[track_file_access()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L350-L364)：

- 工具执行时记录文件路径到 `ctx.extra["_recent_files"]`
- 按访问时间排序，去重保留最近 20 个
- 压缩后回灌最近 5 个

**为什么回灌**：压缩摘要可能丢失文件细节，回灌让模型重新看到最近操作的文件内容。

## 十二、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 压缩策略 | LayeredContext 冻结前缀 | 前缀稳定 → LLM 缓存命中，省 token |
| 摘要格式 | 9 段结构化 | 保留代码细节 |
| Token 估算 | 粗略 | 够用，不追求精确 |
| 图片处理 | 淘汰最新一张外 | 省 token，旧图无价值 |
| 文件回灌 | 最近 5 个 | 不丢失关键文件上下文 |
| 会话记忆 | 自动追加 | 跨会话记忆延续 |
| 反应式压缩 | 兜底 | 防止估算不准 |

## 十三、缓存命中统计与 /cost 命令

### 三段 Token 统计

`/cost` 命令展示三段 token 统计（P 系列修复）：

```
┌─────────────────────────────────────────────────────┐
│ Token 统计                                          │
├─────────────────────────────────────────────────────┤
│ System Prompt:     1,500 tokens   ← 单独统计        │
│ 对话历史:         12,000 tokens                     │
│ 总输入:           13,500 tokens                     │
│                                                     │
│ 缓存命中:          8,200 tokens (60.7%)              │
│ 缓存创建:          5,300 tokens                     │
└─────────────────────────────────────────────────────┘
```

**为什么单独统计 system prompt token**：之前 system prompt 的 token 没被计入总输入，
导致缓存命中率计算偏差。现在用 `estimate_text_tokens()` 单独计算 system prompt token，
让统计更准确。

### 缓存命中率计算

[parse_cache_usage()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/llm/base.py) 处理不同 API 的缓存语义差异：

```python
# OpenAI 兼容 API：cache_read_input_tokens 不包含在 input_tokens 里
# 命中率 = cache_read / (input + cache_read + cache_creation)

# Anthropic 兼容 API：cache_read_input_tokens 包含在 input_tokens 里
# 命中率 = cache_read / (input + cache_creation)
# 需要通过 input_includes_cache=True 标志区分
```

**为什么需要 `input_includes_cache` 参数**：DeepSeek-v4-flash 走 Anthropic 兼容 API 时，
返回的 `input_tokens` 已经包含了 `cache_read_input_tokens`。如果按 OpenAI 语义计算，
会把缓存命中 token 重复计入分母，导致命中率显示 0%。

### /compact 命令异步修复

`/compact` 命令之前的 bug：`RuntimeError: asyncio.run() cannot be called from a running event loop`

**原因**：`handle_compact` 和 `_compact` 是同步函数，内部用 `asyncio.run()` 调用异步压缩逻辑。
但 JARVIS 主循环已经在 asyncio 事件循环里，嵌套调用 `asyncio.run()` 会报错。

**修复**：把 `handle_compact` 和 `_compact` 改为 async 函数，用 `await` 替代 `asyncio.run()`。

### 缓存友好设计清单

| 设计 | 作用 |
|------|------|
| LayeredContext 冻结前缀 | 压缩后摘要固定，前缀稳定 |
| 反应式压缩不变前缀 | compact_reactive 只压缩活跃窗口 |
| Skill 按需加载（摘要注入） | system prompt 从 64k → 1.5k token |
| 工具按 name 排序 | built-in 作为连续前缀，cache breakpoint 稳定 |
| 图片淘汰 | 旧图替换为文本占位，不破坏前缀 |
| 工具结果折叠 | 旧结果替换为文本占位，不破坏前缀 |
| 文件回灌 | 作为新 user 消息追加，不修改历史 |
| 画像注入进程内缓存 | 同会话画像块逐字节稳定，不破坏前缀 |

## 十四、画像记忆（Profile Memory，长期记忆 Phase 1a）

### 设计动机

短期上下文（LayeredContext）解决"当前对话记得住"，画像记忆解决**跨会话的"懂你"**——
Jarvis 记住用户的偏好、习惯、背景，越用越个性化。这是 VISION 六维度中"记忆"维度的第一层
（后续：1b 情景记忆向量化检索、1c 关系图谱）。

### 数据流

```
会话中（零成本）
  └─ 画像块（限额 300 token）注入 system prompt（进程启动时渲染一次并缓存）
  └─ LLM 据此个性化行为（"先生，已经很晚了……"）

会话结束（异步后台线程，10 分钟节流）
  └─ _auto_save() → maybe_refine_async()
  └─ 截取对话（最近 40 条、过滤命令/工具消息）
  └─ LLM 提炼 JSON：{new: [...], updates: [{replace_id, ...}]}
  └─ 冲突裁决：新盖旧；幻觉 replace_id 当新条目处理
  └─ 写入 ~/.jarvis/memory/profile.json（原子写 + 锁）

每日 03:30（ProactiveEngine 静默维护）
  └─ decay()：30 天半衰期，confidence < 0.15 清除（manual 条目永不衰减）
  └─ prune_over_limit(200)：超限淘汰低置信条目
```

### 关键设计决策

| 决策 | 理由 |
|---|---|
| 提炼异步 + 节流（10 分钟） | 绝不在对话路径上跑 LLM（吸取 skill 64k token 教训） |
| 注入进程内缓存 | 同会话 system prompt 逐字节稳定，不破坏 LLM 前缀缓存 |
| 独立提炼模型（`[memory.refine]`） | 用便宜模型（如 deepseek-v4-flash）跑后台任务，省成本；api_key 留空时按“环境变量 → 自定义模型 → 主 LLM”解析，避免拿错别厂商 key（见 fixlogs/profile-refine-auth-fix.md） |
| 宁缺毋滥 prompt | 一次性闲聊不记，只提取稳定事实 |
| 半衰期衰减 + manual 豁免 | 过时记忆自动淡忘；用户亲写的最高信任 |
| `/memory` 用户可见可编辑 | 信任原则：管家记得你什么，你必须看得见 |

### 知识图谱画像桥（P2 双向同步）

`agent/core/extensions/profile_bridge.py` 打通 jarvis 与 aceFelix 知识图谱：

```
[图谱] ──MCP get_profile──▶ 启动预加载 ──▶ system prompt 画像段（与本地画像两段合并）
    ▲                                            冲突规则：图谱为唯一事实源，以图谱为准
    └────MCP ingest_text（/memory sync 预览确认后）──── 本地画像条目汇总文本```
- 图谱 → jarvis：`preload_kg_profile` 在 MCP 连接后、`build_system_prompt` 前拉取并缓存，
  渲染成 `# 关于用户（知识图谱画像）` 段（`token_limit` 限额裁剪）
- jarvis → 图谱：回写复用图谱抽取管线（查重/类型白名单/防噪闸），而非逐条 `add_entity`
- 开关 `[profile_bridge] enabled`（默认关），`server` 指定 mcp.json 中的 server 名
