## 二、分层上下文压缩（LayeredContext）

[layered_context.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py) 是 QueryLoop 当前的上下文管理器，
替代了原"动态水位原地篡改历史"方案：

```
┌──────────────┐   ┌─────────────────────────────┐
│   冻结区      │   │        活跃窗口（滑动）        │
│ 压缩后的摘要   │   │  最近 N 条原始消息（持续追加）  │
│ 一旦锁定永不改 │   │  超阈值 → 合并进冻结区 → 重置  │
└──────────────┘   └─────────────────────────────┘
        └─────────── 组合成完整消息发给 LLM ────────┘
```

### 冻结触发

[freeze_if_needed()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L103-L161)：

```python
async def freeze_if_needed(provider, model, *, window_limit=8000, keep_recent=4):
    if self.active_tokens() < window_limit:
        return False   # 未超阈值，不冻结
    result = await compact_messages(provider, model, all_msgs, keep_recent=keep_recent)
    # 冻结区 = 摘要部分（永不修改），活跃窗口 = 保留的最近消息
    self._frozen = result.new_messages[:split_at]
    self._active = result.new_messages[split_at:]
```

### 反应式压缩

[compact_reactive()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/layered_context.py#L163-L199)：
API 报 `context too long` 时**无条件**压缩（不检查阈值），冻结前缀不变。

**为什么替换水位方案**：原方案"原地篡改历史消息"使每次请求的前缀都变化，
破坏 LLM 服务端 Prompt 前缀缓存。分层上下文让摘要固定，长对话保持缓存命中（省 token、降延迟）。

### 窗口内轻量优化（仅活跃窗口）

- `collapse_old_tool_results()` — 旧工具结果折叠（保留最近 4 个）
- `evict_old_images()` — 旧图片淘汰（保留最新一张）

冻结区不可变，这些操作只作用于活跃窗口。

## 三、compact_messages() 压缩流程

[compactor.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L211-L339)：

```
messages = [old...] + [recent 6 条]

1. 分割：to_summarize = messages[:-6], to_keep = messages[-6:]
2. 剥离图片：to_summarize 里的图片替换为 [图片] 文本
3. 格式化历史：转成 "用户: ... / 助手: ..." 纯文本
4. 调 LLM 生成摘要（9 段结构化）
5. 返回 [摘要消息] + to_keep
```

### 9 段摘要提示词

面向代码场景的感知式摘要：

```
### 1. 用户请求与意图
### 2. 关键技术决策
### 3. 文件与代码变更（文件路径 + 代码片段 + 变更原因）
### 4. 错误与修复
### 5. 用户反馈
### 6. 用户消息列表
### 7. 待办事项
### 8. 当前工作状态
### 9. 下一步行动
```

**为什么 9 段**：保留足够的代码细节，让 Agent 压缩后能无缝继续工作。丢失关键细节会导致它犯错。

### 摘要参数

COMPACT_MAX_OUTPUT_TOKENS = 2048  # 摘要输出上限
temperature = 0.0                  # 确定性输出
tools = []                         # 摘要模式不给工具
```

## 七、压缩后文件回灌

[restore_recent_files()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L367-L407)：

压缩后重新注入最近操作过的文件，让 LLM 不丢失关键文件上下文。

```python
def restore_recent_files(ctx) -> int:
    files = ctx.extra.get("_recent_files", [])
    recent = list(reversed(files[-5:]))  # 最近 5 个
    for file_path, _ts, access_type in recent:
        content = read_file(file_path)[:5000]  # 每个最多 5000 字符
        ctx.messages.append(Message(
            role="user",
            content=[TextContent(text=f"[压缩后文件回灌] `{file_path}`\n```\n{content}\n```")]
        ))
```

### 文件访问追踪

[track_file_access()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/memory/compactor.py#L350-L364)：

## 九、长期记忆 MEMORY.md

### 用户级

`~/.jarvis/MEMORY.md` — 跨项目持久记忆

### 项目级

`<workdir>/.jarvis/MEMORY.md` — 项目特定记忆

启动时 `long_term_memory=True` 自动加载，注入 system prompt。

### 写入与编辑（2026-11）

长期记忆有两种改写方，共用 `agent/core/memory/store.py` 的同一组函数：

| 入口 | 函数 / 工具 | 能力 |
|---|---|---|
| 模型「记住…」 | `MemoryUpdate`（args `{content, scope}`）→ `append_memory_entry()` | **只追加**：整条子串去重、单条 ≤2000 字符、追加行带日期；不允许覆盖/清空 |
| 桌面设置面板 | `memory.save` RPC → `save_memory_scope()` | **整体覆盖**：≤100 000 字符、临时文件 + `os.replace` 原子写、覆盖前留一份 `MEMORY.md.bak` |
| 桌面设置面板（读） | `memory.get` RPC → `read_memory_scope()` | 返回 `{scope, path, content, exists, chars, updated_at}`，无项目时只返回 user |

保存后的生效链路（桌面「设置 → 长期记忆」气泡编辑器）：

1. `rpc_memory.MemoryRpcMixin._rpc_memory_save` 落盘；
2. `WorkbenchAPI.reload_memory(scope)` 入引擎指令队列（`{"cmd": "reload_memory"}`）；
3. 引擎线程 `ChatEngine._reload_memory` → `_rebuild_system_prompt()` 重拼
   system prompt（含 workdir / 思考开关 / 当前模型）并热替换进 `QueryLoop`；
4. 推 `memory_changed` 事件（payload `{scope}`），桌面重拉 `memory.get` 刷新字数与预览。

选择「整体覆盖只给用户、模型只能追加」的原因：模型一次误写就能抹掉历史记忆，
且它没有“这段该不该留”的判断力；用户要清空/重写时，桌面面板的确认与 `.bak`
才是合适的位置。

## 十二、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 压缩策略 | LayeredContext 冻结前缀 | 前缀稳定 → LLM 缓存命中，省 token |
| 摘要格式 | 9 段结构化 | 保留代码细节 |
| Token 估算 | 粗略 | 够用，不追求精确 |
| 图片处理 | 淘汰最新一张外 | 省 token，旧图无价值 |
| 文件回灌 | 最近 5 个 | 不丢失关键文件上下文 |
| 会话记忆 | 自动追加 | 跨会话记忆延续 |
| 反应式压缩 | 兜底 | 防止估算不准 |

## 十三、缓存命中统计与 /cost 命令

### 三段 Token 统计

`/cost` 命令展示三段 token 统计（P 系列修复）：

```
┌─────────────────────────────────────────────────────┐
│ Token 统计                                          │
├─────────────────────────────────────────────────────┤
│ System Prompt:     1,500 tokens   ← 单独统计        │
│ 对话历史:         12,000 tokens                     │
│ 总输入:           13,500 tokens                     │
│                                                     │
│ 缓存命中:          8,200 tokens (60.7%)              │
│ 缓存创建:          5,300 tokens                     │
└─────────────────────────────────────────────────────┘
```

**为什么单独统计 system prompt token**：之前 system prompt 的 token 没被计入总输入，
导致缓存命中率计算偏差。现在用 `estimate_text_tokens()` 单独计算 system prompt token，
让统计更准确。

### 缓存命中率计算

[parse_cache_usage()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/llm/cache_policy.py)
处理不同 API 的缓存语义差异（按厂商 `CachePolicy` 查表取命中字段）：

```python
# OpenAI / DashScope 兼容协议：input_tokens 已包含缓存命中部分（命中是其子集）
# 命中率 = cache_read / input_tokens            → input_includes_cache=True（默认）

# Anthropic 协议（含各家 /anthropic 兼容端点）：input_tokens 只记未命中部分
# 命中率 = cache_read / (input_tokens + cache_read)  → input_includes_cache=False
```

**为什么需要 `input_includes_cache` 参数**：Anthropic 协议下 `input_tokens` 不含
`cache_read_input_tokens`，命中数可以远大于未命中输入（如 system prompt 全命中）。
若按 OpenAI 语义做「命中数远超输入数即为累计值异常」的合理性校验，会把正常命中
丢弃，导致命中率显示 0%。DeepSeek 走 Anthropic 兼容端点时即为此场景，
复盘见 [docs/fixlogs/token-stats-compact-cache-fix.md](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/docs/fixlogs/token-stats-compact-cache-fix.md)。

### 会话级命中率统一口径（`Usage.cache_hit_rate`）

单次 usage 归一化后，跨轮累计的命中率展示统一由
[Usage.cache_hit_rate](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/llm/base.py)
计算（百分数 0~100）：以 `cache_read_tokens > input_tokens` 作为「input 不含缓存」
的信号决定分母，无输入 token 时返回 0。两个展示端共用这一份实现，避免各写一套
分母规则导致指标对不上：

桌面壳侧展示与字段口径见 [07-UI层.md](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/docs/architecture/07-UI层.md)，
本次统一口径的复盘见 [docs/fixlogs/desktop-form-overflow-usage-hit-rate.md](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/docs/fixlogs/desktop-form-overflow-usage-hit-rate.md)。

### /compact 命令异步修复

`/compact` 命令之前的 bug：`RuntimeError: asyncio.run() cannot be called from a running event loop`

**原因**：`handle_compact` 和 `_compact` 是同步函数，内部用 `asyncio.run()` 调用异步压缩逻辑。
但 JARVIS 主循环已经在 asyncio 事件循环里，嵌套调用 `asyncio.run()` 会报错。

**修复**：把 `handle_compact` 和 `_compact` 改为 async 函数，用 `await` 替代 `asyncio.run()`。

### 缓存友好设计清单

| 设计 | 作用 |
|------|------|
| LayeredContext 冻结前缀 | 压缩后摘要固定，前缀稳定 |
| 反应式压缩不变前缀 | compact_reactive 只压缩活跃窗口 |
| Skill 按需加载（摘要注入） | system prompt 从 64k → 1.5k token |
| 工具按 name 排序 | built-in 作为连续前缀，cache breakpoint 稳定 |
| 图片淘汰 | 旧图替换为文本占位，不破坏前缀 |
| 工具结果折叠 | 旧结果替换为文本占位，不破坏前缀 |
| 文件回灌 | 作为新 user 消息追加，不修改历史 |
| 画像注入进程内缓存 | 同会话画像块逐字节稳定，不破坏前缀 |

## 十四、画像记忆（Profile Memory，长期记忆 Phase 1a）

### 设计动机

短期上下文（LayeredContext）解决"当前对话记得住"，画像记忆解决**跨会话的"懂你"**——
Jarvis 记住用户的偏好、习惯、背景，越用越个性化。这是 VISION 六维度中"记忆"维度的第一层
（后续：1b 情景记忆向量化检索、1c 关系图谱）。

### 数据流

```
会话中（零成本）
  └─ 画像块（限额 300 token）注入 system prompt（进程启动时渲染一次并缓存）
  └─ 渲染（profile_inject）：主题命中 → 短条目 → 长条目，逐条试装（放不下就跳过）
  └─ LLM 据此个性化行为（"先生，已经很晚了……"）

提炼（后台线程，三类触发；绝不在对话路径跑 LLM）
  └─ 阈值：每轮 _auto_save → maybe_refine_async()（delta ≥ profile_refine_min_delta，默认 7 条）
  └─ 终态：退出 / 切换会话 / 新建 → final=True（只要求 delta≥1；退出时最多等 15 秒）
  └─ 手动：/memory refine → force=True
  └─ 水位台账 ~/.jarvis/memory/refine_ledger.json：只取 messages[refined_until:]
  └─ 截取增量（过滤命令/工具消息，单条截 300 字、最多 40 条）
  └─ ① 抽取（第 1 次 LLM）：只读增量对话 → 候选 {content, category, confidence}
     —— 硬闸：空内容 / >40 字 / 非法类别（降 other）/ 置信度 clamp 0.3~0.95
  └─ ② 逐条召回（纯本地）：每个候选取 top-K 最像旧条目
     —— 打分 = bigram 相似度 + 别名命中 0.30 + 同类别 0.15
  └─ ③ 裁决（第 2 次 LLM）：候选 + 各自近邻 → **add / update / delete / noop**，
     并给 add/update 生成 2–5 个检索别名（每个 2–6 字）
  └─ ④ 落盘：add→查重闸；**update→建新 + 旧条目打失效标记（P2b 软删除）**；
     delete→物理删；**noop→不写内容，但 touch_reference 续命**（“不记但确实又提到了”）
  └─ 存储层查重闸（merge_or_add）：new/updates 写入前归一化全等或
     相似度 ≥0.85 命中已有条目 → 合并（置信取大、manual 优先），不新增
  └─ 本轮写盘后全量归并（dedup_all）：清掉修复前积压的深重复条目
  └─ 写入 ~/.jarvis/memory/profile.json（原子写 + 锁）
  └─ 成功/无内容 → advance 水位（同时落 `last_report` 计数，供 `/memory` 展示）；
     报错/无 LLM → 不推进，下次重试同一段

每日 03:30（ProactiveEngine 静默维护）
  └─ expire_episodic()：已到期的 episodic 条目物理出清（显式到期，不是衰减）
  └─ audit_freshness()：只统计“休眠”条数，**不改数据、不删除**
     weight = confidence × 0.5^(距最近确认天数/30)；weight < 0.10 → 休眠
  └─ prune_over_limit(200)：超容量才物理淘汰权重最低者
```

### 生命周期（P2a）

| lifecycle | 典型内容 | 遗忘策略 | 合并时 |
|---|---|---|---|
| `permanent` | 姓名、学历、家人、长期抱负（identity/relationship/aspiration） | 不降权（weight = confidence），只能被显式 update 替换 | 最高优先，不被 stateful 降级 |
| `stateful` | 偏好、作息、工作习惯、在做的事、心思 | 30 天半衰降权；weight < 0.10 进休眠（不注入，保留） | 中间 |
| `episodic` | 带到期时间的一次性事项 | `expire_at` 到期直接出清；未设时按 stateful 降权 | 最低 |

- **类别派生**（确定性，不靠 LLM）：identity / relationship / aspiration → permanent，其余 stateful；
- **兼容**：老库（version≤2）无 lifecycle 字段 → 读取时按类别派生，不写盘迁移；磁盘 version 3；
- **合并**：`permanent > stateful > episodic`，`expire_at` 取大——同一条事实被以 stateful 再报一次不会降级。
- **软删除（P2b）**：`update` 不再物理删旧条目，而是打 `invalidated_at` + `superseded_by`（指向新条目）；
  失效条目不再注入、不召回、不参与去重/降权/展示，但保留在磁盘上可追溯；
  `delete`（模型明确要求删）仍物理删；`/memory` 末尾提示“另有 N 条已被新事实取代”。
  **类别与 lifecycle 缺省时继承旧条目**（2026-11-15 实机修复：模型不写 category 曾把
  identity/permanent 降级成 other/stateful，见 fixlogs/profile-update-category-downgrade-fix.md）。

### 权重与休眠（衰减只降权，不删除）

`confidence` 是“这条事实多可信”（LLM 给的），不被时间反复乘；时间只影响“还该不该
把它顶到前面”。因此**权重是读时派生值，不落盘、不改条目**：

```
weight = confidence × 0.5 ^ (距最近确认天数 / 30)
距最近确认 = max(updated_at, last_referenced_at, created_at)
```

| 用途 | 行为 |
|---|---|
| 注入 | 只用 `active_entries()`（weight ≥ 0.10）；休眠条目不占预算 |
| 召回（写入侧裁决） | 休眠条目不排除（仍是 update 的合法目标），权重作同分排序 |
| 超容量淘汰 | 按权重最低先淘汰（唯一“容量兜底才删”） |
| `/memory` | 显示权重与“休眠”标记；休眠条目仍然看得见 |

- **复活**：再被提及（noop 或合并）刷新 `last_referenced_at` → 权重自动回到 `confidence`；
- **真正会删的只剩**：episodic 显式到期、超 200 条容量淘汰、用户/模型显式 `delete`；
- **参数**：半衰期 30 天、休眠阈值 0.10 仍为经验值，待 P4 评测集校准。

### 事件轨（P2c）

画像库回答“他是什么样的人”，事件轨回答“何时有什么事”。两者物理分离：

```
裁决为 episodic（带 expire_days 的临时事项）
  └─ 写入 profile.json（带 expire_at，到期由 expire_episodic 出清）
  └─ 同时追加 ~/.jarvis/memory/events.jsonl（append-only，一行一条）
  └─ 默认**不注入** system prompt；/memory events [n] 查看最近未过期事件
  └─ 每日维护按 profile_event_retention_days 清理“到期或过老”记录
```

- 契约：裁决段可选输出 `"lifecycle": "episodic"` + `"expire_days"`（1–365）；
  非 episodic 的候选会被**强制清空**这两个字段，防普通事实被误设到期；
- 存储：`events.jsonl` 只追加、不参与去重与画像主库；坏行跳过不报错；
- 取舍：临时事项不该长期占注入预算，所以默认不进 system prompt，需要时用命令查看。

### 按需检索（P5，RecallProfile 工具）

注入段只放「活跃且权重高」的一小部分；库越大覆盖率越低。P5 补一条**模型主动检索**的路：

| 项 | 契约 |
|---|---|
| 工具名 | `RecallProfile`（`deferred=True`，经 ToolSearch 按需发现，不占每轮 schema） |
| 入参 | `query`（必填）、`category`（可选）、`top_k`（默认 `profile_recall_tool_top_k`=8，夹 1–20） |
| 检索 | 纯本地：`recall_similar` = 字符 bigram + 别名命中 0.30 + 同类别 0.15；**不引向量、不发网络** |
| 范围 | 包括休眠条目（用户主动问起就该捕回来）；失效条目已由 `entries()` 排除 |
| 返回 | 类别 + 内容 + 置信度 + 提及次数 + 前 3 个别名；无命中时告知库内条数 |
| 权限 | 只读、并发安全、ALLOW |

提示词只在**确实存在未注入条目**（`dormant_count() > 0`）时补一句“可调用 RecallProfile 检索”，
小库不推销工具；这句与画像段一起进进程级缓存，不破前缀缓存。

### 关键设计决策

| 决策 | 理由 |
|---|---|
| 提炼异步 + 水位增量 + 三类触发 | 绝不在对话路径跑 LLM；只喂增量，同一段对话不被反复提炼。触发只有阈值（默认 7 条）/ 终态（退出·切会话·新建）/ 手动；**成功不节流**（水位+条数已限频），`profile_refine_interval` 只用于失败退避，否则 provider 报错时每轮重试 |
| 注入进程内缓存 | 同会话 system prompt 逐字节稳定，不破坏 LLM 前缀缓存 |
| 独立提炼模型（`[memory.refine]`） | 用便宜模型（如 deepseek-v4-flash）跑后台任务，省成本；api_key 留空时按“环境变量 → 自定义模型 → 主 LLM”解析，避免拿错别厂商 key（见 fixlogs/profile-refine-auth-fix.md） |
| 宁缺毋滥 prompt | 一次性闲聊不记，只提取稳定事实；**禁止推测/替用户补因果**，非 episodic 的 add/update 含“可能/也许/大概”等推测词由解析层直接拒收（见 fixlogs/profile-refine-speculation-fix.md） |
| **两段式 + 四操作（NOOP）** | 抽取与裁决拆开、候选各自带 top-K 近邻；`noop` 承接“看着像重复但不值得改”的全部情况——只给 add/update 两个出口时，重复是协议逼出来的 |
| **画像只记"人"，不记"事/系统"** | 判断口径：**这条 5 年后还成立吗？描述的是"人"还是"事/系统"？** 助手工作流、命令/端口/路径/依赖、技术实现细节、环境状态、一次性事件一律不记（2026-11-15 用户校正）。类别因此新增 `personality`（性格）/ `aspiration`（愿望抱负）/ `mindset`（心思）；细碎事实归长期记忆 `MEMORY.md`，不进画像 |
| 存储层确定性查重（merge_or_add） | 去重不能只靠提炼 prompt 的软约束（LLM 常把旧事实当新事实再报，或已有画像超展示上限看不见）：写入时归一化全等或字符二元组相似度 ≥0.85 即并入已有条目，置信取大、manual 优先保留（见 fixlogs/profile-duplicate-memory-fix.md） |
| **生命周期分层（P2a）** | 身份/关系/抱负是 permanent，不该靠反复提及续命；临时事项带 `expire_at` 到期出清；其余 stateful 走半衰期。分层由**类别确定派生**，不增加配置、不靠 LLM 拍脑袋 |
| **注入侧主题优先 + 两轮填充** | `render_for_prompt` 拆到 `profile_inject.py`：命中 `profile_inject_prefer_topics` 的条目置顶（空列表＝旧排序）；其余条目按"长度 ≤ 中位数"先放一轮、长条目补第二轮，避免一条 40 字事实挤掉 4–5 条短事实 |
| **预算口径可切换（默认不变）** | `pseudo`＝`len/4`（旧口径，默认）；`weighted`＝中英分权真 token。默认不切，切到 weighted 必须同步下调 `profile_inject_token_limit`，具体值待评测集实测定 |
| 半衰期衰减 + manual 豁免 | 过时记忆**只降权不删除**：`weight = confidence × 新鲜度`，低于 0.10 休眠（不注入、保留可复活）；真正删除只剩到期 episodic / 超容量淘汰 / 显式 delete。续命依据已接线：noop 或合并会刷新 `last_referenced_at` 并 `ref_count+1`（见 fixlogs/profile-decay-reference-wiring-fix.md）；30 天/0.10 仍为经验值，待评测集校准 |
| `/memory` 用户可见可编辑 | 信任原则：管家记得你什么，你必须看得见 |

### /memory 命令系

| 命令 | 作用 |
|---|---|
| `/memory` | 查看画像列表（id/类别/内容/置信度/来源/提及次数）；头部附**上轮提炼计数**遥测（抽取/新增/更新/删除/合并/跳过/拒绝）；末尾提示被取代的历史条数 |
| `/memory add <文本>` | 手动添加（当前会话立即生效——重建 system prompt；深重复则并入已有条目而非新增） |
| `/memory del <id>` | 删除条目 |
| `/memory clear yes` | 清空全部（二次确认） |
| `/memory dedup [yes]` | 归并画像库里已积压的深重复记忆（先预览重复组与可归并条数，`yes` 才执行；manual 优先保留） |
| `/memory refine` | 立即提炼当前会话（不等自动节流；本轮写盘后顺带做一次全量归并，清理修复前积压的重复） |
| `/memory sync` | 同步本地画像到知识图谱（dry_run 预览；`/memory sync yes` 确认后写入，管线查重保证幂等） |
| `/memory events [n]` | 查看事件轨最近 n 条（默认 5、最多 50；临时事项，默认不注入对话） |
| `/memory file` | 查看 MEMORY.md 长期记忆文件（旧功能） |

### 知识图谱画像桥（P2 双向同步）

`agent/core/extensions/profile_bridge.py` 打通 jarvis 与 aceFelix 知识图谱：

```
[图谱] ──MCP get_profile──▶ 启动预加载 ──▶ system prompt 画像段（与本地画像两段合并）
    ▲                                            冲突规则：图谱为唯一事实源，以图谱为准
    └────MCP ingest_text（/memory sync 预览确认后）──── 本地画像条目汇总文本```
- 图谱 → jarvis：`preload_kg_profile` 在 MCP 连接后、`build_system_prompt` 前拉取并缓存，
  渲染成 `# 关于用户（知识图谱画像）` 段（`token_limit` 限额裁剪）
- jarvis → 图谱：回写复用图谱抽取管线（查重/类型白名单/防噪闸），而非逐条 `add_entity`
- 开关 `[profile_bridge] enabled`（默认关），`server` 指定 mcp.json 中的 server 名
