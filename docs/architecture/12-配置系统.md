## 二、四文件分层配置合并

### 优先级（后者覆盖前者）

```
1. 内置默认值 (Settings dataclass)
       ▼
2. configs/settings.toml (项目级通用配置，随仓库分发)
       ▼
3. configs/models.toml (项目级模型域，同层覆盖上一项)
       ▼
4. ~/.jarvis/settings.toml (用户级通用配置，自动创建)
       ▼
5. ~/.jarvis/models.toml (用户级模型域，同层覆盖上一项)
       ▼
6. 环境变量 (JARVIS_* / 厂商专属 *_API_KEY，由 env.py 处理)
       ▼
7. API Key 系统 keyring (仅 api_key，env.py 兜底)
       ▼
8. CLI 参数 (--model / --provider / --api-key，main.py 处理)
```

### 配置查找策略

[load_settings()](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/config/settings.py#L301)：

```python
def load_settings(workdir: str | None = None) -> Settings:
    cwd = Path(workdir or os.getcwd()).resolve()
    _pkg_root = Path(__file__).resolve().parent.parent.parent

    s = Settings(workdir=str(cwd))

    # 2. 项目级 settings.toml（找不对则回退 agent/configs/*.example.toml）
    project_cfg = cwd / "configs" / "settings.toml"
    s = _apply_toml(s, _read_toml(project_cfg))
    # 2b. 项目级同层 models.toml（模型域）
    s = _apply_toml(s, _read_toml(models_path_for(project_cfg)))

    # 3. 用户级 settings.toml（兼容 ~/.my-agent/）
    # 先跑 schema 迁移，再把模型域拆分到同层 models.toml（幂等）
    user_cfg, user_models_cfg = user_config_paths()
    auto_split_user_config(user_cfg)
    s = _apply_toml(s, _read_toml(user_cfg))
    # 3b. 用户级 models.toml（同层覆盖 settings.toml，用户级整体覆盖项目级）
    s = _apply_toml(s, _read_toml(user_models_cfg))

    # 4. 环境变量（内部含 keyring 兜底）
    return apply_env_overrides(s)
```

**为什么分层**：
- 项目级：随仓库分发，提供默认值
- 用户级：个人偏好，持久化（如 last_model、custom_models）
- 同层两个文件：模型域（含密钥、程序回写）与通用域隔离，互不牵连
- 环境变量：CI/CD、容器化部署

> `user_config_paths()` 成对返回 settings/models 路径，两者必须同目录：
> 目录优先 `~/.jarvis`，仅当 `~/.jarvis/settings.toml` 不存在且 `~/.my-agent/settings.toml`
> 存在时才用旧目录（否则会出现「settings 读老的、models 读新的」而模型配置失效）。

### 上下文压缩

```python
context_compaction: bool = True
context_window: int = 128000  # 模型窗口大小（token），换模型时同步修改，勿设 0
compact_ratio: float = 0.5    # 触发比例（占窗口百分比）
compact_refreeze_growth: float = 1.25  # 防抖：冻结后总量增长不足此倍数不重复压缩
compact_max_output_tokens: int = 2048  # 压缩摘要请求的输出 token 上限
tool_result_keep_recent: int = 4  # 工具结果折叠时保留最近 N 条完整输出
```

自动压缩触发条件（唯一机制，比例模式）：

- 总 token（冻结摘要 + 活跃窗口 + system prompt）≥ `context_window × compact_ratio` 时才触发；未超比例绝不压缩，用满窗口前半程。
- 附带防抖：总量较上次冻结后增长不足 `compact_refreeze_growth` 倍不重复压缩，避免窗口配置过小时每轮白压。
- 旧的 `compaction_threshold`（绝对阈值）与 `keep_recent_messages`（可配保留条数）已移除：保留条数固定为内部默认 6。

## 八、last_model 持久化

### 为什么持久化

用户切换模型后，下次启动自动恢复上次选择。

### 实现

- `last_model` 存在 `~/.jarvis/models.toml` 顶层（由 `models_config.upsert_last_model`
  经 `upsert_top_scalar` 写入，始终落在顶层键区，不会掉进子表）
- 启动时若 `last_model` 存在，覆盖 `model`（位置在所有配置层与环境变量之后，优先级最高）
- 切换模型时调用 `save_last_model()` 持久化

**发布模板不预置 `last_model`**：`models.example.toml` 在没有项目级 `configs/*.toml`
时就是项目层（三级回落的兜底），它一旦带着 `last_model`，就会压住用户后改的 `model`
与用户层配置，表现为「改了配置不生效」。该约束由
`tests/config/test_models_config.py::TestExampleTemplateLayer` 把守，
复盘见 [fixlogs/example-template-last-model.md](../fixlogs/example-template-last-model.md)。

### 关联字段

切换模型时一起持久化：
- `last_model`
- `provider` / `api_format` / `base_url` / `api_key`
- `default_provider` / `default_api_format` / `default_base_url` / `default_api_key`（原始值）

**为什么存 default_*：切回内置模型时用这些值重建 provider，避免停留在自定义模型配置上。

### 与运行时热切换的关系（2026-09）

- `last_model` 仍是「跨重启恢复」的唯一来源：写盘失败（`save_last_model` 返回 false）时
  serve 回 `result=false`、且**不**入队切换指令；
- 写盘成功后 serve 另发 `{"cmd": "switch_model"}` 给引擎线程，立即换掉运行中的
  provider / QueryLoop（见 [07-UI层.md](07-UI层.md) 「模型热切换」），无需重启进程；
- REPL `/model` 与工作台/桌面壳共用 `model_manager._build_switched_provider` 决定
  「重建 provider 还是复用」，两端口径一致。

**`baseline` 参数（2026-10-27，真机实测后补）**：判断「要不要重建」必须拿
**正在跑的那份端点**当基准。`/init` 的路径是「先把新值原地写回 `ctx.settings`
（其他模块持有同一引用，不能换对象）→ 再切模型」，若拿被改过的 settings 去比，
`cfg` 与 settings 恒等 → 永远判定无需重建 → 复用启动时那个旧 provider（旧
`base_url` / 旧 key），于是用户看到「✓ 连接成功」下一句却报 `Connection error`。
所以 `_build_switched_provider(..., baseline=...)` / `_switch_model(..., baseline=...)`
把「比较用哪份」与「构造新 provider 用哪份」拆开：**比较用 baseline，构造用
settings**；不传 baseline 时沿用 settings（REPL `/model`、工作台热切换行为不变）。
复盘见 [fixlogs/init-not-applied-to-session-fix.md](../fixlogs/init-not-applied-to-session-fix.md)。

### `base_url` 留空到底走哪里（容易误判）

留空**不会**按 `provider` 自动补厂商地址，它只是“不传给 SDK”：

| `api_format` | 留空时的实际端点 |
|---|---|
| `openai` 及各类 OpenAI 兼容 | SDK 默认：读 `OPENAI_BASE_URL`，否则 `https://api.openai.com/v1` |
| `anthropic` | `https://api.anthropic.com` |
| `dashscope` / `dashscope_sdk` / `zai` | 由 SDK 自己管端点 |

所以「配了 key 却报 `Connection error`」的第一嫌疑就是 base_url 实际落到了
`api.openai.com`（banner 里的 provider 名也会被推断成 `openai`——名字按 base_url 反推）。

厂商 → 默认地址的**单一来源**是 [vendors.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/config/vendors.py)：
`/init` 的首启表用它，`/models` 添加模型时 base_url 留空也从它推断。
历史上这两处各写一份且已漂移（DeepSeek 少 `/v1`、小米 MiMo 只在一边有），
表现为「首启配的能连通、`/models` 加的同厂商模型连不通」。

> 阶段 12 P1。立论数据（2026-10-26 实测盘点）：`Settings` 共 **190 个字段**，桌面面板

### 为什么不让模型直接写 settings.toml

直接让模型编辑配置文件，它维护的就是**实现细节本身**：字段一改名、默认值一调整，
用户当初那句"以后我写代码时别念出来"就丢了，剩下一行 `quiet_hours = "..."`，
谁也说不清它为什么是这个值。所以分成三层，P1 只做前两层：

| 层 | 谁负责 | 产物 |
|---|---|---|
| **意图** | 模型（理解人话） | —（P3：偏好账本）|
| **推导** | 确定性代码（不烧 token、可测） | 真源表 + 分级 + 校验 |
| **落盘** | 已有的外科式写入（`toml_writer.save_section`）| 只改该改的那几行 |

### 真源表：`agent/config/config_specs.py`

`CONFIG_SPECS` 是唯一真源。**阶段 12 P2（2026-10-27）之后**，`percept_settings`
与 `desktop_settings` 都从本表**派生**，不再各写一份。每项带五组元数据：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `key / section / field / attr` | 协议键 / TOML 段落 / 段内字段名 / Settings 属性名 | 多数三项同名，但 `[deadline] enabled` → `deadline_enabled`、`[policy.notify_budget] daily_max` → `notify_daily_max` 并不相同；写错段落**不会报错**，值会落进没人读的地方 |
| `tier` | `auto` / `confirm` / `forbidden` | 谁能改（见下）|
| `apply_mode` | `live` / `policy` / `percept` / `reschedule` / `restart` | 改完怎么生效——由表声明，**不让模型自己判断** |
| `panels` | `desktop-settings` / `percept-panel` | 哪个界面能改（与 tier 正交，见「双入口派生」）|
| `lo / hi / default / hint` | 范围、缺省、一句人话 | 校验与解释 |

共 28 项：**15 auto + 12 confirm + 1 forbidden**（模型可见 27 项，forbidden 那项
`log_events` 只在面板上可改）。

### 双入口派生：一份表，三个消费者

P1 收尾时跑差集，同一个配置散在四处的代价已经显现：

```
面板能改、真源表没有（7 项）：enabled、file_watch_dirs、log_events、mail_watch_senders、
    vcs_repos、vision_auto_stop_minutes、window_exclude_apps
真源表有、面板改不了（7 项）：quiet_hours、daily_max、min_salience、aggregate_window_s、
    percept_enabled、tasks_enabled、undo_window_s
```

最刺眼的是 `enabled` 与 `percept_enabled`——**同一项两个名字**，两张表各自维护。
P2 改成派生后：

| 消费者 | 怎么拿到自己那份 |
|---|---|
| `ConfigList` / `ConfigSet` | `list_specs()` → tier 属于 auto/confirm 的项 |
| 桌面 `settings.get/set` | `desktop_settings.DESKTOP_SETTING_SPECS` = `panel_specs(PANEL_DESKTOP)` |
| 感知源面板 `percept.config.get/set` | `percept_settings.PERCEPT_CONFIG_FIELDS` = `panel_specs(PANEL_PERCEPT)` |

新增一项只改真源表一处，三个入口自动跟上；`tests/config/test_config_derivation.py`
（49 例）负责让"又漂回去"变成不可能：派生集与真源集必须逐项相等、视图字段
（attr/kind/label/范围）必须等于真源、面板键要么同名要么在别名表里、
每个 `tier=forbidden` 项必须有自洽理由。

**面板侧唯一的不同名**：`PANEL_KEY_ALIASES = {"enabled": "percept_enabled"}`。
`[percept] enabled` 在面板对象里叫 `enabled` 已经够清楚（对象名限定了语境），
而模型面对的是一个**扁平键列表**，叫 `enabled` 会与 `[deadline] enabled` 撞名。
两边各自合理，所以把差异写成显式表——而不是靠"碰巧一致"。

### 三类分级

| 分级 | 范围 | 落到哪 |
|---|---|---|
| `auto` | 纯表达层：音量、语速、主动播报出声、简报/截止日期开关与时间、感知逐源开关、停留阈值 | `PermissionResult.allow` |
| `confirm` | 涉及"何时能打断用户"或"能干什么活"：`quiet_hours` / `daily_max` / `min_salience` / `aggregate_window_s` / `percept_enabled` / `tasks_enabled` / `undo_window_s`，以及 P2 新收的感知**名单类**（守望目录 / 登记仓库 / 发件人名单 / 排除应用）与摄像头空闲时长 | `PermissionResult.ask`（W1 那套管线已有的 ASK）|
| `forbidden` | 权限与凭据本身：`sandbox_*` / `api_key*` / 邮箱密码 / `log_events` | `PermissionResult.deny` + 一句"正确改法" |

**为什么打扰预算必须 confirm**：模型若能自己把 `daily_max` 从 10 调到 50、或把
`quiet_hours` 挪开，等于它单方面拆掉了 W1 用来约束自己别碎嘴的护栏。这是**自我提权**
的另一种形式，与改沙箱开关同类。

`forbidden` 项分两种登记方式：

- **纯名字 + 理由**（`sandbox_*` / `api_key*` / 邮箱密码）：登记在 `FORBIDDEN_SPECS`
  （键 → 理由）+ `FORBIDDEN_PREFIXES`（成族前缀），不进 `CONFIG_SPECS`——它们
  不需要范围/缺省/面板位置，登了也没用。
- **带元数据进表**（`log_events`，P2 新增的情形）：它**面板上要能改**（人该能关
  本地留痕），但**模型一律不许改**（关掉等于让自己的采集不留痕迹，是审计断链）。
  允许它带 `tier=forbidden` 进 `CONFIG_SPECS`，硬约束两条：①`list_specs()` 里
  一个都不能出现（模型连名字都看不到）；②必须在 `FORBIDDEN_SPECS` 里有自洽理由。
  两条都由测试钉住。

理由一律写成**自己站得住**的一句话——`forbidden_reason()` 一次只返回一条，
写成"同上：…"到了那种上下文就是废话。

### 五种 `apply_mode`

| 模式 | 判据 | 例子 |
|---|---|---|
| `live` | 每次用都现读 Settings | `tts_volume`（TTS 每次构造时读）|
| `policy` | 进程内**懒建单例**，须显式重建 | `[policy.notify_budget]` 四项 |
| `percept` | 装配快照，须重装配感知总线 | 逐源开关、`percept_enabled`、名单类与停留阈值 |
| `reschedule` | 启动快照，须重注册每日任务 | 简报/截止日期 |
| `restart` | 只落盘，下次启动生效 | `tasks_enabled`、`undo_window_s` |

**`policy` 这一档是写代码时才发现的坑**：`get_budget()` 是
`if _budget_singleton is None:` 才重建的懒建单例，把那四项标成 `live` 就是
"只落盘不生效"——用户看到"保存成功"而阈值没变。`init_policy(settings)` 顺手把
单例置空，重建后不会丢当日计数（计数落在 `~/.jarvis/notify_state.json`）。

**`list` 类的两道口径**（P2 新对模型开放的名单项）：

- 写入侧统一走 `clean_list`：非字符串拒、strip、丢空、按序去重、单项 ≤500 字、
  最多 50 项；模型（`validate_value`）与面板（`validate_percept_config`）
  **共用这一份**，否则迟早一处放行一处拒。
- 读侧刻意**不做**那套上限校验：手改的 TOML 里写了 60 条名单也该如实显示，
  读不该报错；但缺省若是不可变空元组（dataclass 不容可变缺省）必须转回 list，
  否则面板拿到 `()` 而前端只认数组。

### 生效钩子：宿主注册，工具分派

`config_specs` 维护 `{apply_mode: [回调, ...]}`。`percept` / `reschedule` 两档改的是
**宿主装配出来的东西**，只有宿主知道怎么重新装配，所以由宿主登记：

```
ProactiveHub._start_percept()
  └─ agent/serve/config_hooks.register_hub_apply_hooks(self)
       ├─ APPLY_PERCEPT    → hot_update_percept()   （停旧总线 → 重装配，去重账本接续）
       └─ APPLY_RESCHEDULE → hot_update_schedule()  （按当前 Settings 重注册每日任务）
```

为什么不让工具直接调 hub：终端 REPL 场景压根没有 hub，而"没有宿主"本身要**如实回执**
（"已保存，重启后生效"）——工具不该知道自己跑在哪种宿主里，否则同一段逻辑要在
CLI / serve 各分叉一次。`policy` 档则相反，它是进程内的，工具自己就能重建。

钩子拆在 [config_hooks.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/config_hooks.py) 而不是塞进 `hub.py`：
`hub.py` 已 790 行贴着单文件 800 行硬上限，而这几个方法本质是**配置层与宿主的接线**，
既不属于"感知总线装配"也不属于"通知投递"。

### 两个工具（`agent/tools/config_tool.py`）

| 工具 | 作用 | 要点 |
|---|---|---|
| `ConfigList` | 列可改项：协议键 / 中文名 / 一句话说明 / 当前值 / 是否需要确认 | `forbidden` 项**连名字都不返回**（给了模型就会反复试探，得到的只有一句拒绝）|
| `ConfigSet` | 按协议键改一项或多项，记"原值 → 新值"进副作用账本 | ①**先校全部再落盘**：多键补丁任一失败则整批不动，不留"改了一半"；②权限分级直通 `check_permissions`；③`call()` 里对 `forbidden` **再兜一道**（权限层被绕过时也不放行）|

两个工具都不做具体读写：`ConfigList` 调 `render_spec_list`、`ConfigSet` 调
`apply_config_patch`，与终端命令共用同一条路径（见下一节）。

### 改完之后：界面怎么知道（`settings_changed`）

后端改成功不等于用户看得见。桌面设置面板只在 `init`（连上后端）时拉一次
`settings.get`，之后**从不刷新**——模型把音量 100 改成 50、文件与运行时都对了，
滑杆却还停在 100；更危险的是用户顺手拖一下滑杆，面板会把 100 又写回去，
**静默覆盖掉模型的改动**（实测缺陷，见
[复盘](../fixlogs/config-panel-not-refreshed-after-model-set-fix.md)）。

所以配置层多了一层**变更监听器**（与生效钩子刻意分开）：

```
config_tool: 落盘 + 改运行时 + 跑生效钩子
  └─ notify_changed({协议键: 新值})
       └─ 宿主登记的回调 → 事件队列
            {"type":"settings_changed",
             "payload":{"keys":["tts_volume"],"source":"model"}}
                 └─ 桌面 dispatcher → refreshSettings()
                      └─ 感知键额外 refreshPercept()（计数器 → 面板重拉）
```

三条边界必须分清：

| 情形 | 行为 |
|---|---|
| 值没变（无变更被剔掉） | **不广播**（面板没必要重拉）|
| 校验失败 / 禁改项被拒 | **不广播**（值没落地）|
| 监听器自己抛异常 | 吞掉，写入仍算成功（界面刷新失败不该让配置写入变失败）|

为什么单独加一层而不复用生效钩子：钩子按 `apply_mode` 登记，而 `live` 类项
（音量、语速）本来就不需要"生效"动作，也就没有钩子可挂——**可界面恰在这个时候
最容易说错话**。"怎么生效"与"谁该知道"是两件事。

### 回退：`undo_spec` 新增第三种形态

配置回退不是文件树快照，git 检查点那套"回到本轮开始前的工作区"术语用不了，
所以 `journal.py` 单列 `UNDO_CONFIG = "config"`：

```json
{"kind": "config", "before": {"tts_volume": 50}}
```

`/undo` 据此"把原值再写一遍"（落盘 + 运行时），不碰 checkpoint。
副作用账本关着时，回执会如实说"本次改动无法用 /undo 回退"。

### 与既有两个写入口的关系

| 入口 | 谁能用 | 落盘路径 |
|---|---|---|
| 桌面面板 `settings.set` / `percept.config.set` | 用户 | `panel_specs` 派生的 `desktop_settings` / `percept_settings` |
| 终端 `/config show` \| `/config list` | 用户 | 只读 |
| 终端 `/config set <键> <值> [--yes]` | 用户 | `config_ops.apply_config_patch` |
| **`ConfigList` / `ConfigSet`** | **模型** | `config_ops.apply_config_patch`（同一个函数）|

四处最终都走同一个 `toml_writer.save_section`（唯一实现，保注释与其他字段），
所以"外科式写入"的行为不会漂移。

### 两个入口共用一条写入路径（`agent/config/config_ops.py`，阶段 12 P2）

`/config set` 与 `ConfigSet` 要做的六步**完全一样**：禁改兜底 → 逐项校验 →
剔掉"本来就是这个值" → 外科式落盘（失败整批回写）→ 改运行时并按 `apply_mode`
生效 → 广播变更 + 记副作用账本 + 给回执。所以只留一条实现：

```
agent/config/config_ops.py
├── render_spec_list(settings, tiers)                  ← ConfigList 与 /config list 共用
├── apply_config_patch(settings, patch, *, entry=...)  ← ConfigSet 与 /config set 共用
├── parse_cli_value / render_cli_value                 ← 终端独有：文本 ↔ 原生值（互逆）
└── _save_batch / _apply_modes / _rebuild_policy / _render_changes
```

`config_tool.py` 只留**工具契约**（schema / 权限分级 / 结果包装），`config_commands.py`
只留**终端体例**（子命令分发 / 两段式确认 / Rich 转义）。两个入口的差别只剩：

| 差别 | 模型侧（`ConfigSet`） | 终端侧（`/config set`） |
|---|---|---|
| `confirm` 项怎么过 | 权限管线弹 ASK（W1 已有：无人值守入待批、租约、沙箱都管） | **两段式**：先给预览（原值 → 新值 + 为什么要问），再加 `--yes` |
| `forbidden` 项 | 权限层 DENY | 同样拒绝（护栏是配置本身的属性，加 `--yes` 也绕不过）|
| 值从哪来 | JSON 原生类型 | 一行文本，按 `kind` 解析（布尔认 `开/关/是/否/true/1`）|
| 账本来源 | `args.entry = "model"` | `args.entry = "terminal"` |

为什么终端用两段式而不是阻塞式 `input()`：REPL 主循环不接受嵌套输入；而且
"先看一眼原值 → 新值再决定"比一个 y/N 弹框信息量大（与 `/memory sync` →
`/memory sync yes` 同一体例）。

三条终端侧独有的边界：

| 情形 | 行为 |
|---|---|
| 名单类**没给值** | 拒绝执行，提示写 `/config set <键> ""` 才是清空（裸写一个键就清空太容易误伤）|
| 预览回显 | 回显**规范化后的值**而不是原始输入串（`A, B ,A` → `A, B`），保证照抄回去干净 |
| 值里带方括号 | 回执过 `escape()` 再 `ui.info`（否则 `[x]` 被当 Rich 样式标签吞掉，又是"终端少字、桌面正常"的假象）|

## 十五、偏好账本（阶段 12 P3：配置 = 偏好 + 上下文）

`settings.toml` 回答的是"现在这个值是多少"，偏好账本回答的是"在什么情况下该是多少"。
一句「以后我写代码时别念出来」不能存成 `proactive_tts_enabled = false`——那是永久关闭，
第二天不写代码也不出声了，而用户只会觉得"它今天怎么不说话了"。

```
~/.jarvis/prefs.jsonl        append-only，按 id 合并（与副作用账本同一体例）
{"id":"1edb29c6","key":"proactive_tts_enabled","value":false,
 "when":{"app":"Code.exe"},"said":"以后我写代码时别念出来",
 "created_at":1793000000.0,"hits":3,"state":"active"}
```

### 三条硬边界

| 边界 | 为什么 | 落在哪 |
|---|---|---|
| **只能落 `auto` 域** | 「以后每天最多提醒 50 次」若进偏好，等于用一句话固化了一次本该当场问人的决定——偏好会变成绕过 `confirm` 的后门 | `prefs.remember` 直接 `ValueError` |
| **必须带至少一个条件** | 无条件偏好就是偷偷永久改配置，而且不入账本、不可 `/undo` | `Preference` 工具 `validate_input` 拦；无条件就改走 `ConfigSet` |
| **命中时只降出声不降投递** | 用户说的是"别念出来"，不是"别告诉我"。搞错会真丢消息 | 闸门只把 `speak` 置假，`kind` 仍为 `emit` |

### 推导层的落点：闸门，不是提示词

偏好若只写进系统提示词，模型忘了它就等于没记住——第二天复发，而用户说不出原因。
所以命中判定与施放都在**确定性代码**里：

```
主动播报 → notify_gate_action()
  ├─ 预算闸（W1）→ NotifyAction(kind, speak)
  └─ 偏好闸 ─ prefs.evaluate(current_context())
       ├─ 上下文：{"app": 前台进程名, "workdir": 当前目录, "hour": 小时}
       ├─ 命中且 value=False → NotifyAction("emit", text, "上下文偏好：…（你说过「…」）", speak=False)
       └─ 没命中/取值失败 → 原样放行（绝不因偏好出问题把播报弄没）
```

三个求值口径：

| 口径 | 行为 |
|---|---|
| "不知道"不算命中 | 拿不到前台进程名（无 GUI / 无依赖）时，带 `app` 条件的偏好**不生效**，宁可不动 |
| 越具体越优先 | 同时命中"22 点后"与"在 Code.exe 时"，取条件更多的那条（后者更贴切）|
| 只施放白名单内的键 | 目前只有 `proactive_tts_enabled`（出声）与 `tts_volume` / `tts_speech_rate`（音量语速）接了决策点（`ENFORCEABLE_KEYS`）；其他键可记可查但不自动施放，新增键必须同时改表与调用点 |

### `when_app` 可以写多个

```
“以后我写代码时别念出来”
  → when_app = Code.exe,Qoder.exe,idea64.exe
  → 描述：在 Code.exe / Qoder.exe / idea64.exe 时 → 主动播报是否出声 = 关
```

单值只能命中一个进程，而“写代码”很少只用一个编辑器；记错了用户只会看到
“命中 0 次”却查不出原因（实测暴露：记成 `Code.exe`、实际在 `Qoder.exe` 里工作，
永远不命中）。所以：

| 规则 | 说明 |
|---|---|
| 分隔符 | 英文逗号、中文逗号、分号、多余空格都认（`app_names()` 统一拆） |
| 拆不出名字当空条件 | `app=" , "` 不当有效条件——否则存下去就是一条永远不命中的幽灵偏好，连“必须带条件”也拦不住 |
| 子串方向 | 条件是“被包含”的那侧：`code` 能盖住 `Code - Insiders.exe`，`Code.exe` 只命中它自己 |

### 回执必须说人话：命中没命中，以及为什么

记下一条条件偏好时，回执把**当前前台程序**摊出来：

```
已记住：在 Code.exe 时 → 主动播报是否出声 = 关
（当前不命中：当前前台是 Qoder.exe，15 点；条件写的是「在 Code.exe 时」；id 73a28756）
```

只说“当前不命中”是没用的信息：用户写 `Code.exe` 而实际在用 `Qoder.exe`，
永远想不通。`/prefs` 列表同样每条标出「✓ 此刻命中 / － 此刻不命中」并附当前上下文
（一次列表只探测一次前台窗口，不按条数乘 N）。

### 用户面与模型面

| 面 | 入口 | 能做什么 |
|---|---|---|
| 用户 | `/prefs`、`/prefs suggest`、`/prefs accept <id>`、`/prefs forget <id>`、`/prefs clear` | 看清单（含原话与命中次数）、提炼、接受或拒掉候选、取消 |
| 模型 | `Preference` 工具（`action=list/remember/accept/forget`） | 记一条、列、接受候选、忘一条；一次性调整仍走 `ConfigSet` |

两边的分工是"一次性 vs 带条件"，已写进提示词段（`_SELF_CONFIG_SECTION` 新增
「一次性还是带条件」小节）：判据就看用户有没有说"以后 / 每次 / 当我…时"。

### 施放层只有一个入口：`prefs.effective(key, base)`

新接决策点时最容易写错的地方是"每个调用点各取一份逻辑"（查表 → 比键名 → 判值）。
所以施放只留一个 API：

| 键 | 决策点 | 施放效果 |
|---|---|---|
| `proactive_tts_enabled` | `proactive.notify_gate_action` | `speak=False`（投递不变）|
| `tts_volume` | `serve/hub` 构造 TTS 时 | 音量用偏好值（不改 Settings）|
| `tts_speech_rate` | 同上 | 语速用偏好值 |

表 `ENFORCEABLE_KEYS` 是白名单：键可以记、可以查，但只加了名字却没接调用点，
就是"能记但不生效"的假功能——比没有更糟。所以新增一项必须同时改表和调用点。

### 提炼：只在有共同证据时提，而且它自己不生效

`/prefs suggest` 扫一遍副作用账本里最近的 `ConfigSet` 记录（`args.context` 存了改配置
那一刻的 app 与 hour），按规则产出**候选**（`state=suggested`）：

| 规则 | 为什么 |
|---|---|
| 同一键被改成同一值 ≥ 2 次 | 一次可能只是当场不爽；两次以上才像习惯 |
| 且这几次**有共同上下文**（同一程序或同一小时） | 没有共同点＝没有条件，那不是偏好而是"用户想要这个新值"；凭两次改动编个条件是用户最讨厌的魔法 |
| 只提炼 `auto` 域 | 同记偏好的边界（否则偏好成了绕过确认的后门）|
| 一次改多项的记录跳过 | 分不清是哪一项让用户不满意 |
| 拒过/忘过的同一条件不再重提 | "拒了就闭嘴"；用户想重复可直接说 |

**候选不生效**：`evaluate` 只看 `active`，`suggested` 必须 `/prefs accept` 才转正。

为什么提炼不挂定时器（原计划写的是走 `Scheduler`）：每天凌晨扫一遍，没新意的时候
只会多响一次——而 W1 打扰预算存在的意义就是"别无关紧要地响"。改成**按需触发**
（`/prefs suggest`），用户主动问时才提，比机器主动猜要好。

### 测试隔离（一个真实隐患）

闸门现在会读**真实的** `~/.jarvis/prefs.jsonl`。开发机上若真有一条
「在 Code.exe 时不出声」而跑测试的终端恰好就是 Code.exe，
以前的打扰预算/后台驱动测试会随机变红——那不是回归，是测试读到了别人的配置。

## 十六、首启三问与「用几天后提议」（阶段 12 P4）

P1–P3 之后改配置不再是问题，剩下的问题是**第一次**：新机器上打开什么都没配，
用户得先读文档、跑命令、手改 TOML 才能说上第一句话。

### 只问三件：厂商 / API Key / 模型

```
$ jarvis                      ← 全新机器（未配置 + 交互式终端）
═══ J.A.R.V.I.S 首次配置（3 个问题）═══
① 用哪家厂商    列表选（DashScope / DeepSeek / OpenAI / … / 其他 OpenAI 兼容）
② API Key       回车可跳（跳过后配置也写，之后 /init 补）
③ 选模型        **实时从厂商拉取这个账号可用的模型**，可筛选，也可「手动输入模型名…」
→ 其余全默认：api_format/base_url 取厂商默认，model_type 保守给 text
→ 工作目录不单独问：默认当前目录，结束时提示 jarvis --workdir 可改
```

**为什么模型要在线拉，而不是内置一张“最新模型表”**（实测后改的）：

1. 内置表**会过时**——原来写死的 `gpt-4o`、`deepseek-chat`，一个是 2024 年型号，
   一个已于 2026-07-24 被官方弃用，用户照着选第一次调用就报错；
2. 它**替用户做了决定**——jarvis 要给别人用，“你喜欢哪个模型”不该由我们回答。

所以模型清单由厂商实时提供（`agent/llm/model_catalog.py`：OpenAI 兼容与 Anthropic
两路 `models.list()`，10s 超时，失败返回空）。拉不到时回落到内置兑底款**并明说
没拉到**，且永远保留“手动输入模型名”——列表不能成为用户用不了的借口。

**为什么工作目录不再单独问**：问券预算只有三问，要留给**没有安全默认值**的那件事。
工作目录默认当前目录不会出错；模型写错第一次调用就失败。

| 粒度 | 入口 | 用在哪 |
|---|---|---|
| 三问（默认） | `jarvis --init`、`/init`、首启自动 | 全新机器到能用 |
| 完整引导 | `/init full` | 换厂商、接自建兼容服务、改多模态 |

另外两条：多模态**默认关闭**（猜成多模态会让不支持视觉的模型在发图时报错，
用 `/models` 改才安全）；厂商表的 `name/desc` **不写具体型号**（写上去就是下一张
会过期的表），`default_model` 只作断网兑底。

### 不该问的地方绝不多问

| 情形 | 行为 |
|---|---|
| `stdin` 不是终端（管道 / CI / 脚本） | **不问**——一道交互提示会卡死自动化，比"没引导"严重得多 |
| 已经配过（有 model / custom_models / key 或环境变量 key）| 不问；"配了一半"的走 `/init` |
| 取消过一次首启 | 写 `declined`，**以后不再自动问** |
| `--serve`（桌面壳） | 不问（壳侧有自己的引导与设置面板）|

### 用几天后主动提议一次

`~/.jarvis/usage.json` 只记五件事（首启时间 / 启动次数 / 是否完成首启 / 是否取消过 /
是否提议过）。满足**启动 ≥5 次且首启满 3 天**、且没提过，启动后（banner 之后）
提一次：

```
我注意到你可能想让我记住这些（**还没生效**，需要你点头）：
  · 在 Code.exe 时 → 主动播报是否出声 = 关
    依据：你在 Code.exe 时把「主动播报是否出声」改成了这个值共 2 次（当时你说：写代码别念）
  看全部并接受：/prefs    不要就忽略这条，我不会再自动提。
```

三条边界：候选**不生效**（要 `/prefs accept`）；**只提一次**（没候选也算提过，
否则每次启动都要扫一遍账本）；建议失败不影响启动。

## 十七、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 配置格式 | TOML | Python 3.11+ 内置支持 |
| 合并层级 | 四文件（settings/models × 项目/用户）+ env + keyring | 灵活覆盖 |
| 持久化 | 用户级文件 | 跨会话保持 |
| 环境变量 | env.py 独立模块（A-03） | 职责单一，易维护 |
| 模型持久化 | model_registry.py 薄封装 + models_config.py 实现 | 与加载逻辑解耦 |
| 模型域拆分 | 独立 `models.toml`（同层成对加载） | 程序回写与密钥隔离，避开顶层键顺序陷阱 |
| API Key | keyring 加密存储（S-01） | 减少明文暴露面 |
| 敏感字段 | mask.py 统一脱敏（S-03） | 展示场景一致安全 |
| last_model | 顶层存储 | 早期存 [llm] 段导致不加载 |
| custom_models | [llm.custom_models] | 结构化存储 |
| 模型侧配置入口 | 独立真源表 + 三类分级（阶段 12），权限靠**复用** W1 管线 | 另起一套确认流程必然两处口径不一致 |
| 生效方式 | 由表声明 `apply_mode`，不让模型判断 | 判断错了的后果是"用户以为生效了其实没有" |
| 改完的可见性 | 协议级 `settings_changed` 事件，界面自己重拉 | 不推事件就得前端逐个猜哪个键会影响哪块面板 |
| 沙箱/凭据 | 一律 `forbidden`，模型不可改 | 这两类改动本质是模型给自己提权 |
