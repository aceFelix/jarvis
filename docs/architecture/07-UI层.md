## 二、RichCLI 终端 REPL

### 实现 UIProtocol

[cli.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/ui/cli.py) 的 `RichCLI` 实现 [UIProtocol](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/core/context.py#L22-L38)：

```python
class RichCLI:
    def assistant_text(self, text: str) -> None:
        """流式文本增量 → Rich Live 渲染"""

    def assistant_thinking(self, text: str) -> None:
        """思考内容 → 暗色面板（💭 思考过程）
        交互终端用 Rich Live 原地刷新；非交互终端（重定向/IDE 终端）
        降级静态模式，思考结束时一次性打印，防止刷屏"""

    def tool_use(self, tool_name, tool_input, tool_use_id) -> None:
        """工具调用开始 → spinner + 工具名"""

    def tool_result(self, tool_name, tool_use_id, content, *, is_error) -> None:
        """工具结果 → 成功/错误样式"""

    def info/warn/error(self, text) -> None:
        """提示信息 → 不同颜色"""

    def notify_reminder(self, text) -> None:
        """后台线程（Scheduler 到期回调）播报定时提醒 → `⏰` 上屏。
        打印后必须调 prompt_toolkit `app.invalidate()` 把提示符重绘到输出
        下方，否则提醒会叠在用户正在输入的行上；全程 try/except，
        一次 UI 故障不能终止调度循环。2026-10-14 新增。"""

    def ask_user(self, prompt) -> str:
        """阻塞式询问 → input()"""
```

#### 进程模型（与 realtime_window 子进程方案不同）

工作台本身就是主进程，不另开子进程：

```
主进程（jarvis --gui / --talk）
    ├─ 主线程：pywebview 窗口（Windows：frameless + transparent + 工作区铺满）
    ├─ ChatEngine 工作线程（独立 asyncio 循环）
    │     ├─ QueryLoop 文本对话（懒装配，首次 send 才初始化）
    │     └─ RealtimeTalk 实时双工（独立线程）
    ├─ MetricsCollector 采集线程（2 秒推 CPU/内存/磁盘）
    └─ SingleInstanceGuard（端口 47812 + 锁文件心跳）
```

#### 无边框透明窗口（Windows 专属机制）

实机反馈白底后定位的根因与修复：

- **根因**：pywebview 的 `transparent=True` 只把 WebView2 控件底色设透明，宿主 WinForms Form 仍是不透明底色（#F0F0F0），桌面透不出来。
- **修复**：Windows 下建窗改 `frameless=True + transparent=True`，尺寸用 `SystemParametersInfoW(SPI_GETWORKAREA)` 取工作区（避开任务栏；WinForms 的 maximized 与 AllowTransparency 互斥）；窗口 shown 后延迟 0.3 秒经 `form.Invoke` 打补丁：`AllowTransparency=True`（WS_EX_LAYERED，仅无边框可用）+ `BackColor=Color.Transparent`，实现像素级透明。
- **自绘标题栏**：无边框后无系统按钮，页面顶部自绘标题栏（`#title-drag` 带 `.pywebview-drag-region` 整条拖动），最小化/关闭两按钮经 `api.window_minimize / window_close` 转给主进程。不提供全屏：启动即铺满工作区，真全屏会盖住任务栏（用户实测拍板移除）。
- **任务栏图标**：窗口图标用深蓝实底版 `~/.jarvis/jarvis_window.ico`（与桌面图标同图案；透明底在任务栏会发白）。`AllowTransparency` 分层窗口下 `Form.Icon` 在任务栏不可靠，`WM_SETICON` / 窗口类图标（GCL）实测也无效——Windows 10 任务栏真正按 **AppUserModelID** 显示图标：窗口启动前经 `win32_icon` 注册进程 AUMID（`AceFelix.JARVIS.Workbench`）+ HKCU 注册表图标映射，桌面/自启快捷方式同步写入同一 AUMID 对齐，任务栏即显示深蓝反应炉图标。
- **非 Windows 兜底**：常规最大化 + 深色底（透明补丁依赖 WinForms，其他平台不做）。

#### 双向队列通信（沿用 realtime_window 模式）

- 前端→后端：指令队列（send/load_session/new_session/switch_model/start_talk/stop_talk/answer_user）
- 后端→前端：事件队列 `{"type","payload"}`，JS 每 50ms 轮询 `poll_events`
- `WorkbenchUI`（UIProtocol 适配）/ `WorkbenchRealtimeUI`（实时事件扩展）把引擎调用转为事件；`ask_user` 用 `threading.Event` 跨线程握手回填

#### 单实例与召唤

绑定固定端口 `127.0.0.1:47812`（**不能设 SO_REUSEADDR**，Windows 下会导致双进程同绑一端口）：绑定成功 = 首个实例（启监听，任意连接触发聚焦回调）；失败 = 已有驻留实例，发 FOCUS 后退出。锁文件 `~/.jarvis/workbench.lock`（PID + 5 秒心跳）兜底诊断。

### 引擎懒装配与 MCP 接入

启动后台预热（2026-09 优化，见 [mcp-prewarm-first-send.md](../fixlogs/mcp-prewarm-first-send.md)）：
引擎线程起跑即后台 `_prewarm()`：`build_default_registry()` → `registry_hook` →
`_connect_mcp`（实测 7 server 并发约 9s），把 MCP 连接耗时装进启动空窗；
首条消息的 `_ensure_session()` 等 `_registry_ready` 后复用预热 registry，
不再同步等 MCP（预热窗口内发消息也只是先少 MCP 工具聊，工具连上自动补挂，
与 harness 后台加载同口径）；预热失败降级回同步装配兜底。

`_ensure_session()`（首次 send 时）其余顺序对齐 `main.repl()`：
provider → 复用预热 registry（兜底才现建 + hook + MCP）→ **ToolSearch 注册**
（`tools_deferred_loading=true` 时把钥匙工具 `ToolSearchTool` 注册进 registry，
`build_system_prompt` 之前）→ harness 后台加载 → 系统提示词（含延迟工具摘要，MCP 工具在列）→ QueryLoop。
client 引用保留在 `_mcp_client` 防 GC 断连。2026-09 修复为 workbench/serve 路径
补上该接入步骤（此前遗漏导致桌面壳永远缺 MCP 工具，如 `mcp__amap-maps__*`），
见 [serve-mcp-truncation-fix.md](../fixlogs/serve-mcp-truncation-fix.md)。

> **延迟加载 = 注册 + 钥匙两件事**：MCP/harness/GUI 等工具 `deferred=true`，初始不发给

### 模型热切换（2026-09）

`models.select` 原先只写 `~/.jarvis/models.toml` 的 `last_model`（由 `load_settings` 在
**进程启动时**应用一次），引擎不换 provider、QueryLoop 也不换模型，而 `list_models` 的
`current` 取自启动快照 —— 表现为「桌面壳选了新模型，列表仍标旧模型为当前、切换要重启
才生效」。现改为写盘成功即入队 `{"cmd": "switch_model", "name": …}`：

- `WorkbenchAPI.set_model` 写盘成功后 `_post` 引擎指令，入队即回执（不等落地，落地由
  事件回执）；
- 引擎线程在自己的 asyncio 循环里 `_dispatch` →
  [model_switch.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/ui/workbench/model_switch.py)：
  复用 REPL `/model` 的 provider 构造（`model_manager._build_switched_provider`，按
  「当前 provider 端点快照」决定重建还是复用），`QueryLoop.switch_model` 就地换
  `_provider` / `_model`（**不**重建 loop：会话 token 累计、思考模式覆盖、消息上下文全保留），
  旧 provider `close()` 释放 HTTP client；
- 端点比较基准是引擎留存的 `_provider_settings`（装配/切换时更新），不能用启动 settings ——
  否则「自定义 → 内置 → 自定义」往返会误判为可复用、把 provider 连回错误端点；
- 切换在指令队列里串行：正有一轮回复在跑时，它在回复结束后落地（无「半轮换模型」竞态，
  也不打断流式输出）；
- 会话未装配时只记 `_model_override`（不因一次切换提前触发 MCP 连接 + 提示词生成的重型
  装配），`_ensure_session` 装配末尾补落地 —— 首个 send 就用上用户刚选的模型；
- 落地推 `model_switched`（payload `{model}`）、provider 构造失败推 `warn` 且不推事件
  （前端「待生效」标记保留，可重试）；`list_models` / `get_cost` / `get_state` 的模型与厂
  字段改取 `engine.current_model` / `current_vendor`，跟随热切换。

桌面壳侧配套：`model_switched` → 清「待生效」标记 + 刷模型列表/用量/状态，成功提示
由引擎 `info` 事件上屏（壳不本地弹，避免双气泡）。语音音色仍为「下次语音会话生效」
（不热切换运行中的语音会话），但 `voices.select` 已与终端 `/tts-voice` 同口径：立即写盘
并在音色-模型不兼容时自动联动 `tts_model`（见下文「音色管理」）。

## 四、实时聊天独立窗口架构（realtime_window，❌ 2026-09 已退役删除）

> 保留理由：父子进程方案与 pywebview 主线程约束的结论仍适用于任何后续窗口形态。

### 父子进程模型

```
父进程（daemon 或 CLI）
    │
    ├─ RealtimeTalkWindow (控制器)
    │   ├─ standalone=True  → 子进程自己跑 RealtimeTalk
    │   └─ standalone=False → 父进程跑 RealtimeTalk，子进程只渲染
    │
    └─ multiprocessing.spawn → 子进程
            ├─ _FrontendWindow (pywebview 主线程)
            ├─ JSBridge (Python ↔ JS 桥接)
            └─ RealtimeTalk 线程（standalone=True 时）
```

**为什么用 multiprocessing**：
- pywebview 必须在主线程运行，用独立子进程承载窗口生命周期最干净
- 子进程主线程跑 webview，通过队列通信

|---|---|
| `window.py` | 父进程窗口控制器（单例管理） |
| `process.py` | 子进程入口 + 前端窗口 + JSBridge |
| `bridge.py` | WebviewRealtimeTalkUI 实现 |
| `assets/reactor.js` | 方舟反应炉粒子动画 |
| `assets/app.js` | 前端事件处理 |

## 七、外部前端接入（serve 模式）

`--serve` 是 headless API 服务模式：不渲染任何本地 UI，把与工作台**完全相同**的引擎零件经 WebSocket 暴露给外部前端（首个消费者是 jarvis-desktop —— 独立仓库的 Electron 桌面壳）。它对齐 dsh-desktop 的「上下游分离」原则：壳不重写 Agent 运行时，只管桌面宿主能力。

### 与工作台引擎层的关系（复用 vs 换宿主）

serve 与退役前的 `--gui` 工作台共用同一套零件，唯一差异是**宿主**：历史工作台用 pywebview 在本进程渲染，serve 用 `DesktopBridgeServer` 把事件流推到 WS，由 jarvis-desktop 桌面壳渲染。工作台引擎层现役，窗口壳已退役。

| 零件 | 工作台（`--gui`，❌ 2026-10 已退役） | serve（`--serve`，现役） |
|---|---|---|
| ChatEngine（指令分发/懒装配/会话持久化） | ✅ | ✅ 同一份 |
| WorkbenchAPI（能力口径） | pywebview `js_api` | WS 指令处理器表 |
| MetricsCollector（CPU/内存/磁盘） | 2 秒推事件队列 | 2 秒推 WS |
| ProactiveHub（每日简报/提醒/截止日期） | ✗（本期不接） | ✅ 到期推 `proactive_notify` |
| 宿主/传输 | pywebview 窗口 + 队列轮询 | WebSocket（token 认证） |
| 绑定 | 单实例端口 47812 | `127.0.0.1` + 随机端口 |

### 进程契约（供外部宿主实现）

- **就绪握手**：装配完成、事件泵启动后，向 stdout 打印**单行** JSON（[app.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/app.py) 的 `_serve_main`）：
  ```json
  {"type": "jarvis-serve-ready", "port": <ws>, "http_port": <http>, "token": "<hex>", "pid": <int>}
  ```
  Electron 主进程逐行读 stdout、解析此行拿到端口与 token。
- **每连接首帧**：`init` 事件由 `DesktopBridgeServer._on_client_connected` 在每条新 WS
  连接认证通过后直发（payload 同 `state.get`）。启动期一次性 broadcast 在无在线
  客户端时会被 `broadcast` 静默丢弃（此刻桌面壳尚未连上），首帧必须按连接推送，
  否则桌面壳首屏七路刷新（含设置面板 `settings.get` 回填）永不触发；断线重连
  同由该钩子覆盖（见 `docs/fixlogs/serve-init-lost-before-connect.md`）。
- **停机信号**：独立守护线程监视 stdin 直到 EOF（父进程退出/杀管道时触发），或 `SIGINT`；随后优雅停机（先 `hub.stop()` 停主动播报避免停机中再投事件，再 `server.stop()` 关传输层与事件泵，最后停 metrics、engine）。
- **绑定收敛**：仅 `127.0.0.1` + 系统分配随机端口，**不对局域网暴露**（与手机协同桥接的 `0.0.0.0` + 固定端口刻意区分）。
- **依赖降级**：`websockets` 已升级为核心依赖（2026-09 起随 pip install 自动安装）；仍保留缺失降级：import 失败时 `run_serve` 返回退出码 3（历史上工作台缺 pywebview 同样返回退出码 3；可选依赖组 `realtime_ui` 已随窗口壳退役从 `pyproject.toml` 移除）。

### 协议契约（唯一来源）

指令/事件 schema 定义在 [protocol.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/protocol.py)，jarvis-desktop 侧 TS 镜像在其 `src/shared/contracts.ts`，两边改动必须同步。

- 指令（客户端→服务端）：`{"type": "<cmd>", ...params}`，51 条桌面指令（与 `protocol.py` 的 `CMD_` 常量数一致）。
- 事件（服务端→客户端）：`{"event": "<name>", "data": <payload>}`，与手机 PWA 桥接协议同构。
- 回执（request/response 型指令）：`{"event": "reply", "data": {"type", "ok", "result" | "error"}}`。
- 未注册指令：回 `ok=false` 失败回执（**不静默忽略**）。客户端按回执等待，静默只会让新指令对旧后端表现为「回执超时」（桌面壳 15s）且看不到原因；缺 `type` 字段同样回失败回执（分发层 `BridgeServer._handle_ws` 统一处理，见 `docs/fixlogs/unknown-command-silent-drop.md`）。

### 命令处理器表（BridgeServer 分发重构）

`DesktopBridgeServer` 继承手机协同的 `BridgeServer` 复用传输层（HTTP + WS、token 认证、broadcast、客户端管理），但完全接管指令分发：`message` 改道引擎指令队列（结果经事件泵以流式事件返回，回执仅确认入队），其余 29 条经 `_register_rpc` 注册为同步取值型 handler（能力口径与 `WorkbenchAPI` 一一对齐；`sessions.{new,rename,delete}` / `talk.*` / `voice.*` 为入队即返型（api `_post` 入引擎队列，回执仅确认，结果走 `session_new` / `session_renamed` / `session_deleted` 等事件）；`reply.abort` 直调引擎线程安全取消不入队；`proactive.ack` 例外，透传给可选注入的 `ProactiveHub`）；手机 PWA 旧协议（`query`/`abort`）行为不变、向后兼容。分发层兜底：`_ws_handlers` 未命中的 type（含缺 `type` 字段）由 `BridgeServer._send_reply_error` 回 `ok=false` 失败回执，错误文案提示「后端不支持指令 X（后端进程可能未加载最新代码，请重启后端后重试）」——旧的「静默忽略」行为已废除（手机协同模式下同样生效，PWA 不消费 `reply` 事件故无影响）。事件泵 `_pump_loop` 每 50ms 轮询引擎事件队列，将 `{"type", "payload"}` 原样 broadcast 为 `{"event", "data"}` 给所有已连 WS 客户端（与 workbench 前端 poll 节奏一致）。

### 斜杠命令透传与补全目录（slash.exec / slash.commands + slash_bridge，2026-10）

终端 45 个斜杠命令（`agent/commands/router.py`）此前无法在桌面壳使用：引擎

- **链路**：桌面 RPC → `WorkbenchAPI.exec_slash`（形态校验后入队 `slash_exec`）→
  `ChatEngine._dispatch`（仅 2 行路由，engine 已超大体量、逻辑全部外置）→

  cost/c/diff/doctor/tools/mcp/skills/memory/plugin(s)）；桌面已有原生控件的（mode/
  think/model/sessions/rewind…）不透传防双入口；引擎无多 Agent 运行时，/agents /
  /tasks 不放行；白名单外命中已安装技能（`/<skill-name>`）照常执行：持与手机/微信
  共用的 `_query_lock` 串行、挂 `_send_task`（可被 `reply.abort` 停止）、轮后
  `_after_turn` 落盘，对话流事件照常渲染。测试见 `tests/ui/test_workbench_slash.py`。
- **补全目录（`slash.commands`，第 47 条只读指令，2026-10）**：`slash_bridge.build_desktop_commands`
  返回桌面可执行命令目录 `[{name, description, source}]`，三类 `source`：`passthrough`

  必然可执行。`WorkbenchAPI.list_slash_commands` 只读直返不入队（`agent.ui.cli` 惰性 import

  - **plugins**：`list` / `search` / `install` / `uninstall` / `enable` / `disable`——
    `PluginManager(marketplace_url=..., marketplace_local=...)`；
  - **harness**：`list_installed` / `market` / `install` / `uninstall` / `enable` / `disable`
    （`agent.cli_anything` 与 `agent.cli_anything.market`）。
- **MCP 禁用态落盘（新文件 `~/.jarvis/mcp_disabled.json`）**：MCP 原无「禁用」概念，
  且 `mcp.json` 可能含明文 token，直接改风险高。故新增独立禁用名单文件
  （`mcp_client.mcp_disabled_path/load_mcp_disabled/save_mcp_disabled`），
  `connect_mcp` 连接时据此过滤被禁用项——`mcp.json` 不动。
- **跨线程竞态规避**：harness 的写操作涉及 registry，径直改引擎活动 registry 有跨线程
  竞态风险，故写操作走一次性临时 registry（`build_default_registry()`），列表靠磁盘扫描。
- **阻塞 IO**：插件 / harness 的 git 克隆安装为阻塞 IO，服务端以 `asyncio.to_thread` 承载，
  不冻事件循环（同 `email.send` 口径）。
- **契约同步**：`protocol.CMD_EXTENSIONS = "extensions.exec"`（第 51）已加入
  `DESKTOP_COMMANDS`（50→51）；TS 镜像契约（`ExtensionCategory` / `ExtensionEnvelope<T>` /
  `McpServerItem` / `ToolItem` / `SkillItem` / `PluginItem` / `HarnessItem` 等）在 jarvis-desktop
  `src/shared/contracts.ts`。测试见 `tests/ui/test_workbench_extensions.py`（分发守卫 +
  MCP 全动作 + tools/skills + plugins + harness，全 hermetic）与

## 八、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 终端 UI | Rich + prompt_toolkit | 美观 + 补全 |
| 图形化窗口宿主 | 独立仓库 jarvis-desktop（Electron） | 本仓库只做引擎与 headless 后端；两套前端并存属重复建设（2026-10 决策，见 [`workbench-gui-retired`](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/docs/fixlogs/workbench-gui-retired.md)） |
| 引擎装配位置 | serve 进程内（引擎工作线程 + 事件泵）；历史上也曾内嵌于窗口主进程 | 单进程承载多能力，免子进程管理 |
| 外部前端接入 | `--serve` headless WS（复用工作台引擎层） | 壳不重写运行时，上下游分离 |
| 窗口 UI（历史） | pywebview + Canvas | 跨平台 + 动画（已随窗口壳退役） |
| 实时窗口父子进程（历史） | multiprocessing | pywebview 要主线程（已改为纯终端 / 桌面壳音频桥） |
| 通信（历史） | 队列 + 轮询 | 简单可靠（serve 已改 WS 事件流） |
| 单例窗口（历史） | 是 | 避免重复占用麦克风（现由语音互斥锁 + 桌面壳单实例承担） |
| 启动动画 | 可跳过 | 非TTY会乱码 |
