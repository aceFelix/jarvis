## 三、三栏工作台（workbench）

2026-08 一期落地：单窗口三栏（左：模式/历史/模型/音色三面板切换；中：文本对话气泡流；右：CPU/内存/磁盘指标），透明背景 + 方舟反应炉淡蓝波纹，取代原托盘遥控形态，成为桌面图标宿主。

### 进程模型（与 realtime_window 子进程方案不同）

工作台本身就是主进程，不另开子进程：

```
主进程（jarvis --gui / --talk）
    ├─ 主线程：pywebview 窗口（Windows：frameless + transparent + 工作区铺满）
    ├─ ChatEngine 工作线程（独立 asyncio 循环）
    │     ├─ QueryLoop 文本对话（懒装配，首次 send 才初始化）
    │     └─ RealtimeTalk 实时双工（独立线程）
    ├─ MetricsCollector 采集线程（2 秒推 CPU/内存/磁盘）
    └─ SingleInstanceGuard（端口 47812 + 锁文件心跳）
```

### 无边框透明窗口（Windows 专属机制）

实机反馈白底后定位的根因与修复：

- **根因**：pywebview 的 `transparent=True` 只把 WebView2 控件底色设透明，宿主 WinForms Form 仍是不透明底色（#F0F0F0），桌面透不出来。
- **修复**：Windows 下建窗改 `frameless=True + transparent=True`，尺寸用 `SystemParametersInfoW(SPI_GETWORKAREA)` 取工作区（避开任务栏；WinForms 的 maximized 与 AllowTransparency 互斥）；窗口 shown 后延迟 0.3 秒经 `form.Invoke` 打补丁：`AllowTransparency=True`（WS_EX_LAYERED，仅无边框可用）+ `BackColor=Color.Transparent`，实现像素级透明。
- **自绘标题栏**：无边框后无系统按钮，页面顶部自绘标题栏（`#title-drag` 带 `.pywebview-drag-region` 整条拖动），最小化/关闭两按钮经 `api.window_minimize / window_close` 转给主进程。不提供全屏：启动即铺满工作区，真全屏会盖住任务栏（用户实测拍板移除）。
- **任务栏图标**：窗口图标用深蓝实底版 `~/.jarvis/jarvis_window.ico`（与桌面图标同图案；透明底在任务栏会发白）。`AllowTransparency` 分层窗口下 `Form.Icon` 在任务栏不可靠，`WM_SETICON` / 窗口类图标（GCL）实测也无效——Windows 10 任务栏真正按 **AppUserModelID** 显示图标：窗口启动前经 `win32_icon` 注册进程 AUMID（`AceFelix.JARVIS.Workbench`）+ HKCU 注册表图标映射，桌面/自启快捷方式同步写入同一 AUMID 对齐，任务栏即显示深蓝反应炉图标。
- **非 Windows 兜底**：常规最大化 + 深色底（透明补丁依赖 WinForms，其他平台不做）。

### 双向队列通信（沿用 realtime_window 模式）

- 前端→后端：指令队列（send/load_session/new_session/start_talk/stop_talk/answer_user）
- 后端→前端：事件队列 `{"type","payload"}`，JS 每 50ms 轮询 `poll_events`

## 四、实时聊天独立窗口架构（realtime_window）

### 父子进程模型

```
父进程（daemon 或 CLI）
    │
    ├─ RealtimeTalkWindow (控制器)
    │   ├─ standalone=True  → 子进程自己跑 RealtimeTalk
    │   └─ standalone=False → 父进程跑 RealtimeTalk，子进程只渲染
    │
    └─ multiprocessing.spawn → 子进程
            ├─ _FrontendWindow (pywebview 主线程)
            ├─ JSBridge (Python ↔ JS 桥接)
            └─ RealtimeTalk 线程（standalone=True 时）
```

**为什么用 multiprocessing**：
- pywebview 必须在主线程运行，用独立子进程承载窗口生命周期最干净
- 子进程主线程跑 webview，通过队列通信

class RealtimeTalkWindow:
    """父进程中的实时聊天窗口控制器。

    管理一个子进程中的 webview 窗口。同一父进程生命周期内
    只维护一个子进程/窗口实例。
    """
    def __init__(self, on_close=None, *, standalone=True):
        self._config = {}
        self._standalone = standalone
        ...

    def set_config(self, config):
        """设置 RealtimeTalk 配置（api_key/model/voice/ws_url）。"""
        self._config = config

    def show(self):
        """启动子进程显示窗口。"""

**单例行为**：
- 宿主（REPL `/talk`）生命周期内只维护一个窗口（CLI `--talk` 已合并进工作台，不再走此路径）
- 重复唤起只聚焦已有窗口，不新建

### standalone 模式

| 模式 | standalone=True | standalone=False |
|---|---|---|
| **用途** | REPL `/talk` 独立入口 | 宿主嵌入（历史 daemon，已下线） |
| **RealtimeTalk 运行在** | 子进程 | 父进程 |
| **子进程职责** | 渲染 UI + 跑 RealtimeTalk | 只渲染 UI |
| **配置传递** | `set_config()` 传给子进程 | 父进程直接用 |

**为什么 standalone=True**：REPL `/talk` 时父进程是 REPL，不能阻塞。子进程自己跑完整实时对话，父进程只等窗口关闭。

class JSBridge:
    """暴露给前端 JS 调用的 Python API。"""

    def poll_events(self) -> list[dict]:
        """JS 轮询获取 Python 端产生的事件。"""
        # 返回 [volume/status/transcript/...] 事件列表

        """用户点击"结束"按钮 → 关闭窗口。"""

### WebviewRealtimeTalkUI

## 七、外部前端接入（serve 模式）

`--serve` 是 headless API 服务模式：不渲染任何本地 UI，把与工作台**完全相同**的引擎零件经 WebSocket 暴露给外部前端（首个消费者是 jarvis-desktop —— 独立仓库的 Electron 桌面壳）。它对齐 dsh-desktop 的「上下游分离」原则：壳不重写 Agent 运行时，只管桌面宿主能力。

### 与工作台的关系（复用 vs 换宿主）

serve 与 `--gui` 工作台共用同一套零件，唯一差异是**宿主**：工作台用 pywebview 在本进程渲染，serve 用 `DesktopBridgeServer` 把事件流推到 WS。

| 零件 | 工作台（`--gui`） | serve（`--serve`） |
|---|---|---|
| ChatEngine（指令分发/懒装配/会话持久化） | ✅ | ✅ 同一份 |
| WorkbenchAPI（能力口径） | pywebview `js_api` | WS 指令处理器表 |
| MetricsCollector（CPU/内存/磁盘） | 2 秒推事件队列 | 2 秒推 WS |
| ProactiveHub（每日简报/提醒/截止日期） | ✗（本期不接） | ✅ 到期推 `proactive_notify` |
| 宿主/传输 | pywebview 窗口 + 队列轮询 | WebSocket（token 认证） |
| 绑定 | 单实例端口 47812 | `127.0.0.1` + 随机端口 |

### 进程契约（供外部宿主实现）

- **就绪握手**：装配完成、事件泵启动、投递 `init` 事件后，向 stdout 打印**单行** JSON（[app.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/app.py) 的 `_serve_main`）：
  ```json
  {"type": "jarvis-serve-ready", "port": <ws>, "http_port": <http>, "token": "<hex>", "pid": <int>}
  ```
  Electron 主进程逐行读 stdout、解析此行拿到端口与 token。
- **停机信号**：独立守护线程监视 stdin 直到 EOF（父进程退出/杀管道时触发），或 `SIGINT`；随后优雅停机（先 `hub.stop()` 停主动播报避免停机中再投事件，再 `server.stop()` 关传输层与事件泵，最后停 metrics、engine）。
- **绑定收敛**：仅 `127.0.0.1` + 系统分配随机端口，**不对局域网暴露**（与手机协同桥接的 `0.0.0.0` + 固定端口刻意区分）。
- **依赖降级**：`websockets` 已升级为核心依赖（2026-09 起随 pip install 自动安装）；仍保留缺失降级：import 失败时 `run_serve` 返回退出码 3（与工作台缺 pywebview 退出码 3 同口径）。

### 协议契约（唯一来源）

指令/事件 schema 定义在 [protocol.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/protocol.py)，jarvis-desktop 侧 TS 镜像在其 `src/shared/contracts.ts`，两边改动必须同步。

- 指令（客户端→服务端）：`{"type": "<cmd>", ...params}`，20 条桌面指令。
- 事件（服务端→客户端）：`{"event": "<name>", "data": <payload>}`，与手机 PWA 桥接协议同构。
- 回执（request/response 型指令）：`{"event": "reply", "data": {"type", "ok", "result" | "error"}}`。

### 命令处理器表（BridgeServer 分发重构）

`DesktopBridgeServer` 继承手机协同的 `BridgeServer` 复用传输层（HTTP + WS、token 认证、broadcast、客户端管理），但完全接管指令分发：`message` 改道引擎指令队列（结果经事件泵以流式事件返回，回执仅确认入队），其余 17 条经 `_register_rpc` 注册为同步取值型 handler（能力口径与 `WorkbenchAPI` 一一对齐；`talk.*` / `voice.*` 为入队即返型（api `_post` 入引擎队列，回执仅确认）；`reply.abort` 直调引擎线程安全取消不入队；`proactive.ack` 例外，透传给可选注入的 `ProactiveHub`）；手机 PWA 旧协议（`query`/`abort`）行为不变、向后兼容。事件泵 `_pump_loop` 每 50ms 轮询引擎事件队列，将 `{"type", "payload"}` 原样 broadcast 为 `{"event", "data"}` 给所有已连 WS 客户端（与 workbench 前端 poll 节奏一致）。

### 主动播报接线（ProactiveHub）

2026-08 下线常驻托盘架构（提交 `59f746a`）时，主动感知套件（`agent/core/daemon/` 下 Scheduler / ProactiveEngine / DeadlineTracker，含单测）整体休眠，提交信息明确「等待 GUI 接线」。[hub.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/hub.py) 的 `ProactiveHub` 即桌面壳的接线体：

- **装配**：`Scheduler`（秒级轮询，持久化 `~/.jarvis/schedule.json`）+ `ProactiveEngine`（每日简报/截止日期）+ `DeadlineTracker`，配置沿用 settings 的 `briefing_*` / `deadline_*` 字段；日历源与系统监控本期不接（传 None 优雅降级）。
- **通道换宿**：老 `NotificationMixin` 的三通道（终端日志 + 托盘通知 + 待机 TTS）换成单一 `proactive_notify` 事件（payload `{kind, title, text, task_id}`，kind = briefing/reminder/deadline），经事件泵推给桌面壳渲染为聊天气泡 + 系统通知。TTS 语音播报二期再接（事件已带全文，届时加通道不改协议）。
- **提醒工具挂载**：`ChatEngine` 新增 `registry_hook` 可选参，serve 宿主在钩子里调 `register_schedule_tools` / `register_deadline_tools` 共享 hub 内部的 Scheduler / DeadlineTracker 单例，对话里说“提醒我”即可创建任务（workbench 宿主不传钩子，行为零变化）。
- **与常驻语义的差异**：serve 随桌面壳启停，播报仅在运行期间生效。补救链：Scheduler 自带错过补偿（一次性任务 ≤1 小时）+ hub 的简报补播窗口（启动时今天 `briefing_time` 已过且 ≤ `briefing_catchup_window_min` 分钟、默认 120→延迟 5 秒补播一次，等桌面壳 WS 连上）。
- **已读回执**：桌面壳收到 reminder 类事件且窗口可见时自动回 `proactive.ack`（task_id），经 hub 落到 `Scheduler.acknowledge` 停止升级重发。

### 半双工语音接线（/voice 解耦桥接）

2026-09 二期把 `/voice`（STT→LLM→TTS 半双工循环）从 RichCLI 解耦，照 `/talk` 模式经 serve 桥接进 jarvis-desktop：

- **解耦**：`agent/voice/voice_events.py` 定义 `VoiceSessionEvents` 回调协议（`on_state`/`on_user_transcript`/`on_ai_text_delta`/`on_ai_text`/`on_info`/`on_error`）+ `VoiceEventsBase` 空实现基类；`voice_loop(events, settings, loop, ctx, *, stop_event, interrupt_event)` 不再收 `ui: RichCLI`，打断改监听外部传入的 `interrupt_event`（不自 new 键盘 watcher）。
- **双适配器**：REPL 走 `agent/voice/repl_adapter.py::RichCLIVoiceAdapter`（事件映射回 `ui.info/warn/error` + stdout 识别进度，键盘 ESC watcher 挂接 `interrupt_event`，行为保底）；serve 走 `engine.ServeVoiceAdapter`（事件转 `voice_*` WS 事件外抛）。
- **引擎桥接**：`_handle_start_voice` 起独立 asyncio task 跑 `voice_loop`，与 `/talk` 互斥（start_voice 先停 talk，start_talk 先停 voice）；麦克风 `_BargeInWatcher`（RMS）挂接 `interrupt_event`（播报中开口自动打断），桌面壳 `voice.interrupt` 指令另置位同一 event（按钮 + 麦克风双通道）。阻塞音频 I/O 在 `voice_loop` 内经 `asyncio.to_thread` 工作线程跑，保证聆听/播报期间引擎指令循环仍能即时消费 `voice.stop/interrupt`（修复桌面壳按钮无响应，见 jarvis `docs/fixlogs/voice-stop-unresponsive-fix.md`）。
- **音频本地**：STT 录音 / TTS 播放（`StreamTTSPlayer`）留在 serve 子进程本机 pyaudio（与桌面壳同机出声），**不向桌面壳传音频流**；桌面壳只做遥控器 + 状态/文字显示。指令 `voice.{start,stop,interrupt}`，事件 `voice_started/stopped/state/user_transcript/ai_text_delta/ai_text`。

### 停止回复与 serve 卡死修复（2026-09）

- **子进程 stdin 隔离**：Bash 工具（`agent/tools/bash.py`）与沙箱执行器（`agent/core/sandbox/executor.py`）创建子进程时显式 `stdin=DEVNULL`。根因：serve 宿主的 stdin 是 Electron 永不关闭的管道且有 `_watch_stdin` 线程阻塞读，MSYS2 bash 继承该管道后 Cygwin 初始化探测 stdin 句柄时挂在父进程同句柄的 pending 阻塞读上 → bash 永不退出、`communicate()` 吃满超时、recovery 重试再挂 → 工具调用永久卡死（REPL stdin 是 tty 故不触发）。复盘见 [docs/fixlogs/serve-bash-hang-fix.md](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/docs/fixlogs/serve-bash-hang-fix.md)。
- **询问异步化**：`WorkbenchUI` 新增 `ask_user_async`（`asyncio.to_thread` 等待回答），orchestrator 权限询问与 error_recovery 询问站点优先走异步版——同步版 `ask_user` 在 serve 宿主下阻塞的是引擎事件循环线程，同环串行的 `_command_loop` 无法消费 `answer_user` → 自死锁至 600s 超时。
- **停止回复（`reply.abort`，第 18 条指令）**：`ChatEngine.abort_current_reply()` 经 `loop.call_soon_threadsafe(task.cancel)` 线程安全取消 `_handle_send` 记录的 `_send_task`（不入指令队列：队列被当前 send 轮次串行占用，入队会自死锁）。CancelledError 沿流式/工具层优雅退出（Bash 子进程被 kill 回收不留孤儿），`_handle_send` 的 finally 仍发 `assistant_done` 让前端收尾，`_command_loop` 捕获后发 info「已停止回复」继续服务。桌面壳发送按钮 busy 时变「■ 停止」，再点即发此指令。
- **右栏数据源（`schedule.list` / `cost.get` / `state.get` 扩 MCP，第 19-20 条指令）**：桌面壳右栏五区块的后端支撑——`schedule.list` 经 server 持有的 `ProactiveHub` 读 `Scheduler.list_pending()`（提醒）与 `DeadlineTracker.list_active()`（截止日期，含 `days_left`），hub 未装配返回空列表；`cost.get` 经 `ChatEngine` 新增只读属性 `session_usage`（`QueryLoop.session_usage` 快照，口径同 REPL `/cost`）/ `dialog_count` / `message_count`；`state.get` 新增 `mcp` 键（引擎 `_connect_mcp` 写入的连接快照 `{connected, failed, tools}`，未启用为 null）。

## 八、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 终端 UI | Rich + prompt_toolkit | 美观 + 补全 |
| 工作台 | 主进程内嵌（主线程窗口 + 工作线程引擎） | 单窗口承载多能力，免子进程管理 |
| 外部前端接入 | `--serve` headless WS（复用工作台引擎） | 壳不重写运行时，上下游分离 |
| 窗口 UI | pywebview + Canvas | 跨平台 + 动画 |
| 实时窗口父子进程 | multiprocessing | pywebview 要主线程（历史方案） |
| 通信 | 队列 + 轮询 | 简单可靠 |
| 单例窗口 | 是 | 避免重复占用麦克风 |
| 启动动画 | 可跳过 | 非TTY会乱码 |
