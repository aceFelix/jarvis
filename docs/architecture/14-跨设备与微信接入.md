# 14 - 跨设备与微信接入

> 本文档详解 J.A.R.V.I.S 的两种远程接入渠道：跨设备协同（`/connect-phone`，Bridge 模块）和微信 ClawBot 接入（`/connect-wechat`，WeChat 模块）。

@author aceFelix

---

## 一、概述

J.A.R.V.I.S 支持两种远程接入方式，让用户脱离电脑终端也能与 JARVIS 对话：

| 渠道 | 命令 | 模块 | 协议 | 适用场景 |
|------|------|------|------|----------|
| 手机 PWA | `/connect-phone` | `agent/bridge/` | 局域网 WebSocket | 同一 Wi-Fi 下手机远程操控 |
| 微信 ClawBot | `/connect-wechat` | `agent/wechat/` | 腾讯 iLink Bot API | 任意网络，通过微信聊天对话 |

两者共享同一设计范式：
- **独立线程**运行，不阻塞 REPL 主循环
- **全局单例**管理，一个会话只有一个实例
- **共享 messages**，远程对话与电脑终端看到同一对话历史
- **串行化锁**保护共享 messages 不被并发写入

## 二、跨设备协同（Bridge 模块）

### 2.1 架构

```
┌─────────────┐   HTTP(8765): 静态文件 + /api/config + /upload
│  手机 PWA   │ ───────────────────────────────────────────────┐
│ (index.html)│                                                │
└─────────────┘   WebSocket(8766): 双向通信（token 认证）      │
     │  ↑                                                      │
     ↓  │  event: assistant_text / tool_use / done             │
┌──────────────────────────────────────────────────────────────┐
│                    BridgeServer (电脑端)                       │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────────┐  │
│  │ThreadingHTTP │  │ websockets   │  │ threading.Lock    │  │
│  │Server(线程)  │  │ serve(loop)  │──│ 并发控制:单query  │  │
│  └──────────────┘  └──────────────┘  └───────────────────┘  │
│                                              │              │
│              共享 messages ┌─────────────────┘              │
│                            ▼                                │
│  ┌──────────────┐  ┌──────────────────┐  ┌─────────────┐  │
│  │  BridgeUI    │←─│  ToolContext     │←─│  QueryLoop  │  │
│  │ (UIProtocol) │  │  (plan 权限)     │  │ (daemon共享)│  │
│  └──────────────┘  └──────────────────┘  └─────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 文件结构

```
agent/bridge/
├── __init__.py      # 模块导出（BridgeServer, BridgeUI, BroadcastUI）
├── server.py        # BridgeServer 核心（HTTP + WS + 单例管理）
├── ui.py            # BridgeUI（UIProtocol → WS 事件流）+ BroadcastUI
└── static/
    └── index.html   # PWA 前端（暗色主题单文件）
```

### 2.3 核心流程

1. **启动**：`/connect-phone` → `start_bridge_in_thread()` → 独立线程启动 HTTP + WS 服务
2. **认证**：手机连接 WS 时通过 `?token=xxx` 校验，token 自动生成
3. **对话**：手机发消息 → WS → `_run_query()` → 加锁执行 `QueryLoop.run()` → 流式推送事件回 WS
4. **同屏**：`BroadcastUI` 把电脑端对话同步推送给已连接的手机端
5. **停止**：终端退出或手动调用 `stop_bridge()`

### 2.4 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 权限模式 | `plan`（只读） | 手机端远程操控风险高，写操作需确认 |
| HTTP 服务 | `ThreadingHTTPServer` | 同步简单，独立线程不干扰 asyncio |
| WS 库 | `websockets` | 与 realtime_talk 共用依赖 |
| 并发控制 | `threading.Lock` | 跨线程串行化，保护共享 messages |
| 事件传输 | 线程安全 `queue.Queue` | UIProtocol 回调是同步的，避免跨 loop 问题 |

### 2.5 配置

```toml
[bridge]
http_port = 8765    # PWA 页面端口
ws_port = 8766      # WebSocket 通信端口
token = ""          # 认证 token，留空自动生成
```

## 三、微信 ClawBot 接入（WeChat 模块）

### 3.1 架构

```
┌─────────────┐         ┌──────────────┐         ┌─────────────────────┐
│  微信 APP   │ ←────→  │  腾讯云 iLink │ ←────→  │  agent/wechat/      │
│ (ClawBot)   │         │  (消息中转)   │         │  ilink.py (HTTP)    │
└─────────────┘         └──────────────┘         └─────────┬───────────┘
                                                           │
                                                 ┌─────────▼───────────┐
                                                 │  server.py          │
                                                 │  WeChatBridge       │
                                                 │  (独立线程+单例)    │
                                                 └─────────┬───────────┘
                                                           │
                                                 ┌─────────▼───────────┐
                                                 │  QueryLoop          │
                                                 │  (共享 messages)    │
                                                 └─────────────────────┘
```

### 3.2 文件结构

```
agent/wechat/
├── __init__.py      # 模块导出（WeChatBridge, start/stop/get）
├── ilink.py         # iLink Bot API 客户端（扫码/轮询/收发消息）
├── server.py        # WeChatBridge（消息循环 + 单例 + 24h 重连）
└── ui.py            # WeChatUI（UIProtocol，收集回复文本）
```

### 3.3 iLink Bot API 协议

基于腾讯官方 `@tencent-weixin/openclaw-weixin` 2.x 协议：

**域名**：`ilinkai.weixin.qq.com`

**请求头**（每次请求）：
```
Content-Type: application/json
AuthorizationType: ilink_bot_token
X-WECHAT-UIN: <随机uint32的base64>
iLink-App-Id: bot
iLink-App-ClientVersion: 132099
Authorization: Bearer <bot_token>
```

**核心 API**：

| 端点 | 方法 | 用途 |
|------|------|------|
| `ilink/bot/get_bot_qrcode?bot_type=3` | POST | 获取登录二维码 |
| `ilink/bot/get_qrcode_status?qrcode=xxx` | GET | 轮询扫码状态 |
| `ilink/bot/getupdates` | POST | 长轮询接收消息（hold ~35s） |
| `ilink/bot/sendmessage` | POST | 发送文本消息 |
| `ilink/bot/sendtyping` | POST | 显示/取消"正在输入" |
| `ilink/bot/getconfig` | POST | 获取 typing_ticket |

**sendmessage 必填结构**（缺少字段会静默丢失）：
```json
{
  "msg": {
    "from_user_id": "",
    "to_user_id": "<用户ID@im.wechat>",
    "client_id": "openclaw-weixin-<随机hex>",
    "message_type": 2,
    "message_state": 2,
    "context_token": "<从收到的消息中原样取>",
    "item_list": [{"type": 1, "text_item": {"text": "回复内容"}}]
  },
  "base_info": {"channel_version": "2.4.3", "bot_agent": "jarvis-wechat/1.0.0 (python)"}
}
```

### 3.4 核心流程

```
/connect-wechat
    │
    ▼
ILinkClient.fetch_login_qrcode()
    │ 返回 qrcode + qrcode_img_content
    ▼
终端渲染 ASCII 二维码
    │
    ▼
ILinkClient.wait_login_confirmation()  ← 轮询 get_qrcode_status
    │ 用户扫码 → "scanned" → 确认 → "confirmed"
    │ （可能需配对码 → verify_callback → 终端 input）
    ▼
获得 bot_token → 启动消息循环线程
    │
    ▼
┌─── run_loop() ────────────────────────────────┐
│  while running:                               │
│    result = getupdates(buf)   # 长轮询 35s    │
│    for msg in result.msgs:                    │
│      _handle_message(from_id, ctx_token, text)│
│        ├─ sendtyping(status=1)                │
│        ├─ QueryLoop.run(text, ctx)  # 加锁    │
│        ├─ sendmessage(reply)        # 分段    │
│        └─ sendtyping(status=2)                │
└───────────────────────────────────────────────┘
```

### 3.5 扫码状态机

```
wait → scanned → confirmed (→ 拿到 bot_token)
  │        │
  │        └→ need_verifycode → 输入配对码 → confirmed
  │
  └→ expired → 重新获取二维码（最多 3 次）
  └→ scaned_but_redirect → 切换轮询节点
  └→ binded_redirect → 已连接过，沿用
```

### 3.6 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 权限模式 | `default`（完整能力） | 微信是私人对话，应能用全部工具 |
| HTTP 客户端 | `aiohttp` | 异步、支持长轮询超时控制 |
| 消息共享 | 共享 REPL messages | 与 bridge 一致，多端同一对话 |
| 长消息 | 超 2000 字分段发送 | 微信单条消息有长度限制 |
| 重连 | 24h 到期前终端提醒 | iLink token 有效期 24h，需重新扫码 |
| 并发控制 | `threading.Lock` | 与 bridge 一致，保护共享 messages |

### 3.7 依赖

```toml
[project.optional-dependencies]
wechat = [
    "aiohttp>=3.9.0",    # iLink API HTTP 客户端
    "qrcode>=7.4.0",     # 终端二维码渲染
]
```

安装：`pip install "jarvis-agent[wechat]"`

### 3.8 限制与注意事项

- 仅支持**文本消息**（图片/语音/文件需额外实现 CDN 加密上传）
- 微信版本需 ≥ 8.0.70，设置 → 插件中可看到 ClawBot
- `context_token` 必须使用当前消息中的值，不可复用旧 token
- 每次扫码 bot_id 会变化（iLink 平台设计，正常现象）
- 腾讯保留内容过滤和限速权利，不建议用于核心业务

## 四、两模块对比

| 维度 | Bridge（/connect-phone） | WeChat（/connect-wechat） |
|------|--------------------------|---------------------------|
| 网络要求 | 同一局域网 | 任意网络（走腾讯云中转） |
| 认证方式 | 自动生成 token | 微信扫码（iLink 协议） |
| 权限模式 | plan（只读） | default（完整能力） |
| 流式输出 | 支持（WS 实时推送） | 不支持（等 QueryLoop 完成后一次发送） |
| 消息类型 | 文本 + 图片 | 仅文本 |
| 有效期 | 随终端生命周期 | 24h（需重新扫码） |
| 依赖 | websockets + qrcode | aiohttp + qrcode |
| 合规性 | 自建服务 | 腾讯官方接口，不封号 |

## 六、桌面端接入（2026-10）

终端里 `/connect-phone`、`/connect-wechat` 直接跑在 REPL 主线程上。桌面壳
（`jarvis-desktop`）把同一能力搬进图形界面：输入栏新增一个**跨设备协同下拉按钮**
（取代原 `[LIV]` 实时语音入口，语音在左栏仍有），点选「手机 / 微信」即发起连接，
**二维码内联显示在中间聊天区**。

### 6.1 与终端的关键差异：唯一共享锁

终端模式下 `BridgeServer` / `WeChatBridge` 各自 `threading.Lock()` 自锁，只在本桥接
内串行。桌面模式额外满足一条硬约束：**桌面文本 / 手机 / 微信三通道共享同一会话，
都能发消息但绝不同时发**。做法是把锁提升为**引擎持有的唯一共享 query 锁**
（`ChatEngine._query_lock`），三通道都调度到**引擎自己的 asyncio loop**
（`engine._loop`）执行 `QueryLoop.run` 并抢同一把锁：

| 通道 | 抢锁处 | 执行 loop |
|------|--------|-----------|
| 桌面文本 | `engine._handle_send`（`run_in_executor(acquire)`） | `engine._loop` |
| 手机 PWA | `BridgeServer.run_query` | 注入的 `main_loop=engine._loop` |
| 微信 ClawBot | `WeChatBridge._exec_query` | 注入的 `main_loop=engine._loop` |

`start_bridge_in_thread(..., main_loop, query_lock)` 与 `start_wechat_in_thread(...,
main_loop, query_lock)` 新增这两个入参：桌面 serve 传引擎的 loop 与唯一锁；不传
（终端）则各自默认，行为不变。

### 6.2 装配链路

```
桌面下拉点「手机」
    │ WS RPC phone.connect
    ▼
DesktopBridgeServer → WorkbenchAPI.connect_phone()  # 入队即返回
    │ command_queue: {cmd: connect_phone}
    ▼
ChatEngine._dispatch → remote_bridge.connect_phone(engine)
    │ await engine._ensure_session()          # 拿到 query_loop / ctx
    │ start_bridge_in_thread(main_loop=engine._loop, query_lock=engine._query_lock)
    ▼
emitter.emit("qrcode", {channel:"phone", url})            # 先出二维码，等扫码（不抢跑 connected）
    │  # connected 以「手机 WS 客户端真正接入」为准：由 BridgeServer.on_client_connected
    │  # 回调触发（桥接 HTTP 启动就绪 ≠ 手机已连），杜绝「没扫就显示已连接」
    ▼
emitter.emit("remote_state", {channel:"phone", connected:true})  # 扫码接入后才推
    ▼
桌面 dispatcher → chatStore.addQrcode → 中间聊天区内联二维码卡片
```

连接逻辑集中在 `agent/ui/workbench/remote_bridge.py`（`engine.py` 已较大，按职责拆出）：
`connect_phone / disconnect_phone / connect_wechat / disconnect_wechat`，以及微信登录
worker `_wechat_login_worker`。

**微信登录不占引擎 loop**：终端 `login` 的 `verify_callback` 是阻塞 `input()`（仅在
服务端返回 `need_verifycode` 时才触发）。桌面把 `login` 丢进**独立线程 + 独立 loop**
（`_wechat_login_worker`）；`qrcode_callback` 把登录二维码经 `qrcode` 事件回推。**正常流程
扫上二维码并确认即直接拿到 `bot_token` 登录成功**，无需配对码；因此桌面卡片**不再内联
配对码输入**（手机 / 微信一致，扫上即连）。`engine._wechat_pairing_q` 队列与 `wechat.pairing`
RPC 作为休眠兜底保留（终端 `input()` 仍用同一 verify 机制；桌面若命中 `need_verifycode` 则
刷新二维码重试），全程不冻结引擎指令循环。

**微信 connected 以 `bot_token` 为准**：`_wechat_login_worker` 只有在 `login()` 成功**且**
`bridge.connected`（即 `bool(bot_token)`）为真时才推 `remote_state connected:true` 并启动消息
轮询。`login()` 的 `already_connected`（`binded_redirect`）分支不写 `bot_token`——若照常报
已连接会出现「还没扫码就显示已连接、却收不到消息」的假连接，故此时只 warn 提示重新扫码、
保留二维码。

**入站消息以带来源标记的用户气泡上屏**：手机 / 微信用户发来的消息，早期走 `desktop_ui.info("[微信] …")`
→ 桌面居中系统气泡；现改为 `WorkbenchUI.remote_user_message(channel, text)` 推 `remote_user_message`
事件，桌面按**普通用户气泡（右对齐）**渲染，仅标签改显“微信 / 手机”（`WeChatUI` / `BridgeUI`
均优先调此方法，终端 RichCLI 无此方法则回退 `info` 前缀）。

**每条远端回复各自成气泡**：`assistant_done` 以前仅由引擎本地输入路径（`_handle_send`）发，
微信 query 走 `_query_loop.run` 不经此路径 → 桌面 AI 气泡永不定稿，下一条微信回复会续写同一
气泡。修复：`WeChatUI.end_turn()` 在 `WeChatBridge._exec_query` 跑完 query 后调 `desktop_ui.assistant_done()`
收尾本轮（终端无此方法则 no-op）；前端 `remote_user_message` 处理也会先 `finishAssistant` 兼做防御。

**远端对话即时落盘到电脑**：手机 / 微信与桌面共享同一 `engine._messages`，但落盘（`_after_turn`
→ `session_manager._auto_save`）此前只在桌面本地输入路径触发，纯手机 / 微信对话要到下一次桌面
发消息或切换会话才存盘。修复：`start_bridge_in_thread(..., on_turn_end)` 与 `start_wechat_in_thread(...,
_on_turn_end)` 新增落盘回调入参，桌面 serve 注入 `engine._after_turn`；`BridgeServer.run_query` 与
`WeChatBridge._exec_query` 在 query 结束（释放锁后、引擎 loop 上）各调一次，使每一轮手机 / 微信
对话都即时增量存盘 + 参与标题生成。终端不注入（`None`），沿用自身存盘，行为不变。

**重连二维码总在底部**：二维码卡片此前对「同通道未连接卡片」一律就地更新 url，导致断开重连
时新二维码刷新到历史里那张旧卡片位置（旧卡在断开时被 `setQrcodeConnected(false)` 还原成未连接
态），气泡一多就得往上翻找。修复：`qrcode` 事件加 `fresh` 字段——一次**新连接**首帧 `fresh:true`
（`connect_phone` 直接推，微信登录 worker 首帧推、后续过期重生成帧推 `false`），前端 `addQrcode`
对 `fresh` 先清理该通道旧未连接卡片、再在列表**底部新建**一张，配合既有「新消息自动滚底」，
当前视口即见二维码；`fresh:false` 仍是同一连接内过期刷新的就地更新（不堆叠）。已连接（`已连接`）
历史卡片作为记录保留，不受清理影响。

**任意来源都能停止（发送/停止双态按钮）**：桌面“正在工作”态（`busy`）此前只由本地
`sendMessage` 置位，而手机 / 微信 / 主动任务的轮次不经此路径，导致 jarvis 已在跑工具时
发送按钮仍停在“发送”；且 `reply.abort` 只取消 `_handle_send` 登记的 `_send_task`，对远端
轮次无效。修复三处：① 前端 `dispatcher` 在收到 `assistant_text` / `assistant_thinking` /
`tool_use` 任一活动事件时 `setBusy(true)`（`assistant_done` 统一撤销），使按钮对任意来源都
切为“停止”；② 引擎新增 `_remote_query_begin()`（把 `asyncio.current_task()` 登记为 `_send_task`），
`start_bridge_in_thread` / `start_wechat_in_thread` 新增 `on_query_begin` 入参，桌面 serve 注入该
方法，`BridgeServer.run_query` 与 `WeChatBridge._exec_query` 在拿到 query 锁、即将跑
`query_loop.run` 前各调一次（三通道由 query 锁串行，同一时刻只有一个在跑，登记不互覆），
使 `abort_current_reply` 能取消任意来源的在跑轮次；③ 手机 `BridgeUI.finish()` 补调
`desktop_ui.assistant_done()`（与微信 `WeChatUI.end_turn` 对称），否则手机轮次桌面收不到
`assistant_done`、`busy` 会永久卡住。终端不注入（`None`）/无 `assistant_done` 方法均 no-op，行为不变。

### 6.3 serve RPC / 事件清单

| 方向 | 名称 | 说明 |
|------|------|------|
| RPC | `phone.connect` / `phone.disconnect` / `phone.status` | 手机桥接开关与状态（`{active,url}`） |
| RPC | `wechat.connect` / `wechat.disconnect` / `wechat.status` | 微信登录开关与状态（`{connected}`） |
| RPC | `wechat.pairing` | 休眠兜底：回喂 `{code}` 到 login 线程（桌面已不内联输入，正常扫码无需） |
| 事件 | `qrcode` `{channel,url,fresh?}` | 内联二维码卡片（手机 / 微信共用）；`fresh:true` 新连接底部新建、`false`/缺省过期刷新就地更新 |
| 事件 | `remote_state` `{channel,connected}` | 下拉按钮文案 / 卡片收起联动 |
| 事件 | `remote_user_message` `{channel,text}` | 手机/微信入站消息，桌面渲染为带来源标记的用户气泡 |

桌面重开 / 重连时，`init` 事件触发 `refreshRemote`（`phone.status` + `wechat.status`）
回填按钮连接态；二维码卡片不回放（每次连接现生成）。

### 6.4 前端落地（jarvis-desktop）

- `RemoteConnectMenu.tsx`：输入栏下拉按钮，读 `remoteStore` 决定「连接 / 断开」与徽标。
- `QrcodeCard.tsx`：聊天区内联二维码卡片（`qrcode` npm 画 `url`），手机 / 微信一致扫上即连；
  二维码前景/背景色读皮肤 `--qr-code-*` 变量随主题联动（监听 `data-theme` 重绘）。
- `remote.css`：下拉弹层与内部按钮 `border-radius:0`（硬边，贴合复古 CRT 质感）。
- `remoteStore.ts`：手机 / 微信连接态；`chatStore` 新增 `qrcode` 消息类型。
- `dispatcher.ts`：`qrcode` / `remote_state` 事件路由；`init` 调 `refreshRemote`。
