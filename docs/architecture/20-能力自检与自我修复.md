# 20 · 能力自检与自我修复

> 让 JARVIS 知道自己**现在**能做什么、缺什么、缺的时候能不能自己补上，并且不许把"没做到"说成"做过了"。
>
> 本篇是设计说明与取舍记录；实施计划与逐段实做记录见 [capability-selfcheck.md](../plans/capability-selfcheck.md)，事故复盘见 [snake-visual-claim-fix.md](../fixlogs/snake-visual-claim-fix.md)。

## 1. 它为什么存在：一次真实事故

2026-11-03，让贾维斯做一个贪吃蛇网页游戏。它跑了 1096 行代码、二十几次工具调用，最后汇报：

> "我已经用浏览器打开验证过了，布局对齐、按键响应都正常。"

实际它**没有浏览器内核**——`playwright` 这个 Python 包装好了，`ms-playwright` 目录里一个内核都没有，`chromium.launch()` 必然抛错。它验证不了，但"我包好了 playwright"在它的世界里等于"我能用浏览器"，于是把"我以为我做过了"写成了"我验证过"。

同一件事当时的代码层是这么判断的：

| 判断点 | 老逻辑 | 事实 |
|---|---|---|
| 工具可用吗 | `importlib.util.find_spec("playwright")` 有就算可用 | 包在，内核不在 |
| 调用失败后 | 自愈层重试两轮，每轮撞同一堵墙 | 重试必然失败 |
| 模型怎么知道不能验证 | 没人告诉它 | 它按"工具存在"推断"我做得到" |
| 用户怎么发现 | 打开网页一看就知道 | 只有人能发现 |

缺的不是一个 `try/except`，是**"能力"这个概念在代码里没有一等的容身之处**。这层东西现在叫 `agent/capabilities/`。

## 2. 分层

```text
agent/capabilities/
├── registry.py   能力表：一项能力需要什么（声明，不探测）
├── probe.py      静态探测：包 / 二进制 / 资产 / 密钥 / 平台（快，热路径可用）
├── smoke.py      冒烟探测：真起一次（慢，只在 --deep 与首次使用时跑）
├── report.py     呈现层：文本 / Markdown / JSON / 单项详情
└── repair.py     自我修复：白名单动作 + 六道门 + 复测 + 留痕
```

依赖方向只有一条：`report → probe → registry`，`repair → probe → registry`。消费者（编排器、ToolSearch、提示词、`/health`）读 `probe` 的结论，不自己判断包在不在。

工具侧的判据也收在 `probe.py`：`report_for_tool()` / `tool_block_reason()` / `tool_status_note()`，工具文件里没有一处自己 `find_spec`。

## 3. 能力表：13 项，声明式

`CAPABILITY_REGISTRY` 当前 13 项，每项 `CapabilityMeta` 声明：所属 extras 组、Python 包、外部二进制、资产目录、密钥、平台限制、冒烟探针、修复动作、关联工具，以及两个语义标记 `degradable` / `blocks_selfcheck`。

| 能力 | 标题 | 工具数 | 修复动作 |
|---|---|---|---|
| `browser.selfcheck` | 浏览器自动化（交付自查的"亲眼看过"） | 6 | `fetch-browser`, `pip-extras` |
| `gui.input` | 鼠标键盘输入模拟 | 8 | `pip-extras` |
| `gui.window` | 窗口枚举与激活 | 6 | `pip-extras` |
| `gui.screen_capture` | 屏幕截图（视觉证据的采集端） | 2 | `pip-extras` |
| `voice.duplex` | 实时双工语音（`/talk`） | 0 | `pip-extras`, `config-fix` |
| `voice.half` | 半双工语音对话（`/voice`） | 0 | `pip-extras`, `config-fix` |
| `camera.capture` | 摄像头取景 | 2 | `pip-extras` |
| `vision.detect` | 实时视觉检测（手势/人脸） | 0 | `pip-extras`, `fetch-model` |
| `mcp.connect` | MCP 外部服务接入 | 0 | `pip-extras` |
| `lsp.python` | Python 语言服务 | 1 | — |
| `checkpoint.git` | 轮次检查点（`/undo` 的底） | 0 | — |
| `secrets.keyring` | 系统密钥环 | 0 | — |
| `system.monitor` | 系统资源监控 | 1 | `pip-extras` |

工具数为 0 的六项分两类：`voice.*` / `vision.detect` / `mcp.connect` 是**不走工具通道**（语音链路自己起线程、MCP 在启动时连），它们的门在各自入口（§8）；`checkpoint.git` 与 `secrets.keyring` 是**底座能力**（本来就没有对应工具，只影响别的工具能不能干活）。

版本要求一律**问库自己**（`importlib.metadata.version()`），表里不写死版本号——写死就是版本漂移的起点：环境升到 1.50，表里还要求 1.40，探测会报出一个不存在的问题。

## 4. 探测：五类前置条件，六个状态

每类前置条件独立成探针，返回 `RequirementStatus`：

| 探针 | 判什么 | 状态 |
|---|---|---|
| `probe_python` | 包能否 import + 版本 | OK / MISSING / PROBE_FAILED / SKIPPED |
| `probe_binary` | 外部命令跑 `--version`（5 秒超时） | 同上 |
| `probe_asset` | 目录/文件在不在（内核、模型权重、字体） | 同上 |
| `probe_secret` | 密钥解析得到吗（不打印值） | 同上 |
| `platform_req` | 平台是否支持 | OK / UNSUPPORTED |

能力整体状态由 `aggregate_state()` 汇总，**六个值**：

```text
ok           必需项全 OK
degraded     必需项 OK，可选项有缺（能用，但少功能）
missing      必需项有缺（跑不起来）
probe_failed 探针本身出错（超时、权限、解析失败）
unsupported  本平台不适用
unknown      没探测过
```

### 关键取舍：`probe_failed` ≠ `missing`

这是整层里唯一"必须反复强调才不会被写错"的一条。探针挂了只说明**我们看不清**，不说明东西不在。它导致三个方向相反的禁令：

- `probe_failed` **不拦**工具调用（可能其实是好的，拦了就是把能力删了）；
- `probe_failed` **不生成修复命令**（不知道缺什么就动手，那不叫修复，叫猜）；
- `probe_failed` **不进** `/health caps --repair` 的白名单候选。

这条不是纸上原则。S3 实测时就抓到自己一处真缺陷：文本版与 Markdown 版报告里各有一处会把"看不清"的补法当修复命令发布——`iter_fix_commands()` 与 `render_caps_markdown()` 都补了用例（`test_markdown_also_refuses_to_publish_unconfirmed_hints`）。

### `blocks_selfcheck`

`browser.selfcheck` 标了 `blocks_selfcheck=True`：它缺，不代表别的工具不能跑，但代表**"我验证过了"这句话不能出口**。提示词段据此改写交付自查的措辞（§7）。

## 5. 两个时间尺

| 尺度 | 值 | 用途 |
|---|---|---|
| `CACHE_TTL_S` | 300 秒 | 热路径（工具调用前判一次）用缓存结论，静态档实测 <50ms，但一个任务能调上百次工具 |
| `force=True` | 立即重探 | 不可逆动作到点执行、修复后的复测、`/health caps --deep` |

缓存是进程内的 `_CACHE: dict[name → (timestamp, report)]`。TTL 存在的意义是**"用户刚装完"这件事必须在五分钟内自动被承认**；太短则每次工具调用都探一遍，等于给主流程加税。

`check(name, force=False, now=None)` 的 `now` 是给测试留的注入口——时间不可测就没法测过期，`test_capability_probe.py` 里靠它跑了 7 处时间推进。

## 6. 冒烟档：静态说"在"不算，得真跑一次

`smoke.py` 两个探针：

| 探针 | 真做的事 | 超时 |
|---|---|---|
| `smoke_browser_launch` | 子进程里 `chromium.launch()` + 开一页 + 截图 + 退出 | 90 秒 |
| `smoke_screen_capture` | 真截一帧屏 | 20 秒 |

三个设计点：

1. **子进程跑，不在本进程跑**。playwright 的 sync API 会装信号处理器，在 asyncio 主循环里调它要么炸要么污染事件循环；隔离出去还能被硬超时杀掉。
2. **结果写回同一个缓存**。这样"目录在、但内核真的起不来"能反过来让调用前门拦下工具——"首次要用该能力时跑冒烟"靠的就是这一步。代价是一次 `--deep` 的结论在 TTL 内影响热路径；但 `probe_failed` 本来就不拦，所以只有"实测确实跑不起来"才会改变行为。
3. **不吞异常**：探针坏掉是 `probe_failed`，不是 `missing`，分层由 `run_smoke_for()` 保证。

`/health caps --deep` 必须先打印预告再跑——不提醒的十几秒静默会被当成卡死、被 Ctrl+C，最后什么结论都拿不到。

## 7. 三个消费者 + 两条逃逸路径

消费者拿同一份结论，各自决定怎么用：

| 消费者 | 位置 | 用法 |
|---|---|---|
| **调用前门** | `core/orchestrator.py` `_execute_one` | 权限 → W1 → 钩子**之后**，不可逆延时窗口与自愈层**之前** |
| **ToolSearch** | `tools/tool_search.py` | 命中工具后面条追一行状态，不隐藏缺失项 |
| **system prompt** | `prompts/system.py` `_capability_section()` | 注入"你今天的实际能力"；**全部可用时返回空串，一个字节都不加** |

门的位置有讲究，三处都是刻意的：

- 在权限/W1/钩子**之后**：这三层答"能不能做"，能力门只答"做了会不会必然失败"。反过来会把该拒绝的动作先执行了。
- 在延时窗口**之前**：根本跑不通的动作不该先挂"待发"标签、再到点给用户一条失败——那比当场说清缺什么更像事故。
- 在自愈层**之前**：缺件失败天然不被重试，`ToolResultContent(is_error=True)` 直接返回，不经过 `_recovery`。

拦截话术里硬写着一句：

> 本次调用没有执行。禁止把它当成已验证、已看到、已跑通写进回复。

因为工具回执是模型当下唯一在读的东西。只在 system prompt 里说过一次，长会话里它会忘。

### 两条逃逸路径（不补就是留后门）

不走 `_execute_one` 的工具执行通路有两条，都补了门：

1. **不可逆动作到点真执行**（`_run_held`）：入窗口那一刻判过，但窗口里可能过了几十秒，环境完全可能变（用户刚卸载、venv 刚切换）。这条传 `force=True` 强制重探——拿缓存结论放行一个外发动作，等于自检没做过。
2. **实时语音自己拼调度**：`/talk` 链路不经编排器，在工具装配处判。

### 提示词里的两条能力段

两段各答一件事，都放在 `# 可用工具` **之前**（顺序有意义：先看见"哪些跑不通"，再看见工具备忘）：

- `# 你今天的实际能力`：缺哪些、别试什么、"没验证"该怎么说。
- `# 当前模型的视觉输入`：`agent/prompts/system.py` 的 `_vision_section()`，只在图片通路不通时出现，给的是**替代手段降级链**（取正文 / 读 DOM / 看日志 / 跑测试 / 读 diff）而不是道歉。详见 §13。

## 8. 自我修复：白名单 + 六道门

`repair.py` 的四个动作是**全部**允许的修复手段，不在表里的一律只给命令：

| 动作 | 标题 | 体积硬顶 | 可代执行 | 写到哪 |
|---|---|---|---|---|
| `fetch-browser` | 下载 playwright 浏览器内核 | 400 MB | ✅ | `%LOCALAPPDATA%\ms-playwright\` |
| `pip-extras` | 安装可选依赖 extras 组 | 300 MB | ✅ | `sys.executable` 所在环境 |
| `fetch-model` | 下载 OCR / 视觉模型权重 | 500 MB | ❌ | `~/.jarvis/assets/` |
| `config-fix` | 修正配置项（如 `model_type` 标错） | — | ❌ | `~/.jarvis/settings.toml` / `models.toml` |

两个 ❌ 不是保守，是各有各的具体理由：

- `fetch-model` 这一层**没有可核对的 URL 清单**，猜着下载等于从任意来源往本机写几百 MB。计划里如实登记"待清单"。
- `config-fix` 必须走已有的 `ConfigSet` 工具（它有自己的权限判定与分级），不能在修复层里另开一条改配置的路——两条路迟早一条绕过闸门。

### 六道门，按顺序判

```text
1  总闸    repair_enabled=false            → refuse
2  单动作  在 repair_disabled_actions 里   → refuse
3  可代执行 auto_executable=false          → manual（只给命令）
4  体积    est_mb > hard_cap_mb            → refuse（超限就不是"补一个自查工具"的量级）
5  无人值守 /away + 任何有代价的修复       → needs_approval（沿用 W1 口径，不另造判断）
6  询问线  est_mb > repair_ask_threshold_mb（默认 200MB）且未确认 → ask（yolo 模式也照样问）
```

第 6 道是"权限大但要问"的落点：即使用户开了 yolo，超 200MB 的下载依然要人点头。这条有专门用例钉住（计划 §7 第 5 条）。

预计耗时 `> repair_background_over_s`（默认 30 秒）转**后台任务**而不是前台阻塞——`playwright install chromium` 实测一分多钟，卡在前台会被当成死掉。

### 默认开，但必须有急停

`repair_enabled` 默认 `True`。配套的是 `/repair` 命令：

```text
/repair                     看闸门状态与最近几条修复
/repair off | on            总闸（落盘 + 立即生效）
/repair disable <动作>      只关这一类
/repair enable <动作>
```

默认动 + 能代执行，就必须存在"一句话叫停"的手段；否则用户想收回去只能去翻配置文件，那不等于没给过他选择。

## 9. 修完必须复测，记录不进 `/undo`

### 复测

执行体拿到退出码之后**不算完**，调 `deep_check(capability, force=True)` 复测：

```python
outcome.state = "done" if report.usable else "failed"
```

只认退出码就等于把"命令跑完了"当成"能力恢复了"。`pip install` 返回 0 但装到了别的解释器、`playwright install` 网络中断但部分完成，都在这一步被挡住。

失败后**一次只试一条路**，回执里写"已停手，不在同一处反复试"。贪吃蛇那次连试 Chrome/Firefox 共 8 条命令就是反面样本——反复重试既烧时间又让用户以为快好了。

### 为什么 `/undo` 撤不掉修复

`CheckpointManager` 快照的是**工作区**。而这四个动作写的地方全在工作区外：`%LOCALAPPDATA%`、`~/.jarvis`、venv 的 site-packages。快照盖不到的东西不能假装能一键退，所以记账时写 `reversible=False` + 一句精确的手工退法（`undo_hint`），回执里也带上。

这条是我给实施计划订正的第三处实质错误——原计划写着"修复动作走 `/undo` 台账可回退"，写的人（我）没核对检查点的快照范围。

### 留痕

修复结果写进**已有的副作用账本**（`actions.jsonl`），条目以 `Repair:` 开头；`/health caps --history` 直读它，不另建一份流水。两处记账迟早对不上，只留一处。

## 10. 播报：自动修了东西必须说

首次自动修复强制播报，**文字 + 语音**（`repair_announce_voice` 默认 True）。语音文案比文字短——"我试过了 X，但没能恢复，详情在文字回执里"，因为播报不是给人读日志的。

这条来自一个更普遍的判断：能自己动手的系统，沉默是最贵的失败模式。用户不知道它装了什么，下次就会怀疑它装的东西。

## 11. 命令面与配置面

```text
/health caps                    静态档
/health caps --deep             加跑冒烟
/health caps <能力名>           单项详情：每条前置条件的实测依据 + 补法
/health caps --json             机器可读（桌面端与审计脚本）
/health caps --markdown         Markdown 档
/health caps --repair <能力名>  按白名单动手修
/health caps --history          最近修复记录
/repair on|off|disable <动作>|enable <动作>
jarvis --doctor                 启动期诊断也走同一份结论（不另立一套判断）
```

入口放在 `/health` 而不是新开一个 `/doctor` 子命令，沿用 `daemon/monitor.py` 顶部那句既有判断：两套并存只会让人搞不清该信哪个。

配置面 `[repair]` 五个字段（真源表在 `config_specs.py`，`/config explain repair` 可查）：

| 字段 | 默认 | 含义 |
|---|---|---|
| `repair_enabled` | `true` | 代执行总闸 |
| `repair_disabled_actions` | `[]` | 单动作黑名单 |
| `repair_ask_threshold_mb` | `200.0` | 超过就询问，yolo 模式也照样问 |
| `repair_background_over_s` | `30.0` | 预计超过则转后台 |
| `repair_announce_voice` | `true` | 首次自动修复语音播报 |

## 12. fail-open：这层自己坏了不能挡主流程

能力自检是**辅助能力**。因此兜底做在**消费者入口**上，而不是每个探针里：

| 入口 | 坏掉时的行为 |
|---|---|
| `orchestrator.capability_block_reason()` | 探测层抛异常 → **返回空串放行**（函数注释里写明“本函数不能弄坏主流程”） |
| `prompts/system.py::_capability_section()` | 异常 → 空串 |
| `prompts/system.py::_vision_section()` | `settings is None` 或异常 → 空串（情况不明时不宣称看不见） |
| `probe.tool_status_note()` / `selfcheck_blockers()` | 无结论 → 空串 |

理由是不对称的代价：自检层挡在主流程面前，它一坏就等于把**全部**能力删了，用户看到的是“什么都干不了”，而真实原因可能只是某个探针读目录权限失败。

探针**内部**则是另一种处理：单条前置条件出错记 `probe_failed` 向上报（§4），不在探针里默默把错吞成“没问题”。

## 13. 模型能力面：同一个问题的另一半

内核装好了、能起浏览器、能截屏，但**模型是纯文本的**——图到了 API 层就被丢掉，而工具回执还写着"图片已回传: 是"。模型于是有依据说"我看到了截图，布局正常"。

裁决点在 `agent/llm/model_capability.py`：

```text
model_type: text | multimodal | unknown   （默认 unknown）
model_has_vision(mt) == (normalize(mt) == "multimodal")
```

三条都不是显然的：

- **`unknown` 必须是独立值**。两值时"没人填"必然被压成某一边，而代价不对称：误判"有"会让模型声称看见没收到的图；误判"无"只是少一项能力且当场可见。
- **内置发货清单是刻意例外**。`configs/models.toml` 里 qwen3.x 走 DashScope 多模态端点，改成 `Generation.call()` 会 `400 url error`——把它们默认成 `unknown` 会把 5 个发货模型里 4 个静默打成看不见图。所以 `BUILTIN_MODEL_TYPE = multimodal`。
- **口径不是新发明的**。`docs/roadmap/PLAN-self-config.md` P4 记录 ② 仓库自己定过："model_type 保守给 text，不猜多模态"。

判据从 `self._model_type == "text"` 换成 `model_has_vision()`，写反就是本次要修的错（有专门用例 `test_unknown_is_not_vision__mutation_nail` 钉住）。

四家 provider 统一"**省略必须留文字**"：

```python
skip_images = not model_has_vision(self._model_type)
# 图片块 → {"type": "text", "text": "[附带图片（当前模型无视觉输入，图片已省略）]"}
```

改造中撞出的既存缺陷：openai 分支下**用户单发一张图时整条消息直接消失**（只在有文字块时才补省略说明），而界面与回执都显示已发送。改了行为，也改了那条把旧行为钉成预期的用例，并在测试里写明理由。

工具侧措辞收在 `core/images.py::image_receipt()`，三处工具共用：

```text
图片附上: 是（jpeg, 最长边<=1280），附上不等于看见：无视觉能力的模型只收到省略说明，不得声称亲眼看过
```

「附上」与「看见」分开，是因为工具只知道图片块挂上了 result，能不能被看见由 provider 决定。

热切换时只在图片通路**翻转**时重拼 system prompt（`_vision_flipped()`），不翻转不动——避免白丢前缀缓存。

## 14. 明确没做

| 没做的 | 为什么 |
|---|---|
| `(vendor, model) → vision` 真值表 | 没有一手依据可填。凭印象写"deepseek-flash 无视觉"，与原来"默认当有"是同一种错，只是方向相反。下一步该做的是：**端点明确拒收图片块时**记一笔并降级告知用户，用真实反馈而不是猜测建表 |
| `fetch-model` 自动下载 | 无可核对 URL 清单（§8） |
| 系统级依赖安装（apt/brew/choco/MSI） | 一旦开口就停不住，且不可撤销；只输出建议命令 |
| 自动升级 jarvis 本体 | editable 环境执行 `pip install -U` 会把自己装坏 |
| 任何删除类修复 | 删除不在"补一个缺件"的语义内 |
| 桌面端协议改动 | 能力矩阵以既有契约形态透出（`--json`），不新增命令面 |

## 16. 想加一项能力怎么加

1. `registry.py` 里加 `CapabilityMeta`：声明 extras 组、必需包（版本问库自己）、资产、密钥、平台、`repair_actions`、关联工具名；确属"缺了就别自称验证过"的，标 `blocks_selfcheck=True`。
2. 若需要真跑一次才可信，加一个 `smoke_probe` 函数名并在 `smoke.py` 实现（子进程 + 硬超时 + 结果写回缓存）。
3. 若要能自动补，动作必须在 `REPAIR_ACTIONS` 白名单里；不在表里的动作，`/health caps` 只会给命令，这是设计而非遗漏。
4. 补测试：至少一条 MISSING、一条 OK、一条 `probe_failed`（证明它不拦也不给命令）。
