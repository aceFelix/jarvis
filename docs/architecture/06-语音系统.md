# 06 - 语音系统

J.A.R.V.I.S 有两套独立的语音系统，各自适用不同场景。

## 一、两套系统对比

| 维度 | `/voice` 语音对话 | `/talk` 实时双工 |
|---|---|---|
| **技术路线** | STT → LLM → TTS 管线 | 全双工 WebSocket |
| **交互模式** | 逐轮对话（听→想→说） | 终端半双工轮替；桌面壳全双工（说话打断） |
| **延迟** | 较高（三段串行） | 极低（流式全双工） |
| **模型** | 任意 LLM + TTS + STT | 绑定 DashScope 实时模型 |
| **打断** | ESC 键/关键词 | 服务端 VAD 自动检测（桌面全双工） |
| **复杂推理** | 支持（任意 LLM） | 受限（实时模型能力） |
| **UI** | 终端 | 终端 + 工作台 + 桌面壳 jarvis-desktop |

**为什么有两套**：
- `/voice` 适合需要复杂推理的场景（任意 LLM）
- `/talk` 适合低延迟自然对话（全双工打断）
- 两者不能互相替代

### 回声消除 AEC（/talk）

[aec.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/aec.py) 用 WebRTC AudioProcessor 消除扬声器回声：

- 近端麦克风（24kHz）与远端参考（扬声器）统一重采样到 **16kHz**
- 按 **10ms 帧**（160 samples = 320 bytes）送入 AudioProcessor
- 依赖：`pip install aec-audio-processing numpy`

**为什么需要 AEC**：实时对话中扬声器播放的 AI 语音会被麦克风拾取形成回声，AEC 让"边说边听"不炸麦。

## 五、/voice 闭环

[voice_loop.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/voice_loop.py) 实现 **听 → 想 → 说** 循环：

```
🎤 聆听 → STT 识别 → LLM 思考回答 → TTS 朗读 → 🎤 聆听 → ...
```

### 单轮流程

```python
async def _voice_loop_round(events, settings, loop, ctx, tts, stt, interrupt_event, stop_event):
    # 1. 听：STT 录音识别（状态外抛给宿主适配器，不再直写终端）
    events.on_state(STATE_LISTENING)
    # 阻塞录音放工作线程（asyncio.to_thread），避免饿死宿主事件循环
    result = await asyncio.to_thread(
        stt.listen,
        max_seconds=settings.voice_max_seconds,
        silence_seconds=settings.stt_silence_seconds,
        on_partial=events.on_user_partial,  # 实时识别中增量
    )
    events.on_user_transcript(result.text)

    # 2. 想：LLM 流式推理（复用 QueryLoop）
    events.on_state(STATE_THINKING)
    stream_player = StreamTTSPlayer(api_key=_voice_api_key(settings), ...)
    stream_player.start()
    # 组合 feeder：LLM 每吐一句 → 同时送本机 TTS 合成 + 外抛流式 delta 给宿主上屏
    def _feed(text):
        stream_player.feed(text)
        events.on_ai_text_delta(text)
    ctx.on_assistant_text = _feed
    # 重置 abort_event，防止上一轮残留信号跳过本轮 LLM 调用
    ctx.abort_event = asyncio.Event()
    stats = await loop.run(user_text, ctx)

    # 3. 说：冲刷剩余缓冲 + 阻塞等播完（WS 断开自动降级整段播放）
    events.on_state(STATE_SPEAKING)
    player_stats = await asyncio.to_thread(stream_player.finish)  # 工作线程，播报期间宿主循环不饿死
```

> 打断：每轮起 daemon 轮询线程监听外部传入的 `interrupt_event`（`_INTERRUPT_POLL_SEC=0.05`），置位即中断本轮推理/播报并回聆听；打断来源由宿主适配器挂接（REPL=键盘 ESC；serve=麦克风 barge-in + 桌面壳按钮双通道）。
>
> 音频 I/O 线程模型：`stt.listen` / `StreamTTSPlayer.start/finish` 均为阻塞 pyaudio / 网络调用，统一经 `asyncio.to_thread` 放工作线程跑，保证宿主事件循环（serve 指令循环 / REPL 主循环）不被录音播放饿死——否则 serve 宿主下桌面壳 `voice.stop` / `voice.interrupt` 指令无法被消费（按钮无响应，见 docs/fixlogs/voice-stop-unresponsive-fix.md）。轮询线程同时监听 `stop_event`：`voice.stop` 在播报中到达时立即停 TTS，让工作线程里的 `finish()` 提前返回。

### 关键设计

- **复用 QueryLoop**：语音模式复用当前 REPL 的 QueryLoop 和 LLM（含工具调用）
- **流式 TTS**：`ctx.on_assistant_text` 回调把文本增量喂给 `StreamTTSPlayer`
- **思考隔离**：思考内容只显示终端面板，不进入 TTS
- **markdown 清洗**：在 [tts_text.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/tts_text.py) 集中剥离代码块/markdown 符号/`<think>`/工具占位符标签；`stream_tts.py` 内置一份等价清洗，改动需保持同步
- **API Key 隔离**：`_voice_api_key(settings)`（在 voice_config.py）始终从 `DASHSCOPE_API_KEY` 环境变量取值，不受 LLM 模型切换影响（切到 DeepSeek 时 STT/TTS 仍用 DashScope Key）
- **待机双层检测**：① 关键词快速匹配——用户说"退下/拜拜/不聊了"等（`_EXIT_WORDS`）；② LLM 意图——回复末尾输出 `<standby/>` 标记。`_detect_standby(since_index=...)` 只检查本轮新增消息（防止旧会话残留误触发），且去掉标记后正文超过 30 字视为正常回答误触，不待机
- **残留清理**：退出语音模式时 `_clean_standby_messages()` 移除 goodbye 消息及其前一条 user 消息，避免下次语音会话误触发待机
- **停止 vs 打断意图区分**：stt 停止标志（`stt._request_stop()`）只负责中断阻塞录音；结合 `stop_event` 判定意图——已置位（Ctrl+C / `voice.stop`）→ 抛 `KeyboardInterrupt` 干净退出会话；未置位（`voice.interrupt`）→ 清标志继续聆听/待机，不误杀会话

### 打断机制

- **打断信号解耦**：`voice_loop` 不再自 new 键盘 watcher，改监听宿主传入的 `interrupt_event: threading.Event`（每轮 daemon 线程 50ms 轮询）；置位即停当前推理/播报并回聆听。打断来源由适配器挂接：
  - **REPL**：`barge_in_key`（默认开）。[repl_adapter.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/repl_adapter.py) 的 `start_key_watcher` 起 [barge_in.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/barge_in.py) 的 `_KeyBargeInWatcher`（`keyboard.is_pressed("esc")` 每 100ms 轮询，非全局钩子免管理员权），ESC 回调置位 `interrupt_event` + 中断阻塞的 `stt.listen`；待机阶段按 ESC 退出语音模式。
  - **serve / 桌面壳**：麦克风 `_BargeInWatcher`（RMS 能量）挂接 `interrupt_event`（播报中开口自动打断）+ 桌面壳 `voice.interrupt` 指令置位同一 event（按钮通道），双通道并存。聆听/待机期间打断仅中断当前录音并继续聆听/待机；退出会话由 `voice.stop` 负责（置 `stop_event` + 中断录音）。
- **关键词打断**：`barge_in`（默认关）TTS 播报期间检测"闭嘴""等一下"等（`_INTERRUPT_WORDS`）
- **退出**：说"退下"（或任意结束意图）→ LLM 告别 → 进入待机，说"贾维斯"唤醒

### 配置

## 六、/talk 实时双工语音

### 架构：传输无关引擎 + 双适配器（2026-09-28 重构）

[realtime_engine.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/realtime_engine.py) 是协议/状态机核心，
不感知音频来自哪里；采集/播放由适配器以鸭子类型注入：

```
            RealtimeEngine（协议状态机 / 静音策略 / 响应救援 / Function Calling）
              ↑ _mic.read(n, False)   ↓ _spk.write(pcm)（鸭子类型音频接口）
   RealtimeTalk（终端）           BridgeMic / BridgeSpk（桌面桥接）
   PyAudio 16k入/24k出 + ESC       jarvis-desktop Web Audio ⇄ serve `talk.audio`/`talk_audio`
```

### 连接建立

```python
async def run_session(self, ui, extra_tasks=()):
    url = f"{self._ws_url}?model={self._model}"
    headers = {"Authorization": f"Bearer {self._api_key}"}

    # 禁用默认 ping 心跳：服务端生成长音频时来不及回 ping 会被判死连接(code=1006)
    async with websockets.connect(url, additional_headers=headers,
                                 ping_interval=None, ping_timeout=None) as ws:
        # 唯一一次 session.update：会话配置（含 tools）必须在此一次性完成于 IDLE
        # 状态——中途补发 session.update 会毒化会话（此后每条响应 ~100ms 内被
        # cancelled），MCP 工具因此必须在 connect 之前加载完毕
        await ws.send(json.dumps({
            "type": "session.update",
            "session": {
                "modalities": ["text", "audio"],
                "voice": self._voice,
                "instructions": self._instructions,
                "turn_detection": td,   # server_vad 带 threshold+silence_duration_ms
                "tools": self._all_tools,
            }
        }))

        # 并发运行四路核心协程 + 适配器附加任务（如终端 ESC watcher）
        await asyncio.gather(
            self._send_audio(ws, ui),      # 发送麦克风音频（含静音门控）
            self._recv_events(ws, ui),     # 接收服务端事件
            self._response_rescue(ws, ui), # 响应救援：补发 response.create
            self._watchdog(ws),            # 停止时主动关闭 WS，解除 recv 阻塞
            *extra_tasks,
        )
```

> 轮次检测由 `turn_detection` 配置决定（默认 `"server_vad"`）：声学 VAD + 静音时长判停，
> **尾音延长当前轮而非触发新轮次**，是免提场景的官方推荐。`"smart_turn"` 语义判停偏早，
> 尾音易被重检为新轮次掐死响应（需配轮末静音窗缓解，见下文）；环境音转写与说话人增强
> 两个能力仅在 smart_turn 下可用（详见本节末尾"环境音转写与事件时间线"）。

### 核心协程

#### 1. `_send_audio` — 发送麦克风音频

```python
async def _send_audio(self, ws, ui):
    while self._running:
        # 阻塞读放在工作线程，不饿死事件循环；3200B ≈ 100ms @16kHz mono
        data = await asyncio.to_thread(self._mic.read, CHUNK_BYTES, False)

        if self._aec is not None:
            # AEC3：用扬声器参考信号消除回声；帧对齐可能产生空数据（跳过发送）
            data = await asyncio.to_thread(self._aec.process_mic, data)
            if not data:
                await asyncio.sleep(SEND_INTERVAL)
                continue

        if self._ai_speaking:
            # 二次回声抑制：AI 说话时把麦克风压到 10%，防残余回声被服务端误判成人声
            data = _attenuate_pcm(data, ECHO_SUPPRESS_FACTOR)

        await ws.send(json.dumps({
            "type": "input_audio_buffer.append",
            "audio": base64.b64encode(data).decode(),
        }))
        # 每 8 个 chunk（~160ms）上报一次音量驱动 UI
        ui.on_volume(_rms(data))
        await asyncio.sleep(SEND_INTERVAL)
```

#### 2. `_recv_events` — 处理服务端事件

```python
async def _recv_events(self, ws, ui):
    async for message in ws:
        event = json.loads(message)
        t = event.get("type")

        # 可观测性：每条事件计数，开关开启时写时间线日志（零行为风险）
        self._events.observe(t, event)

        if t == "input_audio_buffer.speech_started":
            # 服务端判定用户开口 → 打断 AI（先记活动响应，再清状态）
            ui.on_user_speaking(True)
            self._restart_speaker()  # 截断当前 AI 语音

        elif t == "response.audio.delta":
            # AI 语音增量
            audio_data = base64.decode(event["delta"])
            self._speaker.write(audio_data)
            ui.on_ai_speaking(True)

        elif t == "response.created":
            # 一次服务端响应开始 → 标记活动响应（打断判定的权威依据）
            self._response_active = True

        elif t in ("response.done", "response.audio.done"):
            # 响应结束（协议权威事件为 response.done，status=completed/
            # cancelled/failed）→ 统一复位活动标志、说话态与超时计时器
            self._end_response(ui)

        elif t == "response.audio_transcript.done":
            # AI 转录完成
            ui.on_ai_transcript(event["transcript"])

        elif t == "conversation.item.input_audio_transcription.completed":
            # 用户转录完成 → 已进入对话轮
            self._events.note_user_turn()
            ui.on_user_transcript(event["transcript"])

        elif t in (AMBIENT_DELTA, AMBIENT_COMPLETED):
            # 环境音转写 → 服务端听到了但判为非有效轮次（不写对话上下文）
            text = self._events.feed_ambient(t, event)
            if text:
                ui.info(f"🔇 未入对话轮（服务端判为非有效语音）: {text}")
```

```python
async def _esc_watcher(self, ui):

        if keyboard.is_pressed("esc"):
            self._running = False

        await asyncio.sleep(0.1)
```

### 打断机制（VAD）

服务端 VAD 检测到人声 → 下发 `speech_started` 事件 → 客户端重启扬声器流截断当前 AI 语音。

**为什么用服务端 VAD**：
- 客户端 VAD 需要持续检测，延迟高
- 服务端 VAD 与模型理解一体，准确度高
- 真正的"说话即可打断"

#### 响应生命周期与打断判定

一次服务端回复由两个事件界定，二者成对维护 `_response_active`：

| 事件 | 语义 | 客户端动作 |
|---|---|---|
| `response.created` | 一次响应开始 | `_response_active = True` |
| `response.done` | 响应结束（`status` = completed / cancelled / failed） | `_end_response()`：清活动标志 + 说话态 + 超时计时器 + UI 回待机 |

**打断判定只看 `_response_active`**：`speech_started` 到达时，只有服务端确实处于一次
活动响应中，客户端才发 `response.cancel`。若用本地播放态（`_ai_speaking`）推断，
一次状态残留就会让后续每轮都误发取消，把用户的正常追问一并取消——
2026-09 修复，复盘见 [docs/fixlogs/realtime-talk-response-done-fix.md](../fixlogs/realtime-talk-response-done-fix.md)。

> `response.audio.done` 并未定义在 DashScope 协议中，`_end_response()` 把它作为
> 历史兼容一并接受，避免旧路径回潮时状态再次卡死。

**麦克风二次衰减**：AI 说话期间，`_should_attenuate()` 默认把麦克风音频乘
`ECHO_SUPPRESS_FACTOR`（0.1），**AEC 已启用时同样如此**。

原因：WebRTC AEC3 在免提外放 + 非理想延迟对齐下只能消除部分回声，残留会
被服务端重新识别为用户语音 → 触发 `speech_started` → 本轮回复被 `response.cancel`
取消，表现为“AI 永远不开口”。2026-09 曾在 AEC 生效时去掉该衰减，直接导致
`/talk` 完全不可用，随即回退，复盘见
[docs/fixlogs/realtime-talk-echo-self-cancel-fix.md](../fixlogs/realtime-talk-echo-self-cancel-fix.md)。

佩戴耳机（无扬声器回声）时可通过配置关掉，让插话语音保持正常增益：

```toml
[realtime_talk]
echo_suppress_with_aec = false   # 默认 true；仅耳机场景建议关闭
```

该压低只在 AI 真正说话期间生效（`response.done` 会及时复位 `_ai_speaking`），
不会永久压小用户语音。

**自打断可见性**：`response.done` 带 `status=cancelled` 时，客户端会提示
“⚠️ 回复被打断取消”并计入 `cancelled_responses`；若退出时 AI 一条也没说完过
且有取消记录，会输出回声成因的诊断摘要（建议改戴耳机或确认上述配置）。

**回声保护窗口**：单靠压低仍挡不住所有外放回声（AI 长回复时尤其明显），因此
叠加一层基于电平的判定。`_send_audio` 在 AI 说话期间逐帧记录衰减后麦克风的
实时 RMS（`_last_mic_rms`）；`speech_started` 到达时，若 AI 正在说话（`_ai_speaking`）
且 `_last_mic_rms` 低于 `ECHO_GUARD_RMS`（0.012），判定为回声误触发，直接忽略本次
打断（不发 `response.cancel`、不清扬声器、不计入 `interrupts` 打断动作），计入
`echo_guard_hits`。用户真实插话需说够响使衰减后电平超过门限才能打断——
这是“外放连续对话”与“随口打断”之间的折中取舍。

> 回声保护只针对“AI 正在说话时”的回声误触发；AI 已说完后的新一轮 `speech_started`
> 不受影响（`_ai_speaking` 已为 False）。复盘见
> [docs/fixlogs/realtime-talk-echo-guard-window.md](../fixlogs/realtime-talk-echo-guard-window.md)。

**半双工模式（默认，`half_duplex = true`）**：免提外放 + 软件 AEC 的兜底解法。
上述衰减与回声保护都是“边听边说”（全双工）下的补救，但纯外放无法彻底区分回声与
真实语音——只要 AI 说话期间麦克风持续上传，`smart_turn` 就可能把回声/混响误判为
“用户仍在说话”，导致 AI 说完后迟迟收不到安静信号、**永远不开启下一轮回复**（表现为
“第一轮能答，之后我说话它一直不接”）。半双工从源头切断：

- `mic_muted()`（`realtime_audio.py`）为真时，`_send_audio` **不中断上传，改为发送等长静音帧**
  （`silence_like()`：DashScope 要求客户端持续送流，输入一断服务端的判轮状态机就卡住）；
- 静音时机 = **响应进行中**（`_response_active or _ai_speaking`）+ **轮末静音窗**
  （仅 smart_turn：`speech_stopped` 起 `MIC_TURN_END_MUTE_SECONDS`，3s，堵尾音重检空窗）+
  **工具轮之后的等待窗口** + 回复结束后一段回声尾迹窗口（`_end_response` 设
  `_mic_resume_at`：普通回复用 `MIC_TAIL_SECONDS`，默认 0.6s，让扬声器余音/混响散尽；
  工具轮用 `MIC_MUTE_MAX_SECONDS` 兜底，等下一轮最终回复）；
- 窗口过后恢复上传，用户再说下一句，服务端正常判停、AI 正常回复；
- 窗口未到期但用户真在继续说话（RMS 超 `VOICE_RMS`），`voice_gap()` 立即清窗恢复上传，
  **不吞话**。server_vad 默认下无需轮末静音窗（声学判停要求真实静音，天然免疫尾音重检）。

> **静音从 `response.created` 就要生效，不能等 AI 出声**：`response.created` → 首个
> `response.audio.delta` 之间存在空窗期（模型思考 + Function Calling 工具执行，需工具的
> 提问可达数秒）。若只在 `_ai_speaking` 时静音，空窗期内上传的尾音/环境噪声会被服务端
> 当成新用户轮次而取消本轮响应，且需工具的提问最易复现。同时设悬挂保护
> `MIC_MUTE_MAX_SECONDS`（30s）：响应状态异常悬挂过久则强制恢复上传，避免麦克风永久哑掉。
>
> **响应期间一律忽略 `speech_started`**：官方协议中打断是服务端行为（检测到用户新语音时
> 自动以 `status=cancelled` 结束本轮），客户端不应补发 `response.cancel`。smart_turn 会
> **提前**判停并启动响应，管道中剩余的音频稍后才被处理到并触发 `speech_started`；若据此
> 取消，用户每次提问都会被自己刚说的话“打断”（表现为 `⚠️ 回复被打断取消`）。
>
> **静音时仍持续读麦克风**：门控置于 `mic.read` **之后**——只拦上传、不拦读取。否则音频
> 驱动缓冲积压，恢复上传时首批送出的是 AI 说话期间的回声，等价于没静音。
>
> **第五次修正已被推翻（2026-09-28 第六次复盘）**：第五次修正据“成功轮的
> `response.created` 之前没有 `→mic`，失败轮全部紧挨”得出“响应创建前静音会致服务端
> 立刻取消”——实机再验证证明这是**混淆变量归因错误**：当时每轮紧挨的 `→mic` 同时存
> 在另一个变量——**MCP 就绪后中途补发 `session.update` 毒化了会话**（被毒化的会话里
> 每条响应本就活不过 ~100ms 且签名完全相同）。无中途 update 的会话在
> `response.created` 后才静音仍出现取消，且取消早于静音生效——**真实成因**：smart_turn
> 语义提前判停后，半双工静音要到 `response.created` 后的下一个发送循环才生效，中间
> ~100ms 空窗里用户的尾音/换气被服务端 VAD 重新检出为新轮次 →
> `response.done[cancelled, reason=turn_detected]` 掐死刚创建的响应。
>
> **三大对策**（详见 `realtime_engine.py` docstring 与 fixlog 第六次修正）：
> ① 会话配置（含 MCP tools）必须在首个 `session.update` 一次性于 IDLE 完成，禁止中途补发；
> ② 默认轮次检测从 smart_turn 切为官方免提推荐的 **server_vad**（尾音延长当前轮）；
> ③ smart_turn 可选保留，但需轮末静音窗 `MIC_TURN_END_MUTE_SECONDS`（3s）堵住尾音重检
> 空窗；另工具表瘦身（`tools_mode="builtin"`，299 schema 全量表实测会拖慢服务端建响应）。
>
> **工具轮结束后继续静音**：工具轮的 `response.done` 不按普通回复留 0.6s 尾迹，而是保持静音
> 直到下一轮最终回复结束——工具执行 + 二次推理期间的环境声同样会被判成新用户语音
> （表现为“问时间这类要调工具的提问没反应”）。判定方式是 `output` **全为** `function_call`
> （官方文档明确“一轮响应也可能同时包含普通消息和函数调用”，故必须“全为”）。
>
> **取消时打印事件链回溯**：`⚠️ 回复被打断取消` 下方直接打出最近 24 条语义节点（新→旧），
> 当场分辨“服务端收到新语音后取消”（链上有 `speech_started`）与“客户端补发 cancel”
> （链上没有）——两者修复方向相反。客户端指令（`response.create` / `response.cancel` /
> `session.update` / 麦克风静音窗口进出）带 `→` 前缀进入同一条时间线；`response.done`
> 节点带 status（`[cancelled]` / `[completed]`），`event_log = true` 时全量事件按序落盘
> `~/.jarvis/logs/diag.log`（取消快照与开关无关，始终落盘）。

代价是失去“随口打断”——但外放场景本就打断不了，等于无损。**戴耳机想保留全双工
打断**时设 `half_duplex = false`，此时回到衰减 + 回声保护 + `speech_started` 打断逻辑。

> **打断开关即 `half_duplex`**：全双工（false）下服务端判定用户开口即打断
> （`speech_started` → 清扬声器缓冲 + 发 `response.cancel`）；半双工（true，默认）下
> AI 说话期间不上传真实音频（改发静音帧），自然不被打断。（旧版文档提到的 `barge_in_enabled` 字段在
> 当前代码中已不存在；`/voice` 侧的 `voice_barge_in` 是另一套东西，与 /talk 无关。）
> 复盘见 [docs/fixlogs/realtime-talk-half-duplex.md](../fixlogs/realtime-talk-half-duplex.md)。

### 响应救援（rescue，默认开）

服务端存在两类“吞轮”异常：① 响应被 `turn_detected` 取消后不再补答（被检出的
“新轮次”其实只是尾音，无下文）；② 用户轮次已提交（转写完成）但服务端迟迟不自动
创建响应。两者都表现为“说了话，贾维斯永远不回复”。

引擎第 4 路协程 `_response_rescue` 做客户端兜底：到期后补发一次 `response.create`
（官方允许“等待用户下一轮输入时”手动触发；轮内误发只是良性 error，连接不受影响）：

- **武装点**：`turn_detected` 取消后 +1.2s（`RESCUE_AFTER_CANCEL_SECONDS`）；轮次提交后
  无 `response.created` +1.8s（`RESCUE_AFTER_COMMIT_SECONDS`）；正常流会被 `response.created`
  提前撤掉 `_rescue_at`，机制零干扰。
- **三闸门防“重复回答”**：① 任何 `response.done` 撤销待执行救援，且发射需距上次应答
  完成 ≥1s；② phantom 抑制——单字/纯标点轮、与 AI 刚播内容重合的回声轮不武装；
  ③ 两次救援最小间隔 2s（`RESCUE_MIN_INTERVAL_SECONDS`）。
- **救援保持**：补发到 `response.created` 之间置 `_rescue_hold`，强制静音
  `RESCUE_HOLD_SECONDS`（1s）——窗口内用户任何声响都会被服务端当新轮掐死救援响应。
- 可用 `[realtime_talk] rescue = false` 整体关闭；桌面全双工路径（服务端无静音窗）同样启用。


- **协议**（[protocol.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/serve/protocol.py)）：
  `talk.start` 新增 `duplex?: bool`；新指令 `talk.audio`（渲染进程→服务端，base64 PCM16
  16kHz，~100ms/帧，fire-and-forget 无回执，服务端 64KB 上限校验）；新事件
  `talk_audio`（服务端→渲染进程，base64 PCM16 24kHz AI 语音帧；**空串 payload = 打断 flush**，
  是引擎 `spk.stop_stream()` 的远端镜像）。
- **浏览器 AEC 是全双工成立的关键**：`getUserMedia({echoCancellation: true})` 的系统级
  回声消除补齐了 WebSocket 协议官方标注“回声消除：无”的短板——AI 外放被麦克风拾取时
  在进网之前就已消除，服务端 VAD 只听到用户真实语音。因此桌面路径引擎参数
  反向关闭三重软件消除防发闷：`half_duplex=False`、`echo_suppress_with_aec=False`、
  `use_aec=False`。
- **服务端缓冲**（`BridgeMic`）：超限（5s）丢最旧防延迟堆积，欠载等待后补静音帧
  维持送流；**播放侧**（渲染进程 `talkPlayback.ts`）按 AudioContext 时钟 nextTime 接续排播
  免帧间咔哒；采集侧（`talkCapture.ts`）AudioWorklet 整数比抽取重采样，Blob URL 注册免
  打包器配置。
- 终端路径（PyAudio + 软件 AEC）仍是半双工轮替；两条路径共用同一个 `RealtimeEngine`，
  协议/静音/救援逻辑零复制。

### 实时工具调用（Function Calling）

`/talk` 支持实时工具调用，工具面由 `tools_mode` 控制：
- **默认 `"builtin"`**：只注册 `get_current_time` / `end_conversation` 两个内置工具，
  低延迟优先——实测 299 个 schema 的全量工具表会导致“轮次提交后服务端迟迟不创建响应”；
- **`"all"`**：装配 `ToolRegistry` 全部工具（排除 `AskUserTool`）+ MCP，会话启动稍慢，
  MCP 必须在首个 `session.update` 之前加载完毕（经验 ①）；工具名经
  `sanitize_tools_for_realtime` 清洗非法函数名（防模型受限解码停滞）；
- 高风险的写操作（命令执行/文件删除/发邮件）由模型层指示**先语音确认**再执行；
- 权限层 `check_permissions` 对 deny 级操作（如 `rm -rf /`）**直接拒绝**，不依赖模型判断；
- 语音模式下强制开启思考（防止 TTS 朗读 reasoning_content）。

### 环境音转写与事件时间线（2026-09 第 1 层可观测性）

**要解决的问题**：smart_turn 模式下（仅 `turn_detection = "smart_turn"` 时产生；默认
server_vad 无此通道），服务端判定"VAD 检测到语音活动、但语义为非有效轮次"
（噪声、"嗯""啊"等无语义内容、与 AI 刚说内容高度重合的回声）时**不触发对话轮**，
只把 ASR 结果经 `conversation.item.ambient_audio_transcription.delta/.completed`
透传，且**不写入对话上下文**。

客户端此前没有订阅该事件 → 用户说了话、服务端也听到了，屏幕上却一个字都不显示，
表现为"我一直在说，它就是不回复"；因为这条通道不可见，也无法区分"被语义过滤"
与"进了对话轮但没回复"。

**现在的行为**（[realtime_events.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/realtime_events.py) 的 `TalkEventLog`）：

| 通道 | 事件 | 屏幕表现 | 是否进对话上下文 |
|---|---|---|---|
| 有效轮次 | `conversation.item.input_audio_transcription.completed` | `🧑 你: …` | 是 |
| 非有效轮次 | `conversation.item.ambient_audio_transcription.*` | `🔇 未入对话轮（服务端判为非有效语音）: …` | 否 |

- delta 阶段只按 `item_id` 累积，completed 定稿后才打印一行，避免逐片刷屏
- 会话结束时，若本次有语音被判定为非有效轮次，输出诊断摘要（如
  `📋 本次有 3 段语音被服务端判为非有效轮次（已听到、未进入对话轮）` + 是否零对话轮），
  直接回答"话去了哪条路"；只在确有语义过滤时输出，正常对话不受打扰

**事件时间线日志**（可选，`[realtime_talk] event_log`，默认关）：
开启后把本次会话收到的每条事件按序写入 `~/.jarvis/logs/diag.log`（component=`realtime`），
用于复盘交互时序（谁在何时打断谁、有没有出现无响应的空窗）。高频的
`response.audio.delta` / `response.audio_transcript.delta` 只计数不逐条落盘，
避免音频帧刷爆轮转日志（1 MB）。

> 本层**零行为风险**：只增加可见性，不改 VAD、不改麦克风增益、不改 `session.update` 参数。
> 回归测试：`tests/voice/test_realtime_observability.py`。
> 完整排查过程与根因分析见 [docs/fixlogs/realtime-talk-silent-turn-observability.md](../fixlogs/realtime-talk-silent-turn-observability.md)。

**后续层（尚未实施，按证据推进）**：说话人增强（`turn_detection.voiceprint_audio_urls`
声纹锁定，从源头拒掉 AI 音色回声，需公网可访问的声纹音频）→ AEC 实测 → 半双工兜底。

## 八、PyAudio 音频处理

[audio.py](file:///e:/2.MyProjects/MyAgentChat/J.A.R.V.I.S/jarvis/agent/voice/audio.py)：

- **/talk 输入（麦克风）**：PCM 16-bit, 单声道, **16000 Hz**（`INPUT_RATE`）
- **/talk 输出（扬声器）**：**24000 Hz**（`OUTPUT_RATE`，DashScope 实时模型要求 24kHz）
- **/voice 录音**：统一 16kHz 单声道 16-bit PCM
- **PyAudio 全局单例**：Windows PortAudio 非线程安全，audio.py 用模块级单例统一管理，防 segfault
- **音量计算**：RMS（均方根）

## 九、两套系统资源冲突

- 两套系统共用麦克风硬件
- 同时开启可能导致 PyAudio 设备占用错误
- **建议**：一次只用一套

## 十、设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 两套语音系统 | 并存 | 适用场景不同 |
| /voice 复用 QueryLoop | 是 | 支持任意 LLM + 工具调用 |
| /talk 引擎与传输解耦 | RealtimeEngine + 鸭子类型音频接口 | 终端/桌面复用同一协议状态机，逻辑零复制 |
| 轮次检测 | 默认 server_vad | 声学判停要求真实静音，尾音延长当前轮，规避 smart_turn 尾音重检掐死响应 |
| 响应救援 | 客户端补发 response.create | 服务端吞轮（turn_detected 取消/建响应超时）兜底，三闸门防重复回答 |
| 桌面全双工 | 浏览器 AEC（getUserMedia） | 系统级回声消除补齐 WebSocket 协议“回声消除：无”短板，说话即打断 |
| VAD | 服务端 | 准确度高，延迟低 |
| AEC（终端） | WebRTC AEC3（aec-audio-processing） | 消除扬声器回声；软件 AEC 不彻底时退半双工 |
| TTS | 流式优先 | 低延迟体验 |
| STT | 单后端 QwenASR | 统一质量与断句行为，避免多实现分叉 |
| 实时工具 | tools_mode 分层 + Function Calling + 语音确认 | 默认内置 2 工具低延迟；全量需自行验证；高风险先语音确认，deny 级直接拒绝 |
| 环境音转写 | 显式订阅并显示 | 把"被语义过滤"与"进了对话轮"区分开，消除黑盒哑火 |
| /talk 事件时间线 | 可选落盘 diag.log | 复盘交互时序；高频 delta 只计数，避免刷爆日志 |
| 思考隔离 | 不进 TTS | 避免朗读思考过程 |
