## 一、解决什么问题

五层权限管线（见 [04-权限系统](04-权限系统.md)）只能回答"**允不允许**"，
回答不了管家形态的两个问题：

1. **这次调用值不值得打断用户**——允许 ≠ 现在就该问；
2. **人不在场时该不该做**——ASK 在无人时应转为"入库待批"而不是干等。

W1 运行时层挂在管线结论之后，作为统一闸门 `policy_gate()`，由三个确定性
零件组成（刻意不引入 LLM 判断——权限路径必须可解释、可审计、可复现）：

| 零件 | 文件 | 职责 |
|---|---|---|
| 授权租约 | `lease.py` | 有限期、有限范围的免打断授权，到期自动失效 |
| 打扰预算 | `budget.py` | 主动播报的五步闸门：冲刷/重要度/静默时段/聚合窗口/额度 |
| 共享状态 | `state.py` | away 标志 + 待批清单，跨进程 JSON 落盘 |
| 空转检测 | `loop_detect.py` | 同型工具调用滑动窗口，循环时拦刹车（见 §3.5） |
| 统一闸门 | `__init__.py` | `policy_gate()` 合并次序 + `init_policy(settings)` 注入 |

## 二、并入管线的声明式规则（原策略引擎能力）

原 `policy.yaml` 独有的两项能力已并进 `permissions/checker.py`：

1. **allow 规则可放宽 ASK**：旧管线 `_stricter` 只收紧不放宽，带 spec 的
   allow 规则（如 `Bash(git *)`、`FileWrite(~/reports/**)`）永远压不过工具
   默认/特判 ASK，permissions.yaml 形同虚设。现在命中即放宽（独立合并
   函数 `_relax_by_rule`，口径对齐 yolo）；
2. **路径作用域 glob**：文件类工具 spec 做 `~` 展开、workdir 相对化、平台
   大小写归一（`permissions/path_match.py`，与租约共用）。

保守红线（永不放开）：

- **DENY 不可放宽**（硬编码危险规则 / 路径守护拦截）；
- **裸工具名 allow（无 spec）** 只能兜底放宽管线默认 ASK，不能放宽工具
  特判 ASK——免确认必须有明确的免确认范围，防隐式 yolo；
- **跨 workdir 边界的软提醒 ASK**：带 spec 且命中目标的 allow 规则可放宽
  （用户显式白名单，呼应 path_guard"除非用户显式加白名单"的设计）；裸名
  allow 与授权租约均不可放宽（租约只签工作目录内路径）。

## 三、合并次序（fail-closed）

```
PermissionChecker.check（五层管线结论 base，含规则放宽）
      │
      ▼
⓪ 沙箱自动放行压制：away 时，reason 带协议前缀"沙箱自动放行:"
      │        的 ALLOW 升级回 ASK（防"mv 做了、FileEdit 被拦"
      │        的半完成状态；同意的 Bash 租约仍可放宽）
      ▼
① 授权租约：只放宽 ASK
      │        · 路径守护软提醒（reason 前缀"路径提醒"）不放宽
      │        · 命中 = 工具名 fnmatch ∧（未限路径 ∨ path_matches 命中）
      ▼
② away 分流：仍为 ASK 的调用
             · 入待批清单（~/.jarvis/pending_approvals.json）
             · 本次 DENY（"回来 /back 呈批"）
```

沙箱压制只认 Bash 工具特判签发的协议前缀（定义见
`permissions/modes.py` 的 `SANDBOX_AUTO_ALLOW_PREFIX`）：中风险自动
放行是"在场时不弹窗"的委托，不是"无人时也可自主执行"的授权；
用户在 permissions.yaml 里显式写过 allow 规则（reason 为"规则命中"）
的命令属预先授权，away 时照常放行。

零介入语义：无生效租约且非 away 时，`policy_gate()` 原样返回管线结论
**对象本身**（`test_gate_zero_intervention` 以 `is base` 断言兜底），
不需要总开关——租约/away 均为零配置设计，不敲 `/away`、不签 `/lease`
时完全不介入。

## 三点五、行为层刹车：空转拦截（闸门之后）

上面 `policy_gate` 处理的是「允不允许」；`loop_detect.py` 处理的是「该不
该继续」——沙箱自动放行把中风险命令一路绿灯后，agent 可能拿着记忆里的假
线索反复全盘 `find`/`ls` 空转（见
[贪吃蛇空转案](../fixlogs/agent-loop-stall-fix.md)）。两道机制互补：

- **同型调用循环检测**（`orchestrator.execute_calls`，闸门后）：
  `call_signature()` 把工具调用归一为 `工具名:动作`（`find`/`ls`/`tree`/`du`
  折叠为命令词本体，同型识别“换个姿势同一条搜索”），同签名在最近 6 次窗口
  内 ≥3 次即把 ALLOW 强制升级 ASK 拦刹车。每轮任务开头 `reset()`，
  单轮最多提示 2 次后静默（防“每次都问”变成新骚扰）。
- **截断续写熔断**（`query_loop`，不在本包）：与沙箱无关的另一种空转——
  思考型模型写不完「长思考 + 工具调用 JSON」时每轮被 max_tokens 截断，
  连续续写封顶 2 次仍凑不出完整响应则熔断停止，避免烧满迭代。

## 四、打扰预算（Horvitz 注意力模型的确定性近似）

`NotifyBudget.gate()` 五步顺序（**2026-10-19 换过一次序**：门槛提到静默之前）：

1. 非静默时段且**已到冲刷时机**（受 `aggregate_window_s` 冷却）→ 先把积压
   聚合成一条补播；补播**不占 `daily_max`**（它是补播不是新增打扰），并且
   当前这条请求仍继续走后续四步裁决，两者都要播时**合并成一条**返回（一次
   调用只起一条气泡，既不丢事件也不叠两个）；
2. 重要度 = 来源权重 × 紧迫度 × 相关性 × 历史接受率，**低于门槛直接抑制**
   （只进感知总线与留痕文件，不进播报队列）；
3. 静默时段（支持跨午夜，如 23:00-07:00）只入库不播 —— 但**入库前已经过了
   第 2 步**：门槛判的是“这件事值不值得打扰”，静默判的是“现在方不方便打扰”，
   前者不成立的事不该在队列里等着半夜过后补播；
4. 聚合窗口（默认 300s）内同源事件（dedup_key）合并抑制；
5. 当日播报超 `daily_max` 上限 → **入库待补播**（够重要的事值得稍后说，
   低价值的在第 2 步就已经被挡掉了）。

冲刷摘要在拼文本前会**按 `ts` 重排**队列：同 key 合并时 `ts` 刷成“最后一次
发生”的时间但不改变条目位置，不重排则“最近 N 条”会挑错。

换序前逐条核过回归面：非感知源在 `daemon` 默认紧迫度 0.6 下最低档是
`default 0.5 × 0.6 = 0.30`，**刚好不小于门槛 0.3**，夜里照旧入库（这条
浮点刀尖事实由 `test_non_percept_sources_unaffected_by_reorder` 钉住）。

来源权重表（`_DEFAULT_SOURCE_WEIGHTS`）：briefing 0.9 / schedule 0.9 / calendar 0.85 /
deadline 0.8 / system 0.7；W2 感知源 `percept:*` 另档（mail 0.9 / vcs 0.7 / file 0.6 /
window 0.5 / vision 0.4）；**W3.1 任务脊柱源 `task` 0.9**（与 `schedule` 同级：后台目标
都是用户明确交代的长线事，递出来的紧迫度固定 0.45，故 0.9×0.45=0.405 仍在门槛之上）；
未登记的源落 `default 0.5`。**新增一类事件源必须先登记权重**：感知层刚接进来时就是因为
`percept:*` 没登记，全部乘到门槛以下、又被无冷却的冲刷路径放出来，形成
“每两条必播一条”（[复盘](../fixlogs/notify-budget-percept-relay-fix.md)）；W3 把同一条
不变量从“记得登记”升级成了可执行断言（`test_task_driver.py::TestBudgetWeightRegistered`）。
同一条不变量（门槛是绝对判据）还有第二条旁路 —— 静默时段入库不评分，
已于 2026-10-19 连同观测口缺陷一起修掉（[复盘](../fixlogs/percept-panel-history-lost-on-rebuild-fix.md)）。

历史接受率由 `record_accept(source, accepted)` 滑动更新（初始 1.0），
是"越用越懂你"反馈闭环的入口。接入点：闸门本体已上提为模块级
`agent/core/daemon/proactive.py::notify_gate_action(source, text, *, dedup_key, urgency, budget,
 silent_delivery)`（返回完整裁决 `NotifyAction`），`apply_notify_gate()` 是它的
“只回文本”薄包装（旧调用点与“预算未注入时仅 away 静默”的行为一字不变）；
`ProactiveEngine.gate_notify()` / `gate_notify_action()` 各自包一层（固定传入
自己的 `get_budget()` 实例），`_dispatch_notify` 又是它的“播完就走 on_notify”包装。
**为何上提**：W2 感知事件由 serve 宿主调，W3 任务脊柱由 REPL（无 `ProactiveEngine`）也要播——
不改模块层就得伪造一个 engine 或再抄一份闸门，两者都会破“所有打扰都过同一个闸”这条不变量。
budget 异常时降级直接播，不因闸门拖垮提醒。

### 提醒的降级投递（2026-10-22）

两件当时测出来的事：

1. **用户自设提醒以前根本不过闸**。`serve/hub._on_fire()` 对 reminder 是直接
   `_emit(...)`，而简报/截止日期/感知事件/任务脊柱都走 `gate_notify`——于是
   `quiet_hours`、`daily_max`、`aggregate_window_s` 对“10 分钟后提醒我喝水”这类
   全部无效（设三条就响三条）。现在提醒走 `hub._deliver_reminder()` →
   `gate_notify_action(source="schedule", dedup_key="schedule:<task_id>", urgency=0.9)`。
2. **但提醒也不该像简报那样被整条延后**。冲刷靠“下一条通知请求”触发，夜里
   没动静就可能永不补播；而 `ScheduleTask.escalate_count` 那套升级重发只有字段、
   无人递增。所以提醒在命中静默时段/额度用尽时改为**降级投递**：
   `NotifyAction(kind="emit", speak=False)`——气泡与系统通知照投、**TTS 不朗读**、
   不入队也不占 `daily_max`（上屏不算一次打扰），但仍记 `last_emit`，所以同一条
   提醒在聚合窗口内重复不会反复刷屏。`gate(silent_delivery=True)` 只由这条路径传，
   简报与感知事件一字不改地保持“入库待补播”。

通道由 `[policy.notify_budget] reminder_channels` 控制（默认 `["screen"]`）：
`screen`=上屏不出声、`email`=另发一封到 `quiet_email_to`（留空用
`[email].default_recipient`）、`sms`=**留位未接入**（警告一次并忽略，绝不假装已发）；
空列表 = 关掉降级，退回入库待补播。通道解析、邮件正文构造与副作用入账集中在
`agent/serve/quiet_delivery.py`（`hub` 只管过闸与起线程，发送走
`quiet_delivery.send_quiet_email`），**不进 `[actions]` 延时窗口**（这封信的目的就是此刻送达），
但**记一条不可逆副作用账**
（`reversible=False` + 原因，`/undo` 据此如实说撤不回）；发信失败只记日志，不重投气泡。

away 与降级的优先级也是有意区分的：`notify_gate_action` 只把**会出声的**
emit 在 away 时降为 queue（TTS 不对空房间说话），而降级投递本就不发声，
away 时气泡照投——否则“人不在 + 静默时段”叠加会把提醒压到两头都看不见。

**跨仓契约（容易只做一半）**：`proactive_notify` 的 payload 多了 `silent` 字段，
`_emit` 缺省跟随 `speak`。桌面壳必须把它透传给 Electron `Notification`
（`dispatcher.ts` → `notify.ts`）：Windows toast 自带提示音，不透传就是
“TTS 闭嘴、toast 响一声”，静默时段等于只做了一半。壳侧只在 silent 为真时写这个键，
旧后端行为零变化。两个意图不共用一个开关：首次引导那类“只想躲长文 TTS 朗读、
却要 toast 醒目（否则用户看不到引导）”的调用显式传 `silent=False`。

回归：`tests/policy/test_notify_budget.py`（降级四例）+
`tests/serve/test_hub_reminder_delivery.py`（接线与通道 11 例）。
两个缺陷（提醒不过闸、`quiet_hours` 个位数写法无声关闭整个静默时段）均为人工实测发现，
完整复盘见 [reminder-notify-budget-bypass-fix](../fixlogs/reminder-notify-budget-bypass-fix.md)。

## 五、跨进程状态与配置

CLI / serve(hub) / daemon 是不同进程，全部状态落盘 `~/.jarvis/`，
tmp + `os.replace` 原子写、mtime 缓存读：

| 文件 | 内容 |
|---|---|
| `leases.json` | 授权租约（读到过期顺带 GC） |
| `policy_state.json` | away 标志 + 最近活动时间（60s 节流） |
| `pending_approvals.json` | 待批清单（上限 50，丢最旧） |
| `notify_state.json` | 预算当日计数 / 待发队列 / 上次冲刷时刻 / 接受率统计 |

settings.toml 配置域（解析见 `config/settings.py` [policy] 节）：

```toml
[policy]
away_idle_minutes = 0     # 0 = 仅认手动 /away；>0 启用空闲推断

[policy.notify_budget]
enabled = true
daily_max = 10
quiet_hours = "23:00-07:00"
aggregate_window_s = 300
min_salience = 0.3
reminder_channels = ["screen"]   # 提醒在静默/超额时的送达通道（见第四节）
quiet_email_to = ""              # email 通道收件人，留空用 [email].default_recipient
```

> 旧键 `enabled` / `path`（策略引擎总开关与 policy.yaml 位置）已随降级
> 合并删除，旧配置残留对应键静默忽略（白名单映射）。

启动接线（两个入口都要注入，缺一不可）：

- 终端 / `jarvis --serve`：`main()` 在最终 settings 定型后调 `init_policy(settings)`；
- 桌面壳 spawn 的 `python -m agent.serve`：由 `serve/app.run_serve()` 首行注入
  （2026-10-22 补，以前这个入口没人调，五个字段在桌面壳里全是硬编码缺省，
  见 [serve-policy-config-not-injected-fix](../fixlogs/serve-policy-config-not-injected-fix.md)）。

hub 构造 `ProactiveEngine` 时传 `get_budget()` 单例。因 `_budget_singleton` 只在首次
`get_budget()` 时按当时快照建立，**改完配置必须重启宿主**才生效（面板上的「感知源」
开关会热装配总线，但不会重建预算）。
