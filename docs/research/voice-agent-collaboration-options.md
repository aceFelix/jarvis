# 语音前台与全职 Agent 的协作方案对比（调研）

> 作者：aceFelix　日期：2026-11-27　状态：**调研记录，未实施**
>
> 问题：`/talk` 的星期五（实时语音模型）能力有限，能否与“贾维斯”（全职 Agent）协作，
> 把星期五办不了的事交给贾维斯？两个 Agent 要不要“对话”？
>
> 本文只做方案对比与取舍记录，不写代码、不拍板。实施细节见
> [plans/voice/talk-hybrid-tools-delegation.md](../plans/voice/talk-hybrid-tools-delegation.md)。

## 一、问题拆解

“两个 Agent 协作”听起来是一个问题，实际包含五个可以独立决策的维度：

1. **协作形态**：用户能不能听到两个 Agent 对话？是单向委派、有限双向，还是自由聊天？
2. **贾维斯运行时**：一次性子 Agent、常驻队友，还是为语音新写的后台执行器？
3. **上下文传递**：完全隔离、共享完整转写，还是共享同一个会话对象？
4. **权限模型**：语音里没有交互确认入口，高风险操作怎么办？
5. **进程拓扑**：同进程线程、独立子进程，还是独立服务？

把这五个维度混在一起谈，很容易得出“要么全做、要么不做”的结论；分开看才能按阶段落地。

## 二、现有基建盘点（决定“能复用多少”）

| 能力 | 文件 | 现状要点 |
|---|---|---|
| 子 Agent 执行器 | `agent/collaboration/subagent.py` | 一次性：独立 QueryLoop + 受限 ToolRegistry + 独立 messages，跑完返回最终文本；**同步阻塞**；默认 `PermissionMode.YOLO`；只继承内置 50 工具，**不含 MCP/宿主工具** |
| 常驻队友 + 邮箱 | `agent/collaboration/teammate.py`、`mailbox.py` | 异步持久运行；邮箱支持 `permission_request` / `plan_approval_request` / 心跳 / 空闲通知；适合“贾维斯卡住时问星期五” |
| 任务清单 / 团队 | `task_list.py`、`team.py` | 多任务排队与多队友协作；首版可不用 |
| 主循环 | `agent/core/query_loop.py` | `QueryLoop(provider, registry, ...)` + `run(user_text, ctx)`；可作为后台执行器核心 |
| 实时引擎 | `agent/talk/realtime_engine.py` | 单会话、server_vad 控轮、`_discard_audio` 闸门、响应救援；协议上支持 `conversation.item.create(role=system)` 与 `response.create`（已核实文档） |
| 语音前台 | `agent/talk/realtime_talk.py` | 星期五人设、终端/桌面共用；当前直带 2 个工具 |

结论：**不需要从零发明 Agent 通信**。subagent / teammate / mailbox 已经覆盖“派活、授权、汇报”三类消息；
真正要补的是“星期五这一侧的桥”——它不是 QueryLoop Agent，没有邮箱循环。

## 三、维度 1：协作形态

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **1A 单向委派** | 星期五传任务，只收最终结果并播报 | 最简单；延迟可控；无循环风险 | 贾维斯卡住时无法问用户，只能失败返回 | 首版验证 |
| **1B 有限双向** | 只开放 `permission_request`（授权）与 `question`（澄清），最多 2 轮 | 解决“要确认才能继续”；对话有边界，不会跑飞 | 需要状态机与超时；实现量中等 | 长期主形态 |
| **1C 自由双向文本对话** | 两个 Agent 自由聊天，自主决定问什么 | 理论上最灵活 | 容易客套/重复确认/死循环；token 与延迟不可控；出错无法归因；用户听不到过程 | 不建议 |
| **1D 可听的双 Agent 对话** | 星期五说“我问一下贾维斯”，贾维斯用第二个声音回答 | 演示效果好，有“两个管家”的戏剧感 | 需第二套 TTS/音色与播放仲裁，抢麦克风/AEC；延迟翻倍；用户分不清该听谁 | 不建议作为功能 |

**取舍**：1B 是唯一同时满足“能协作、可控、可调试”的形态；1A 是它的降级版；1C/1D 只适合演示。

## 四、维度 2：贾维斯的运行时形态

| 方案 | 优点 | 缺点 |
|---|---|---|
| **2A SubagentRunner 一次性** | 现成、上下文隔离、代码量最小 | 同步阻塞（语音仍需套后台线程）；默认 YOLO；无 MCP/宿主工具；不支持中途提问 |
| **2B TeammateRunner 常驻 + 邮箱** | 天生支持授权请求/澄清/心跳/空闲通知；可长期跑、多任务 | 需要 leader 侧读邮箱；星期五不是 QueryLoop Agent，要写桥接层；复杂度最高 |
| **2C 自定义 DelegateRunner** | 完全可控：异步、全量工具（含 MCP）、正常权限、结果注入、取消/超时都按语音定制 | 要自己实现任务生命周期与权限桥；代码量中等 |
| **2D 复用文本会话的同一 QueryLoop** | 上下文天然共享，贾维斯“记得”刚才聊的 | 与文本会话抢历史/状态；语音短句污染长任务；并发不可控 |

**取舍**：2C 最适合语音；2A 用于 P0 验证；2B 等需要“常驻/多任务”再升级；2D 不建议。

## 五、维度 3：上下文传递

| 方案 | 优点 | 缺点 |
|---|---|---|
| **3A 隔离 + 任务简报** | 隐私好、token 省、不受语音闲聊干扰 | 贾维斯不知道细节，可能需要 `question` 补问 |
| **3B 共享完整语音转写** | 信息最全 | token 爆炸；闲聊噪声干扰；隐私面大 |
| **3C 共享同一个会话对象** | 实时同步 | 并发写冲突；语音短句污染长任务上下文 |

**取舍**：3A + 有限 `question`；记忆库共享，但**写权限只给贾维斯**，星期五只读。

## 六、维度 4：权限模型

| 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **4A ask → 直接拒绝并回报** | 语音里没有确认入口，直接说“需要文本模式确认” | 最安全、实现简单 | 很多写操作办不成 |
| **4B 语音二次确认桥** | 贾维斯发 `permission_request` → 星期五问用户 → 用户口头同意 → 回传 allow | 体验完整，真正“协作” | 需防伪造（模型说“用户同意”不算）；需超时/撤回；高风险仍应 deny |
| **4C 沿用 yolo / accept_edits** | 自动放行 | 最省事 | 语音场景无人监督，等于把 Bash/FileWrite 直接开放，不可接受 |

**取舍**：首版 4A，P2 再做 4B；4C 不用于委派。`deny` 级规则即使 4B 也不放行。

## 七、维度 5：进程拓扑

| 方案 | 优点 | 缺点 |
|---|---|---|
| **5A 同进程 + 独立线程/事件循环** | 复用 provider/registry/MCP；实现简单；结果回传直接 | 工具里的 native 崩溃会带走语音进程 |
| **5B 独立子进程 worker** | 隔离性好，长任务/崩溃不影响语音；可单独重启 | 需要 IPC、序列化上下文、生命周期管理；MCP/registry 要重建 |
| **5C 独立本地服务（HTTP/WS）** | 可多客户端、可远程 | 最重，超出当前需求 |

**取舍**：5A 起步；若实测 Bash/浏览器工具拖崩语音进程，再考虑 5B。

## 八、整体组合对比

| 组合 | 形态 | 能力 | 开发量 | 体验 | 适合 |
|---|---|---|---|---|---|
| **S 轻量单向** | 1A + 2A + 3A + 4A + 5A | 派一次性任务，只收结果；不能问、写操作基本被拒 | 小 | 能查/能读/能分析，写不了 | 验证链路 |
| **M 有限协作** | 1B + 2C + 3A + 4B + 5A | 一次性任务 + 授权/澄清桥 + 全量工具/MCP + 播报/取消 | 中 | 最接近“星期五搞不定就给贾维斯” | 正式形态 |
| **L 常驻团队** | 1B + 2B + 3A + 4B + 5A/5B | 贾维斯常驻、多任务、多队友、心跳与任务清单 | 大 | 最强，但首版易过度设计 | 后台持续干活阶段 |
| **X 可听双 Agent** | 1D | 两个声音对话 | 中 | 演示效果好，实际抢麦/延迟/身份混乱 | 不建议 |

**当前倾向**：先 S 验证链路，再演进到 M；L 等“常驻/多任务”成为真实需求再上；X 不做。

## 九、待调研：独立 Agent 之间如何协作（后续）

以下方向**尚未核实**，只登记为调研问题，不在本文下结论：

### 9.1 协议与标准

- Google **A2A（Agent-to-Agent Protocol）**：任务/能力发现、消息与工件模型是否适合桌面单机场景；
- **MCP**：它是工具/资源协议，不是 Agent 间任务协议；能否作为“能力发现”层与 A2A 组合；
- OpenAI **Agents SDK handoffs**：handoff 语义与上下文传递方式；
- 其它候选：Agent Protocol、ACP 等（需核实活跃度与实现）。

### 9.2 框架与模式

- 监督者（supervisor）vs 对等（peer）vs 黑板（blackboard）vs 合同网（contract net）；
- AutoGen / CrewAI / LangGraph 等框架的消息模型、终止条件、失败回滚；
- 多 Agent 的“发言权/轮次”控制，避免无限对话；
- 共享记忆的并发写与冲突合并策略。

### 9.3 评估维度

- 延迟与成本：一次协作往返的 token/时延上限；
- 确定性：同样任务在多次运行中的结果稳定性；
- 可观测性：消息轨迹、任务 ID、失败归因；
- 安全：授权传递、防伪造、最小权限、审计；
- 可终止性：超时、取消、幂等与回滚。

### 9.4 具体调研问题清单

1. 单机桌面场景是否需要标准化协议，还是文件邮箱 + 结构化消息足够？
2. “用户口头同意”如何转成不可伪造的授权凭证（一次性 token / 签名消息 / 会话内授权表）？
3. 两个 Agent 共享记忆时，谁写、谁读、冲突如何裁决？
4. 长任务跨越语音会话结束时，任务应挂起、转后台还是终止？
5. 多 Agent 协作的失败恢复：部分完成的结果如何标记与回滚？

## 十一、结论（暂定）

- 想法成立：星期五做前台，贾维斯做后台，用结构化协议协作；
- **不做自由聊天、不做双声音对话**；“对话”只保留授权与澄清两类，且最多 2 轮；
- 先 S 后 M，L 按需；所有阶段都必须满足：单飞、可取消、可审计、权限不可伪造。
