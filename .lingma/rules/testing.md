# 新业务/新功能测试交付规则

## 适用范围

本规则适用于所有项目：

- 后端项目（Java / Spring Boot / Python 等）
- 前端项目（Vue / React / Vite / 小程序等）
- 桌面应用、工具脚本、CLI 工具等

无论项目规模大小、技术栈如何，只要涉及**新业务**或**新功能**的开发，都必须遵守本规则。

## 触发条件

以下任一情况发生时，开发者在代码变更完成后必须进行完整的测试交付：

1. 新增业务模块或功能模块。
2. 新增 API、命令、配置项、UI 页面、工具函数、组件等。
3. 引入新的外部依赖、SDK 或服务集成。
4. 对现有功能进行重构或行为变更（影响输入、输出、调用方式）。

## 强制要求

### 1. 必须编写测试

根据项目类型和变更范围，至少完成以下一种测试：

| 项目类型 | 最低测试要求 |
|---|---|
| 后端项目 | 单元测试 + 集成测试（如涉及外部服务/数据库） |
| 前端项目 | 组件测试 / 页面功能测试 + 构建验证 |
| CLI / 脚本 | 命令执行测试 + 核心逻辑单元测试 |
| 跨模块功能 | 端到端（E2E）测试或人工走查清单 |

### 2. 测试必须可运行

- 所有新增测试代码必须能在本地或 CI 环境中稳定运行。
- 不允许提交无法运行、跳过（skip）、或依赖本地特殊环境的测试用例。
- 测试用例命名应清晰表达被测场景，避免 `test1`、`test2` 等无意义名称。

### 3. 必须达到基础覆盖率

- 核心业务逻辑：至少覆盖正常路径和主要异常路径。
- 新增代码应尽量避免无测试覆盖的裸奔代码。
- 对于纯 UI 展示或脚手架代码，可适当放宽，但需在 PR/交付说明中注明原因。

## 后端项目测试要求

后端项目在代码变更后，除满足 [backend.md](backend.md) 的编译要求外，还需：

1. 为新增 Service / Repository / Controller / Util 编写单元测试。
2. 涉及数据库、缓存、消息队列、外部 HTTP 调用的，编写集成测试或本地可运行的模拟测试。
3. 新增 API 时，补充接口测试用例（参数校验、正常返回、异常返回）。
4. 测试命令示例：
   - Java / Maven：`mvn test -q`
   - Python：`pytest` 或 `python -m unittest`

## 前端项目测试要求

前端项目在代码变更后，除满足 [frontend.md](frontend.md) 的构建要求外，还需：

1. 新增组件、页面、Store、组合式函数时，补充单元测试或功能测试。
2. 涉及用户交互的流程，提供手动走查清单或自动化 E2E 测试。
3. 新增 API 调用或状态管理逻辑时，覆盖成功、失败、加载中等状态。
4. 测试命令示例：
   - Vue / Vite：`npm run test:unit` 或 `vitest run`
   - E2E：`npx playwright test` 或 `npm run test:e2e`

## 测试文档要求

如果功能复杂、涉及多模块协作、或自动化测试难以覆盖全部场景，必须编写测试文档：

- 测试目标与范围
- 测试环境（依赖服务、数据库、浏览器版本等）
- 测试用例（输入、操作步骤、预期结果）
- 通过标准
- 已知限制或待补充项

测试文档可放在 `docs/testing/`、`tests/README.md` 或模块级 `README.md` 中，路径需在交付时说明。

## 验收标准

新业务/新功能仅当同时满足以下条件时，才视为完成：

- [ ] 编译/构建通过。
- [ ] 新增测试用例全部通过。
- [ ] 未引入新的失败测试或回归问题。
- [ ] 测试文档或测试代码已随功能代码一并提交。
- [ ] 核心流程经过至少一次人工验证或 E2E 验证。

## 与现有规则的衔接

本规则是对 [backend.md](backend.md) 和 [frontend.md](frontend.md) 中“编译/构建验证”要求的补充：

- 编译通过只是最低门槛，不能替代测试。
- 文档更新规则仍按 [document-update.md](document-update.md) 执行。

## 例外情况

以下情况可酌情降低测试要求，但需在代码注释或 PR 说明中明确记录：

- 纯配置变更、注释修改、日志文案调整。
- 紧急热修复，后续需在 24 小时内补齐测试。
- 第三方依赖版本升级，且无业务逻辑改动。
