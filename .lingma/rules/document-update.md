# 文档更新规则

## 适用范围

本规则适用于所有项目（前端、后端、桌面应用、工具脚本等）。

## 触发条件

凡发生以下任何一种情况，都必须在完成代码变更后同步更新相关文档：

1. **新功能 / 新业务开发**：新增模块、新增命令、新增 API、新增配置项、新增 UI 页面、新增工具函数等。
2. **旧功能 / 旧业务升级**：功能行为改变、接口签名变化、参数增减、返回值变化、调用方式变化等。
3. **旧功能 / 旧业务优化**：性能优化、交互优化、安全策略调整、架构重构、依赖替换、流程改动等。

## 必须更新的文档范围

代码变更完成后，应检查并更新项目内所有已有的 Markdown 文档，包括但不限于：

- `README.md`
- `docs/` 目录下所有 `.md` 文档
- `CHANGELOG.md`
- `CONTRIBUTING.md`
- 模块级 `README.md` 或说明文档
- 项目根目录下的其他说明文档

## 更新要求

1. **README.md 优先**：若变更影响安装、配置、使用方式、功能列表、依赖环境、运行命令等，必须首先更新 `README.md`。
2. **能力详解与架构文档**：若变更涉及核心架构、功能实现、运作流程、安全策略、配置字段等，应同步更新 `docs/architecture/` 下的架构说明文档。
3. **修复 / 优化复盘**：若变更是修复 bug、功能异常或性能问题，必须创建或更新修复复盘文档（如 `docs/fixlogs/`）。
4. **路线图 / 计划文档**：若变更改变了项目阶段目标或技术方向，应同步更新 `docs/roadmap/` 等规划文档。
5. **保持一致性**：所有文档中的示例命令、配置字段、目录结构、功能描述、版本号、徽章等必须与实际代码保持一致。
6. **禁止遗漏**：不能因为文档多、改动小、时间紧等原因跳过文档更新；文档更新是功能交付的必要组成部分。

## 更新前检查清单

提交代码前，先自检以下问题：

- [ ] 新增的功能是否在 README.md 的功能列表或使用说明中有体现？
- [ ] 新增的命令、API、配置项是否在相关文档中有说明和示例？
- [ ] 修改的接口、参数、返回值是否已同步修改文档中的示例和描述？
- [ ] 架构图、流程图、目录结构图是否仍然准确？
- [ ] 本次变更是否涉及安全、权限、错误处理策略，相关文档是否已更新？
- [ ] 本次变更是否需要新增修复复盘、升级记录或变更日志条目？

## 文档更新完成后

完成文档更新后，应与代码变更一起提交，提交信息中应体现文档同步更新的内容。
